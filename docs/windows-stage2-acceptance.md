# Приёмка этапа 2: первичная настройка Windows

Дата: 8 ноября 2026 года. Проверяемый исходный код: `0e4ca90a9e3f2b9b65432fd9d6ddbfe386977ca5`.

Этап принят связанным пакетом: выбор источника, подключение к базе и NAS, проверка источника работающим агентом/службой и первый запуск с тестовым восстановлением. Это невыпущенные изменения рабочей ветки.

## Подблоки

| Подблок | Реализация и проверка |
| --- | --- |
| 2.1. Выбор источника | Примеры для файловой 1С, файлов/папок, MS SQL, PostgreSQL и WebDAV используют существующую подсказку мастера. Название задания отделено от имени базы и адреса сервера. Частые ошибочные пути/URL/строки подключения в поле SQL-базы отклоняются с пояснением; порт PostgreSQL вводится отдельно, IPv6 сохраняется. WPF проверяет все типы и ошибочный ввод; исходные требования видимости параметров в компактных формах файлов и WebDAV пройдены без ослабления. |
| 2.2. Подключение к базе | Логин MS SQL показан отдельно от пользователя Windows; для PostgreSQL указан пользователь параметров подключения. Пояснены Windows/SQL-вход, пароль PostgreSQL, внешние настройки пользователя службы и отдельная проверка TLS. Общая проверка источника использует те же подключения и секреты, что копирование. MS SQL подтверждает доступ и BACKUP DATABASE, PostgreSQL — SELECT 1; интерфейс не выдаёт это за проверку создания и восстановления архива. Нативный SCM-сценарий проверяет PostgreSQL с делегированным паролем и TLS под отдельной учётной записью. Существующие сценарии окна предупреждения MS SQL о сертификате сохранены. |
| 2.3. NAS и сетевые папки | В основном и дополнительном хранилищах показан пример UNC, пояснены подключённые диски, отдельный логин назначения и права чтения источника. Доступ Проводника не принимается за доступ службы. Нативный стенд проверяет разрешённый и запрещённый UNC-источник под фактическим пользователем службы, а также существующие проверки хранилищ/NAS. |
| 2.4. Проверка источника службой | Отдельный канал `source-checks`, явная возможность `CanCheckSources`, привязка к сеансу, сохранённому заданию и его параметрам. Проверены идентичность/время результата, отмена, устаревшие команды, ошибочные подтверждения, отказ и последующая успешная проверка, защита от повторной обработки. Старый агент не подменяется проверкой окна и не получает команду создания копии. WPF проверяет обращение к работающему агенту; SCM проверяет отдельную Windows-учётную запись, занятый файл и неизменность истории/каталога при работающем расписании. |
| 2.5. Первый запуск | Меню «Файл → Первый запуск задания…» открывает отдельную прокручиваемую инструкцию по типу задания: сохранить → проверить источник и хранилища → создать пробную копию → найти/проверить архив → восстановить в отдельную папку или тестовую базу. После сохранения и на итоговом шаге есть указатель следующего действия. WPF открывает/закрывает инструкцию, проверяет её содержание и соответствие размеру владельца в обычном и компактном режимах; общий сценарий включает создание копий, проверку и восстановление тестовых файлов. Инструкция не меняет профиль и ничего не запускает сама. |

## Границы приёмки

Использован GitHub-hosted Windows (`windows-latest`) с изолированной службой и отдельным пользователем, собственными разрешённой/запрещённой SMB-папками и PostgreSQL. Подготовка комплекта Windows-стенда не означает выполнение перезагрузок или полной матрицы ОС. Реальные сеансы 1С, удалённый MS SQL, доменная работа, перезагрузки и целевые версии Windows остаются стендами этапов 3, 4 и 7 дорожной карты.

Новый выпуск не опубликован. Публичные версии остаются Windows `v0.2.0-alpha.34` и Server `v0.1.0-preview.8`. Старые теги, файлы выпусков и ветки дистрибутивов сохранены; PR №2 остаётся открытым черновиком.
