# Установить сервер SP Backup в Proxmox

Этот установщик создаёт **новый непривилегированный LXC** с Debian 13 amd64, PostgreSQL 17 и сервером управления SP Backup. Архивы резервных копий продолжают храниться в хранилищах агентов; это контейнер панели управления и её базы данных.

Скрипт из рабочей ветки и Linux-архива по умолчанию устанавливает опубликованный сервер **preview.9**. Конкретную версию можно закрепить параметром `--version 0.1.0-preview.9`. Существующие выпуски и их файлы не меняются. Нужен доступ администратора к Shell хоста Proxmox, интернет для шаблона/пакетов и свободные ресурсы: по умолчанию 2 CPU, 2 ГБ RAM и 16 ГБ диска. Docker и .NET SDK не требуются.

Для существующего LXC из мастера в рабочей ветке добавлен отдельный режим
`--update --id <номер CT>` — см. раздел «Обновить существующий LXC» ниже.
Режим обновления ещё не входит в скрипт, упакованный в неизменяемый preview.9:
сначала получите актуальный скрипт из рабочей ветки.

Установка сервера, PostgreSQL, HTTPS и вход администратора проверяются в отдельном Debian 13. В этом стенде вызовы `systemctl` записываются, а настоящие PostgreSQL и сервер запускаются отдельно. **Реальный Proxmox и запуск через настоящий systemd пока не проверены.** Первую установку выполняйте в отдельный тестовый CT; существующие рабочие VM/CT скрипт не использует.

## 1. Запустить мастер

1. Войдите в веб-панель Proxmox.
2. Слева выберите **узел Proxmox**, затем **Shell**. Команды выполняются на хосте от `root`, а не внутри другого контейнера.
3. Скачайте скрипт и запустите его:

```sh
wget --https-only -O /root/create-sp-backup-server.py \
  'https://raw.githubusercontent.com/sanekman/1C-Backup/feature/local-backup-agent/deploy/server/create-proxmox-lxc.py' && \
python3 /root/create-sp-backup-server.py --version 0.1.0-preview.9
```

Это загрузка скрипта из рабочей ветки. Он получает проверенный архив preview.9; прежние выпуски не изменяются. Перед запуском файл можно просмотреть: `less /root/create-sp-backup-server.py`.

4. Ответьте на вопросы мастера:

- **Номер контейнера.** Предлагается свободный номер из кластера. Занятые номера, включая VM на другом узле, отклоняются.
- **Понятное имя системы мониторинга.** Например, «Бухгалтерия — основной». Это подпись панели; она не является DNS-именем или адресом подключения.
- **HTTPS-порт.** Обычно 7443. Можно выбрать другой свободный порт, например 8443 или 443. Порты 22 и 5432 зарезервированы для системных служб.
- **Хранилище диска.** Выберите предложенное хранилище Proxmox с поддержкой LXC. Если `local-lvm` отсутствует, мастер предложит другое доступное.
- **IPv4/CIDR.** Для постоянного сервера лучше указать свободный статический адрес, например `192.168.1.120/24`, и шлюз `192.168.1.1`. Согласуйте адрес с администратором сети. Для первого теста можно оставить `dhcp`.

Если оставили DHCP, закрепите полученный адрес за контейнером в маршрутизаторе. Изменение IP после установки нарушит подключение по сохранённому адресу и сертификату.

Мастер сам найдёт и скачает Debian 13 standard amd64 через `pveam`, создаст CT, настроит запуск при загрузке Proxmox, установит PostgreSQL и проверенный пакет сервера. Если каталогу `pveam` давно не делали обновление и шаблона нет, выполните `pveam update` и повторите запуск. Существующие диски, NAS, VM/CT и правила брандмауэра хоста не изменяются.

## 2. Получить пароль и сертификат

В конце будет показан адрес, например `https://192.168.1.120:7443/`, и команды с **фактическим номером CT**. Ниже используется номер 120 — замените его, если мастер создал другой.

Логин панели — `admin`. Получите первоначальный пароль в Shell Proxmox:

```sh
pct exec 120 -- cat /etc/onec-backup-server/administrator-password.txt
```

Пароль генерируется внутри контейнера, не передаётся через аргументы установки и не печатается в общем журнале мастера. Сохраните его в менеджер паролей. После смены пароля панели этот файл продолжает содержать первоначальное значение; повтор установки его не сбрасывает.

Мастер создаёт отдельный центр сертификации для этого сервера и сертификат HTTPS с выбранным адресом. Чтобы Windows и служба агента доверяли серверу, скопируйте **публичный** сертификат:

```sh
pct pull 120 /etc/onec-backup-server/ca.crt /root/SP-Backup-CA.crt
```

Затем на Windows откройте PowerShell и скачайте файл через SSH. В примере `192.168.1.10` — адрес **хоста Proxmox**, а не нового CT; замените его своим:

```powershell
scp root@192.168.1.10:/root/SP-Backup-CA.crt "$env:USERPROFILE\Downloads\SP-Backup-CA.crt"
```

При первом SSH-подключении проверьте отпечаток ключа хоста Proxmox. Используйте свой доступ администратора; пароли в команды или чат не вставляйте.

На каждом Windows-компьютере, который подключается к панели или службой агента:

1. Откройте скачанный `SP-Backup-CA.crt` двойным щелчком.
2. Нажмите **Установить сертификат → Локальный компьютер**. Подтвердите запрос администратора.
3. Выберите **Поместить все сертификаты в следующее хранилище → Обзор → Доверенные корневые центры сертификации**.
4. Завершите импорт и перезапустите браузер.

Выбирайте именно **локальный компьютер**, чтобы сертификат был доступен и службе Windows, работающей под другой учётной записью. Импортируйте только публичный сертификат вашего сервера. Закрытый ключ CA находится в `/etc/onec-backup-server/private` и для подключения клиентов не нужен; его не копируют на клиентские ПК.

## 3. Войти и подключить агент

1. Откройте адрес из вывода мастера в браузере. После импорта сертификата предупреждений HTTPS быть не должно; проверку TLS не отключайте.
2. Войдите как `admin` с полученным паролем. В разделе сервера смените первоначальный пароль на свой.
3. Создайте приглашение агента в панели.
4. В Windows-агенте alpha.31 откройте **Настройки → Подключения** и подключитесь по приглашению.
5. Проверьте, что агент появился в панели и передаёт свежие данные. Для серверных файловых заданий можно включить режим **Задания с сервера**; для обычного мониторинга автономных заданий менять режим не требуется.

Если панель недоступна, проверьте выбранный IP, DNS, порт и правила сети / брандмауэра Proxmox. Скрипт не открывает доступ в интернет через маршрутизатор и не меняет общие правила хоста. При включённом firewall разрешите входящий TCP на выбранный HTTPS-порт для нужных компьютеров. PostgreSQL слушает только `localhost` внутри CT; открывать порт 5432 не нужно.

## 4. Параметры без диалога

Например, для свободного CT 120, пула `local-lvm`, моста `vmbr0`, статического IPv4 и порта 8443:

```sh
python3 /root/create-sp-backup-server.py --non-interactive \
  --id 120 --name 'Бухгалтерия — основной' --rootfs-pool local-lvm \
  --bridge vmbr0 --ip 192.168.1.120/24 --gateway 192.168.1.1 \
  --dns 192.168.1.1 --port 8443
```

Для своего DNS-имени добавьте `--address https://backup.example.com:8443/`. Заранее настройте это имя на IP нового CT. Для нестандартного моста, ресурсов или уже скачанного шаблона предусмотрены `--bridge`, `--cores`, `--memory`, `--disk`, `--template`; полный список — `python3 /root/create-sp-backup-server.py --help`.

## 5. Состояние и повтор после ошибки

Открыть консоль собственного CT:

```sh
pct enter 120
systemctl status onec-backup-server
journalctl -u onec-backup-server -n 50 --no-pager
exit
```

Мастер считает установку успешной только после ответа HTTPS `/health/ready`. При ошибке CT и его данные остаются на месте. Если запрос установки уже скопирован внутрь, мастер выводит команду продолжения; повтор с теми же параметрами сохраняет пароли, сертификат и первого администратора. Если создание не дошло до сохранения запроса, сначала исправьте шаблон/хранилище/сеть; занятый CT скрипт автоматически не переиспользует и не удаляет.

Повтор внутренней установки после успешного завершения проверяет кодировку базы и доступность сервера. Изменение версии, адреса или имени через сохранённый запрос отклоняется. **Это установщик нового сервера, а не средство обновления существующего:** он не заменяет рабочую БД, не сбрасывает пароль и не удаляет старые версии.

### Кодировка базы: исправление в рабочей ветке после preview.5

Новая база `onecbackup` создаётся явно в **UTF8**, независимо от кодировки PostgreSQL и языковых настроек контейнера. Это необходимо для русских названий и сообщений мониторинга. При повторе установки существующая база с другой кодировкой отклоняется; данные, пароли и кодировка базы сохраняются.

Если панель открывается, но агент остаётся «Ожидает первого сигнала», а PostgreSQL сообщает `unsupported Unicode escape sequence`, проверьте кодировку **внутри CT**:

```sh
runuser -u postgres -- psql -X -d onecbackup -c 'SHOW server_encoding;'
```

Ожидается `UTF8`. При `SQL_ASCII` требуется отдельный перенос с проверенной резервной копией в новую UTF8-базу. Повтор установки и обновление клиента эту существующую базу не исправляют. Сохраните исходную базу до проверки переноса; не удаляйте её и не меняйте кодировку правкой системных таблиц PostgreSQL.

Перед будущим обновлением сохраните проверенную согласованную копию всего сервера, включая PostgreSQL, настройки и закрытые ключи. Для полной копии CT можно штатно остановить его и создать резервную копию средствами Proxmox; храните её как секретные данные и проверьте восстановление на отдельном CT. Не копируйте работающую PostgreSQL обычным файловым копированием.

## 6. Обновить существующий LXC

Этот режим предназначен для LXC, созданного мастером SP Backup, **без Docker**.
На узле Proxmox откройте Shell от root. CT должен быть запущен на этом узле.
В примере **120 — номер вашего CT, замените его своим**.

Один раз получите новый скрипт: у старого установщика этого режима нет.

```sh
wget --https-only -O /root/update-sp-backup-server.py \
  'https://raw.githubusercontent.com/sanekman/1C-Backup/bd1c586e30bf6665064d7a96dd7d49ce01291d9a/deploy/server/create-proxmox-lxc.py'
```

Затем обновление запускается одной командой из Shell Proxmox:

```sh
python3 /root/update-sp-backup-server.py --update --id 120
```

Без `--version` выбирается наибольший опубликованный совместимый серверный
preview 0.1.0. Для конкретного выпуска:

```sh
python3 /root/update-sp-backup-server.py --update --id 120 --version 0.1.0-preview.9
```

Команда проверяет существующий LXC и передаёт скрипт внутрь через `pct push/exec`.
Каждый шаг на узле выводит своё название: состояние CT, создание каталога,
передача файла, проверка SHA-256 и запуск. У вызовов `pct` нет терминальных
stdin/stdout/stderr: вывод передаётся в консоль через pipe, ввод не требуется.
После `pct push` SHA-256 файла внутри CT должен совпасть с исходником на узле;
при ошибке передачи или несовпадении запуск блокируется. Автоматических повторов нет.
CT не создаётся заново и не перезагружается. Внутри проверяются завершённая
установка, current, штатная служба, пути, UTF8 базы и текущий HTTPS.
Нестандартная установка и понижение версии отклоняются.

Строка `ConnectionString` проверяется по параметрам: порядок, регистр имён,
пробелы, кавычки, `localhost` и явный порт 5432 не требуют её переписывать.
Допускаются локальная `onecbackup` и UTF8-копия с именем
`onecbackup_utf8_ГГГГММДД_ЧЧММСС` под пользователем `onecbackup`. Перед остановкой
проверяются существование БД, владелец `onecbackup`, кодировка UTF8, таблицы
`public.server_schema`, `public.server_users`, `public.server_agents`, пароль
из штатного файла и совпадение TCP-подключения с кластером PostgreSQL 17/main.
Размер, дамп и возврат относятся к имени из `ConnectionString`; это имя
записывается в закрытый `state.json`. Оставшаяся старая БД не изменяется.
Дополнительный файл подключения, переменные службы, другой адрес, порт,
неподдерживаемое имя БД или пользователь приводят к отказу. Значения строки и пароли в ошибках не выводятся.

Если прежний скрипт остановился с сообщением «Конфигурация отличается от штатной
установки», а диагностика указала только `ConnectionString`, получите исправленный
скрипт по ссылке выше и повторите команду. Настройки вручную менять не требуется:
равнозначная запись принимается, содержимое `server.json` сохраняется. Отказ
на этой проверке происходит до остановки службы, миграции и переключения программы.

Пакет скачивается по публичному манифесту и проверяется по размеру/SHA-256 до
остановки службы. Затем сохраняется закрытый комплект прежней программы,
БД, конфигурации, ключей, данных и unit-файла, выполняется миграция от сервисного
пользователя и атомарно переключается current. После запуска требуется успешный
HTTPS `/health/ready`. Пароли, сертификат и администратор не создаются заново;
PostgreSQL и настройки CT не переустанавливаются. Повтор той же версии проверяет
готовность и не перезапускает службу.

Комплекты находятся **внутри CT** в `/var/backups/onec-backup-server/<дата>-<суффикс>`,
права каталога 0700; они содержат секреты. Другой путь внутри CT можно передать
через `--backup-directory /путь`. Нужны место для БД, программы, данных и 1 ГиБ
запаса; место не резервируется от других процессов. Комплекты и прежние версии
автоматически не удаляются. Кроме них сохраняйте полную штатную копию CT.

При обычной ошибке миграции/запуска возвращаются БД, конфигурация, данные,
программа и current; результат обновления остаётся ошибкой. При повреждённом
комплекте возврат не продолжается и успех не объявляется. Жёсткое отключение CT,
`kill -9` и отказ диска требуют ручного восстановления из комплекта: автоматическое
возобновление после такого сбоя не заявляется. Перенос на другой CT, SQL_ASCII,
внешняя БД, произвольные имена БД, переименование службы и изменённые пути
в этот режим не входят. Подключённая SQL_ASCII-база требует отдельного переноса
в UTF8; сохранённая старая SQL_ASCII-база рядом с рабочей UTF8-копией не мешает обновлению.
