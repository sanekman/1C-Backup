# Копирование баз SQL из приложения

Задания MS SQL и PostgreSQL используют общие ручной запуск, планировщик, ZIP, доставку, историю и хранение последних N копий. Они исполняются вручную, в фоновом агенте или в службе Windows без открытого интерфейса. Доступны локальный и сетевой каталоги, FTP/FTPS с логином и паролем в диспетчере учётных данных Windows. Мониторинг внешних SQL-копий остаётся отдельной функцией и не заменяет эти задания.

## Microsoft SQL Server

Создайте задание `SqlServer`, укажите имя базы в поле источника и экземпляр сервера. Подключение использует начальный каталог `master` и обязательное шифрование с проверкой TLS-сертификата. Начиная с alpha.25 доступны два способа входа: учётная запись Windows исполнителя (прежний вариант по умолчанию) и отдельный логин MS SQL. Во втором случае нажмите «Задать логин и пароль MS SQL…»: значения сохраняются в Windows Vault, а задание содержит только `credentialKey` и `authentication: SqlServer`. В строку подключения пароль не включается: используется `SqlCredential`. Проверка источника использует тот же способ входа, что и копирование. Для службы пароль экспортируется в существующий защищённый DPAPI-кэш; импорт с другим SQL-сервером или без доступного пароля требует заново сохранить данные входа. Существующая привязка повторно используется только для уже известного локального задания с тем же сервером. В alpha.25 мониторинг внешних SQL-копий использует Windows-аутентификацию; в следующем пакете он также получает отдельный SQL-логин — см. [инструкцию мониторинга](external-backup-monitoring.md). Учётной записи нужны права на резервное копирование выбранной базы и `RESTORE VERIFYONLY`.

Укажите два пути к одному каталогу:

- Каталог для `BACKUP` в файловой системе SQL Server, например `D:\SqlStage`.
- Путь к этому каталогу для чтения приложением, например `\\sql-server\SqlStage` либо `D:\SqlStage`, если приложение работает на том же компьютере.

Службе SQL Server нужны права записи в первый каталог, пользователю приложения — чтения через второй путь. Серверный каталог также может быть абсолютным путём Linux для соответствующего SQL Server. Каталог должен существовать на стороне SQL; приложение не создаёт его на удалённом сервере.

Исполнитель создаёт полный `.bak` с уникальным именем командой `BACKUP DATABASE ... WITH COPY_ONLY, CHECKSUM`, затем выполняет `RESTORE VERIFYONLY ... WITH CHECKSUM`. Сжатие SQL не запрашивается, чтобы не зависеть от редакции сервера. База и путь передаются SQL-параметрами. После проверки агент проверяет доступность непустого файла и передаёт его общему модулю доставки. Ограничение времени применяется ко всему созданию и проверке; отмена передаётся SQL-драйверу.

Если конечный каталог совпадает с каталогом чтения SQL-копии и ZIP выключен, файл регистрируется на месте без повторного копирования, и правила N действуют на зарегистрированные `.bak`. При переносе в другой каталог или упаковке исходный `.bak` сохраняется в SQL-каталоге; лимит N относится только к зарегистрированным копиям конечного хранилища. Для исходных SQL-файлов нужна отдельная политика обслуживания. Ошибка проверки, доступа или доставки не удаляет предыдущие успешные копии. При отмене на сервере может остаться частичный `.bak`, который не считается успешной копией.

Рабочий файл `sql-source.json` сохраняет серверный и доступный агенту пути для диагностики; при успешной операции рабочий каталог удаляется. `RESTORE VERIFYONLY` проверяет набор резервной копии, но не заменяет пробное восстановление в отдельную тестовую базу.

## PostgreSQL

Создайте задание `PostgreSql`, укажите имя базы, сервер, порт и пользователя. Начиная с alpha.25 кнопка «Найти PostgreSQL на этом компьютере» ищет установленные клиентские утилиты в реестре Windows и обычных папках Program Files. Если найдено несколько версий, выберите нужную: `pg_dump` и `pg_restore` берутся из одной папки `bin`. При отсутствии результата введённые пути не стираются. Ручной выбор находится в «Выбрать утилиты вручную или посмотреть пути». Поиск не запускает найденные EXE и не проверяет доступность сервера. Создаётся дамп одной базы в формате custom, затем проверяется через `pg_restore --list`. Утилиты должны поддерживать версию сервера; рекомендуется использовать инструменты той же основной версии. Непустой дамп и нулевые коды обоих процессов обязательны до доставки и очистки.

Начиная с alpha.25 для обычного входа выберите **Пароль, сохранённый в программе**, заполните пользователя и нажмите **Задать пароль PostgreSQL…**. Пароль сохраняется в Windows Vault отдельно от FTP и MS SQL; в JSON задания записывается только ссылка. После сохранения задания отдельно нажмите **Проверить источник**: сохранение пароля само по себе не проверяет подключение. При смене сервера, порта или пользователя пароль нужно задать заново.

При проверке подключения и копировании программа создаёт одноразовый файл libpq с доступом только текущему пользователю, SYSTEM и администраторам. Он находится вне рабочей папки архива, не попадает в копию и удаляется после успеха, ошибки или отмены. Пароль не передаётся в аргументах и `PGPASSWORD`. Для службы владелец экспортирует только пароли используемых заданий в защищённый DPAPI-кэш; файл подключения создаётся уже под пользователем службы. При уже настроенной службе новый пароль подготавливается автоматически при сохранении задания; повторять установку службы не нужно. Ввод пароля в отменённом черновике сам по себе не предоставляет службе новую запись. Работа службы с сохранённым паролем не требует ручного `pgpass.conf`.

Импорт настроек не переносит пароль. Доступная ссылка повторно используется только для известного локального задания с теми же сервером, портом, пользователем и идентификатором пароля. В остальных случаях мастер попросит задать пароль заново, сохранив остальные параметры.

Для прежних заданий остаётся вариант **Настройки PostgreSQL на этом компьютере**. Он использует стандартный libpq: например, `%APPDATA%\postgresql\pgpass.conf`, путь `PGPASSFILE`, сертификат или вход Windows. Здесь парольный файл настраивается для пользователя, под которым работает приложение; служба использует файл владельца с предоставленным доступом. После замены файла может понадобиться повторная настройка прав. В alpha.24 этот способ был единственным. Настройки TLS libpq, включая `PGSSLMODE` и сертификаты, продолжают действовать; единый мастер TLS остаётся следующим этапом.

Ограничение времени действует на `pg_dump` и последующую проверку вместе. Отмена останавливает дерево процессов, а рабочие файлы сохраняются при ошибке. Дамп не включает глобальные объекты кластера, роли и внешние файлы, и не предоставляет восстановление до точки во времени. Проверка каталога дампа не заменяет восстановление через `pg_restore` в тестовую базу.

## Настройки и проверка готовности

В `BackupJob` добавлены необязательные поля `SqlServer` и `PostgreSql` (в API — `sqlServer` и `postgreSql`). Старые SQL-задания без этих полей читаются; перед выполнением нужно заполнить и сохранить параметры подключения. Некорректные заданные параметры отклоняются при сохранении.

Проверены команды и передача параметров на подменённых SQL-соединениях и процессах, ошибки проверки, отсутствие файлов, доставка, хранение N и сохранение настроек. В Windows CI настоящие SQL Server LocalDB и отдельный кластер PostgreSQL проходят создание копий и восстановление строк в другие базы; PostgreSQL также проверяет ZIP AES-256, два хранилища с разными лимитами и отчёт внешнего задания. Сценарии и ограничения описаны в [native-sql-tests.md](native-sql-tests.md). Перед эксплуатацией на целевых серверах нужно проверить: успешное копирование, отказ доступа, отмену, правильное сопоставление SQL-каталогов, совместимость утилит и пробное восстановление.

## Если подключение не получилось

В следующем пакете после alpha.25 для известных кодов MS SQL программа показывает причину и действие на русском при проверке источника и копировании. Те же подсказки используются внешним мониторингом.

- **Вход отклонён (18456, 18452, 18470):** проверьте выбранный способ входа. Для SQL-логина заново задайте данные и сохраните задание или источник. Для Windows-входа проверьте пользователя приложения или службы. Администратор должен подтвердить, что вход разрешён.
- **Пароль истёк или требуется смена (18487, 18488):** сначала измените его на сервере с администратором, затем сохраните новый в программе.
- **База недоступна (4060) или недостаточно прав (229):** администратор проверяет доступ. Подключение копирования использует master, мониторинг — msdb; права создания и проверки копии отличаются от чтения истории.
- **Сервер не отвечает:** проверьте имя экземпляра, порт, VPN и сеть; администратор проверяет службу MS SQL и межсетевой экран. Для тайм-аута проверьте также нагрузку и допустимое время выполнения задания.
- **Ошибка сертификата:** программа отличает известные коды недоверенной или неполной цепочки, несовпадения имени, срока действия и отзыва. Администратор исправляет сертификат или доверенную цепочку; имя подключения должно соответствовать сертификату. При ошибке срока сначала проверьте дату и время. Проверка TLS не отключается.

Для PostgreSQL ненулевой код psql сам по себе не определяет причину. Сверьте сервер, порт, имя базы, пользователя и способ входа; при необходимости сохраните пароль заново. Настройки TLS и сертификаты проверяет администратор. Проверка источника не создаёт дамп.

Если программа сообщает об отсутствии сохранённых данных MS SQL, откройте задание или источник мониторинга в программе владельца, задайте логин и пароль заново и сохраните настройки. Для передачи новой ссылки службе нужна именно операция сохранения.

Неизвестные коды сохраняют исходное объяснение. При обращении за помощью сообщите видимый код и сохраните диагностику через «Настройки → Помощь». Диагностические журналы содержат типы и коды ошибок без текста драйвера, паролей и строк подключения. Подсказки проверены кодовыми сценариями; они не заменяют отдельный стенд MS SQL со смешанным режимом и реальными сертификатами.
