# Копирование баз SQL из приложения

Задания SQL Server и PostgreSQL используют общие ручной запуск, планировщик, ZIP, доставку, историю и хранение последних N копий. Они исполняются в автономном приложении, пока оно открыто. Доступны локальный и сетевой каталоги, FTP/FTPS с логином и паролем в диспетчере учётных данных Windows. Мониторинг внешних SQL-копий остаётся отдельной функцией и не заменяет эти задания.

## Microsoft SQL Server

Создайте задание `SqlServer`, укажите имя базы в поле источника и экземпляр сервера. Подключение использует Windows-аутентификацию пользователя приложения, шифрование с проверкой TLS-сертификата и начальный каталог `master`. SQL-аутентификация ещё не подключена. Учётной записи нужны права на резервное копирование выбранной базы и `RESTORE VERIFYONLY`.

Укажите два пути к одному каталогу:

- Каталог для `BACKUP` в файловой системе SQL Server, например `D:\SqlStage`.
- Путь к этому каталогу для чтения приложением, например `\\sql-server\SqlStage` либо `D:\SqlStage`, если приложение работает на том же компьютере.

Службе SQL Server нужны права записи в первый каталог, пользователю приложения — чтения через второй путь. Серверный каталог также может быть абсолютным путём Linux для соответствующего SQL Server. Каталог должен существовать на стороне SQL; приложение не создаёт его на удалённом сервере.

Исполнитель создаёт полный `.bak` с уникальным именем командой `BACKUP DATABASE ... WITH COPY_ONLY, CHECKSUM`, затем выполняет `RESTORE VERIFYONLY ... WITH CHECKSUM`. Сжатие SQL не запрашивается, чтобы не зависеть от редакции сервера. База и путь передаются SQL-параметрами. После проверки агент проверяет доступность непустого файла и передаёт его общему модулю доставки. Ограничение времени применяется ко всему созданию и проверке; отмена передаётся SQL-драйверу.

Если конечный каталог совпадает с каталогом чтения SQL-копии и ZIP выключен, файл регистрируется на месте без повторного копирования, и правила N действуют на зарегистрированные `.bak`. При переносе в другой каталог или упаковке исходный `.bak` сохраняется в SQL-каталоге; лимит N относится только к зарегистрированным копиям конечного хранилища. Для исходных SQL-файлов нужна отдельная политика обслуживания. Ошибка проверки, доступа или доставки не удаляет предыдущие успешные копии. При отмене на сервере может остаться частичный `.bak`, который не считается успешной копией.

Рабочий файл `sql-source.json` сохраняет серверный и доступный агенту пути для диагностики; при успешной операции рабочий каталог удаляется. `RESTORE VERIFYONLY` проверяет набор резервной копии, но не заменяет пробное восстановление в отдельную тестовую базу.

## PostgreSQL

Создайте задание `PostgreSql`, укажите имя базы, сервер, порт, пользователя и полные пути к `pg_dump` и `pg_restore`. Создаётся дамп одной базы в формате custom, затем проверяется через `pg_restore --list`. Утилиты должны поддерживать версию сервера; рекомендуется использовать инструменты той же основной версии. Непустой дамп и нулевые коды обоих процессов обязательны до доставки и очистки.

Пароль не передаётся в аргументах и не хранится в JSON. Утилита запускается с `--no-password`: вместо запроса пароля она использует стандартный файл libpq, например `%APPDATA%\postgresql\pgpass.conf` на Windows, либо путь из `PGPASSFILE`. Файл настраивается для пользователя, под которым открыто приложение. Подключение также использует стандартные переменные libpq, включая настройку TLS через `PGSSLMODE` и сертификаты. При будущей смене пользователя на службу потребуется настроить её окружение и доступ к файлу паролей отдельно.

Ограничение времени действует на `pg_dump` и последующую проверку вместе. Отмена останавливает дерево процессов, а рабочие файлы сохраняются при ошибке. Дамп не включает глобальные объекты кластера, роли и внешние файлы, и не предоставляет восстановление до точки во времени. Проверка каталога дампа не заменяет восстановление через `pg_restore` в тестовую базу.

## Настройки и проверка готовности

В `BackupJob` добавлены необязательные поля `SqlServer` и `PostgreSql` (в API — `sqlServer` и `postgreSql`). Старые SQL-задания без этих полей читаются; перед выполнением нужно заполнить и сохранить параметры подключения. Некорректные заданные параметры отклоняются при сохранении.

Проверены команды и передача параметров на подменённых SQL-соединениях и процессах, ошибки проверки, отсутствие файлов, доставка, хранение N и сохранение настроек. Реальные SQL Server/PostgreSQL здесь не запускались. Перед эксплуатацией нужно проверить на отдельных тестовых базах: успешное копирование, отказ доступа, отмену, правильное сопоставление SQL-каталогов, совместимость утилит и пробное восстановление.
