# План надёжности и восстановления SP Backup

19 ноября 2026 года. Проверен код ветки `feature/local-backup-agent` на коммитах от `4830419` до `618d6b8`. Первым в очередь поставлен риск потери последней пригодной к восстановлению точки. В таблицах перечислены **запланированные** изменения и условия их приёмки. Результаты опытов с текущим кодом приведены отдельно.

Работы идут четырьмя пакетами. Сначала проверяем сохранность копий, затем согласуем результаты службы и Dashboard. После этого проверяем восстановление при потере доступа, затем длительную работу агента и панели. Для изменённого продукта сначала выполняется приёмка на Windows, затем на Linux для общего кода. [Основания и опыты 13–15](system-reliability-review.md)

## Состояние реализации в ветке

- Проверены сохранение предшествующей точки при пропавшей основе инкремента, частичный итог при сбое проверки одного назначения и ошибка при сбое обоих. Копии прежней папки сохраняются при смене источника. Пока текущая папка пуста, сохраняется одна предыдущая непустая точка. В разделе «Резервные копии» можно подтвердить обычную очистку выбранного назначения. Старое подтверждение отклоняется, основа используемой цепочки сохраняется.
- Агент сохраняет локальную квитанцию доставки перед записью в каталог. После прерывания он сверяет найденные квитанции с заданием и хранилищем, проверяет SHA-256 и регистрирует подтверждённый архив один раз. До завершённой квитанции имя ожидаемого архива служит подсказкой для ручной сверки. История сохраняет статус «Прервано» и результат по назначениям.
- Очистка и проверка последних файловых копий учитывают порядок создания цепочек. Отчёт отмечает успешно проверенное отставшее назначение. В панели карточка использует область текущего задания, а история Dashboard отбирает копии агента до ограничения результатов. Квитанция удалённой команды показывает ожидание отчёта и затем открывает точный запуск.
- Диагностика выбирает до 1 000 последних записей потоковым чтением. Проверен профиль с 10 950 записями. Предел входного файла составляет 64 МиБ. При достижении предела ZIP показывает отдельный статус.
- Результат копирования передаётся и после перевода часов назад. История показывает время по часам агента и длительность по таймеру. На исходнике `276cccc` файловое задание доставило копию в два назначения при переводе часов на час назад. После отклонения первого обращения отчёт дошёл, а повторная отправка сохранила одну запись с обоими назначениями. В Windows прошли 182 серверных теста с тремя штатными пропусками, в изолированном PostgreSQL на Linux прошли все 185 тестов. [Прогон Windows](https://github.com/sanekman/1C-Backup/actions/runs/44459696046).
- Dashboard и карточка агента показывают отдельно готовые к отправке, отклонённые сервером и неподготовленные отчёты. Причина отказа сохраняется при перезапуске агента. Очередь старых агентов выводится по их общему счётчику. На исходнике `cc4aa7a` проверены конфликт отчёта, доставка остальных записей и чтение прежних квитанций. На Windows прошли 183 серверных теста с тремя штатными пропусками, на Linux прошли все 186. В Chromium проверены счётчики, причины отказа и узкая карточка агента. [Прогон Windows](https://github.com/sanekman/1C-Backup/actions/runs/44695153457).
- Агент сохраняет ближайший плановый запуск и после перезапуска показывает в Windows последний пропуск. Для локального задания можно включить одну попытку с опозданием от 1 до 1440 минут. На исходнике `3d430c3` прошли WPF-сценарий мастера и проверки службы Windows Server 2022. На Linux прошли 58 тестов расписания и диспетчера. Тесты моделируют перерыв и повторный старт планировщика, а также смену пояса и отключённое задание. Приёмка остановки установленной службы на шесть минут остаётся отдельным сценарием. [Прогон Windows](https://github.com/sanekman/1C-Backup/actions/runs/44699207775).
- Dashboard каждые 15 секунд обновляет связь, этап и последний результат в существующих строках. Если в другой сессии изменился состав дерева, панель предлагает нажать «Обновить». Dashboard и карточка агента показывают время, когда сервер впервые получил текущий прогресс. Повторная отправка того же прогресса сохраняет время, а итог закрывает прогресс по ID запуска. На исходнике `2ea9849` в Windows прошли 184 серверных теста с тремя штатными пропусками и тест собранного пакета. На Linux с PostgreSQL 17 прошли все 187 серверных тестов. В Chromium с тестовыми отчётами проверены обновление этапа и доставки на месте, сохранение фильтра, фокуса и подтверждения переноса. Проверка с отключением связи во время реального копирования остаётся открытой. [Прогон Windows](https://github.com/sanekman/1C-Backup/actions/runs/44730943762).
- В строке Dashboard видны расхождение ревизий, отсутствие подтверждения, готовность исполнителя и недостающий доступ. Сводка и карточка агента показывают сохранённую ревизию, принятую по квитанции и сообщённую агентом. У сведений о доступе есть собственные время и ревизия, поэтому свежая связь не скрывает устаревший отчёт. На исходнике `c56afe5` на Windows прошли 185 серверных тестов с тремя штатными пропусками и проверка собранного пакета. На Linux с PostgreSQL 17 прошли все 188 серверных тестов. В Chromium при 900×580 в обеих темах проверены переход из строки в сводку, смена ревизии и обновление готовности на месте. Готовность и доступ проверены по тестовым сигналам агента. [Прогон Windows](https://github.com/sanekman/1C-Backup/actions/runs/44732897851).
- Приёмка на установленном Windows-агенте и проверка эксплуатации на целевых хранилищах остаются открытыми. Остальные задачи приведены ниже.

На медленном соединении прервать проверку основы по тайм-ауту. Прежняя точка сохраняется, оператор видит причину и может повторить проверку.

## Что воспроизведено

Опыты 1–4 выполнены на `4830419`, опыты 5–7 на `51a8a2e`, опыт 8 на `8e2f512`, опыт 9 на `29da1d5`, опыт 10 на `e6de16c`, опыт 11 на `c22ed26`, опыт 12 на `618d6b8`. Использованы .NET 10.0.13 и временные локальные каталоги на Linux. Для выпуска запланирована проверка исправленных сценариев на Windows. Работа настоящей службы Windows, внешнего NAS и установленного EXE в этих опытах не проверялась.

1. **Исчезла полная основа.** Одно файловое задание с `KeepLast=2` и `FullBackupEvery=2`. Первую полную копию восстановили и сверили файл. После инкремента и второй полной копии её архив переместили из хранилища, оставив запись в каталоге. Следующий инкремент получил `Succeeded` с нулём предупреждений, очистка удалила первую полную копию. Штатная проверка вернула `Failed`, восстановление завершилось `FileNotFoundException`.
2. **Ошибка проверки новых архивов в двух назначениях.** Обе локальные записи выполнило штатное файловое хранилище. После регистрации записи тест добавлял байты в выбранный архив непосредственно перед его проверкой в `BackupRetention.ApplyAsync`. Проверили два варианта.
   - Изменён архив только во втором назначении. История показала `Succeeded` с одним предупреждением, отчёт агента отметил оба назначения как успешные. Проверка последних копий вернула `Verified` и `Failed`. Из первого назначения файл восстановился и совпал с исходным, из второго восстановление завершилось ошибкой.
   - Изменены оба архива. История показала `Succeeded` с двумя предупреждениями, в отчёте снова два успеха. Обе попытки восстановить файл завершились `InvalidDataException`. В обоих вариантах рабочая папка запуска была удалена. Проверялось формирование отчёта агентом, отправка и отрисовка в панели требуют отдельной приёмки.
3. **Процесс остановился между доставкой и регистрацией.** Дочерний процесс завершили после возврата из штатного `FileBackupStorage.StoreAsync`, до возврата управления для записи в каталог. Во втором процессе вызвали штатное восстановление истории. Итог — `Interrupted`, в хранилище один архив, в каталоге ноль записей. Один факт наличия файла не позволяет безопасно включить его в автоматическую очистку.
4. **Пропущено ежедневное расписание.** При задании на 02:00 UTC планировщик, уже работавший в 01:59, при следующем опросе в 02:06 выполнил один запуск. Новый экземпляр с первым опросом в 02:06 выполнил ноль, а в 02:00 следующего дня — один. Использовалось заданное тестом время. Для режима «При загрузке системы» действует отдельный механизм учёта.

5. **После перевода часов проверена прежняя версия.** В двух локальных назначениях создали полную копию в 12:00 UTC и инкремент в 11:00 UTC по тестовым часам. Из A убрали новый инкремент, из B убрали старую основу. Проверка последних копий выбрала полную копию в обоих назначениях. Для A она вернула `Verified`, хотя восстановление выбранного инкремента завершилось ошибкой. Для B вернула `Failed` по отсутствующей основе.
6. **Части одной цепочки сохранились в разных назначениях.** В условиях опыта 5 восстановление инкремента по отдельности из A и B вернуло `FileNotFoundException`. В тестовом каталоге сверили идентификатор снимка и зарегистрированный SHA-256 основы, скопировали сохранившуюся основу из A на её прежнее место в B. Штатное восстановление из B вернуло точное содержимое новой версии. Это проверка возможности собрать цепочку, ручное копирование использовалось только в опыте.
7. **Выбор версии и отмена перед публикацией.** До удаления архивов в опыте 5 восстановили новый текст `BBB` вместо `AAA` при одинаковой длине файла и одинаковом времени изменения. В отдельной попытке отменили операцию на этапе `Publishing`. Ядро вернуло отмену, выбранная пустая папка осталась пустой.

8. **Смена исходной папки в локальном задании.** Скопировали папку с файлом `file.txt` и содержимым `AAA` в два назначения. Затем указали другую папку с одноимённым файлом `BBB`, сохранив ID задания и оба назначения. До первого запуска с новой папкой проверка последних копий вернула два результата `Verified` для старых записей. Восстановление первой из них дало `AAA`. После запуска агент создал полную копию, проверка выбрала новую точку, восстановление дало `BBB`. Прежняя точка по-прежнему восстановила `AAA`.

9. **После перевода часов очистка удалила непосредственно предшествующую версию.** В двух отдельных временных каталогах выполнили по четыре полные копии одного файла с последовательным содержимым A, B, C и D. Лимит — две копии. При отметках 12:00, 12:01, 12:02 и 12:03 после C восстановились B и C, после D — C и D. При отметках 12:00, 11:00, 11:01 и 11:02 после C восстановились A и C, после D — A и D. После каждого запуска восстановили содержимое каждой зарегистрированной точки и сверили наличие всех созданных архивов с каталогом. Удалённые из каталога архивы отсутствовали и на диске. Все восемь запусков завершились успешно без предупреждений.

10. **Смена источника на пустую папку при лимите в одну копию.** Исходный файл скопировали в два локальных назначения и восстановили из каждого. В том же задании заменили исходную папку на другую существующую пустую папку. Первый запуск завершился успешно без предупреждений. В обоих назначениях прежние архивы исчезли с диска и из каталога. Каждая новая точка восстановила ноль файлов. В контрольном опыте новой папке выделили отдельный ID задания при тех же назначениях и лимитах. Оба прежних архива остались на диске и в каталоге после копирования пустой папки и после следующего запуска с добавленным файлом. Лимит применяется к сочетанию задания и назначения.

11. **Прежняя папка стала пустой, параметры задания не менялись.** Проверили полное и инкрементное копирование, в каждом опыте два назначения с лимитом в одну точку. После первого запуска переместили единственный файл за пределы исходной папки. После каждого запуска восстановили все точки из каталога и проверили наличие исходных архивов на диске. В полном режиме первый пустой снимок вытеснил обе копии с файлом без предупреждений. В инкрементном режиме из первой пустой точки восстановилось ноль файлов, а прежний файл ещё восстанавливался по полной основе. Агент предупредил о сохранении основы сверх лимита. Очередная полная копия на третьем запуске удалила обе прежние цепочки без предупреждений. В обоих режимах остались две пустые копии, по одной в каждом назначении.

12. **Одно назначение пропустило версию.** Создали v1 в двух временных локальных каталогах A и B с лимитом 20. На время записи v2 по пути B разместили обычный файл, затем вернули исходный каталог. Запуск v2 получил `PartiallySucceeded`. После возврата B проверка последних копий выдала два результата `Verified`, при восстановлении из A получили v2, из B — v1. Проверили два продолжения в отдельных каталогах. При следующем инкременте агент доставил пропущенную v2, и из каждого назначения восстановились v1, v2 и v3. Если по расписанию наступала полная копия, из A восстановились все три версии, из B — v1 и v3. В обоих случаях проверка последних копий подтвердила v3 в обоих местах. Проверены записи каталога и содержимое файлов при восстановлении.

Для проверки исправлений пакета 1 сначала пройти сценарии на Windows с одним и двумя назначениями, сверить отчёт в панели и восстановить файл из сохраняемой точки. Затем проверить затронутое общее ядро на Linux. Приёмка CT 107 и ранее подтверждённое пользователем восстановление с NAS зафиксированы в [отчёте этапа 7.5](windows-stage75-beta-readiness.md).
