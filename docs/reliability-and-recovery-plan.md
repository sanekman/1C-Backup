# План надёжности и восстановления SP Backup

19 ноября 2026 года. Проверен код ветки `feature/local-backup-agent` на коммитах `4830419`, `51a8a2e` и `8e2f512`. Первым в очередь поставлен риск потери последней пригодной к восстановлению точки. В таблицах перечислены **запланированные** изменения и условия их приёмки. Результаты опытов с текущим кодом приведены отдельно.

## Что воспроизведено

Опыты 1–4 выполнены на `4830419`, опыты 5–7 на `51a8a2e`, опыт 8 на `8e2f512`. Использованы .NET 10.0.13 и временные локальные каталоги на Linux. Для выпуска запланирована проверка исправленных сценариев на Windows. Работа настоящей службы Windows, внешнего NAS и установленного EXE в этих опытах не проверялась.

1. **Исчезла полная основа.** Одно файловое задание с `KeepLast=2` и `FullBackupEvery=2`. Первую полную копию восстановили и сверили файл. После инкремента и второй полной копии её архив переместили из хранилища, оставив запись в каталоге. Следующий инкремент получил `Succeeded` с нулём предупреждений, очистка удалила первую полную копию. Штатная проверка вернула `Failed`, восстановление завершилось `FileNotFoundException`.
2. **Ошибка проверки новых архивов в двух назначениях.** Обе локальные записи выполнило штатное файловое хранилище. После регистрации записи тест добавлял байты в выбранный архив непосредственно перед его проверкой в `BackupRetention.ApplyAsync`. Проверили два варианта.
   - Изменён архив только во втором назначении. История показала `Succeeded` с одним предупреждением, отчёт агента отметил оба назначения как успешные. Проверка последних копий вернула `Verified` и `Failed`. Из первого назначения файл восстановился и совпал с исходным, из второго восстановление завершилось ошибкой.
   - Изменены оба архива. История показала `Succeeded` с двумя предупреждениями, в отчёте снова два успеха. Обе попытки восстановить файл завершились `InvalidDataException`. В обоих вариантах рабочая папка запуска была удалена. Проверялось формирование отчёта агентом, отправка и отрисовка в панели требуют отдельной приёмки.
3. **Процесс остановился между доставкой и регистрацией.** Дочерний процесс завершили после возврата из штатного `FileBackupStorage.StoreAsync`, до возврата управления для записи в каталог. Во втором процессе вызвали штатное восстановление истории. Итог — `Interrupted`, в хранилище один архив, в каталоге ноль записей. Один факт наличия файла не позволяет безопасно включить его в автоматическую очистку.
4. **Пропущено ежедневное расписание.** При задании на 02:00 UTC планировщик, уже работавший в 01:59, при следующем опросе в 02:06 выполнил один запуск. Новый экземпляр с первым опросом в 02:06 выполнил ноль, а в 02:00 следующего дня — один. Использовалось заданное тестом время. Для режима «При загрузке системы» действует отдельный механизм учёта.

5. **После перевода часов проверена прежняя версия.** В двух локальных назначениях создали полную копию в 12:00 UTC и инкремент в 11:00 UTC по тестовым часам. Из A убрали новый инкремент, из B убрали старую основу. Проверка последних копий выбрала полную копию в обоих назначениях. Для A она вернула `Verified`, хотя восстановление выбранного инкремента завершилось ошибкой. Для B вернула `Failed` по отсутствующей основе.
6. **Части одной цепочки сохранились в разных назначениях.** В условиях опыта 5 восстановление инкремента по отдельности из A и B вернуло `FileNotFoundException`. В тестовом каталоге сверили идентификатор снимка и зарегистрированный SHA-256 основы, скопировали сохранившуюся основу из A на её прежнее место в B. Штатное восстановление из B вернуло точное содержимое новой версии. Это проверка возможности собрать цепочку, ручное копирование использовалось только в опыте.
7. **Выбор версии и отмена перед публикацией.** До удаления архивов в опыте 5 восстановили новый текст `BBB` вместо `AAA` при одинаковой длине файла и одинаковом времени изменения. В отдельной попытке отменили операцию на этапе `Publishing`. Ядро вернуло отмену, выбранная пустая папка осталась пустой.

8. **Смена исходной папки в локальном задании.** Скопировали папку с файлом `file.txt` и содержимым `AAA` в два назначения. Затем указали другую папку с одноимённым файлом `BBB`, сохранив ID задания и оба назначения. До первого запуска с новой папкой проверка последних копий вернула два результата `Verified` для старых записей. Восстановление первой из них дало `AAA`. После запуска агент создал полную копию, проверка выбрала новую точку, восстановление дало `BBB`. Прежняя точка по-прежнему восстановила `AAA`.

Для проверки исправлений пакета 1 сначала пройти сценарии на Windows с одним и двумя назначениями, сверить отчёт в панели и восстановить файл из сохраняемой точки. Затем проверить затронутое общее ядро на Linux. Приёмка CT 107 и ранее подтверждённое пользователем восстановление с NAS зафиксированы в [отчёте этапа 7.5](windows-stage75-beta-readiness.md).
