# Подтверждения серверной конфигурации

Следующий пакет после **alpha.28**. Это подтверждение проверки и сохранения настроек библиотекой агента, а не подтверждение работы исполнителя или создания копии. Настоящий `LocalAgentHost` пока поддерживает только Standalone и не объявляет `managed-execution-v1`. Подключение Managed к службе и веб-мастер остаются следующими этапами.

## Выдача предложения

Клиент объявляет `configuration-receipts-v1` в `SP-Backup-Capabilities`. После проверки всех остальных необходимых возможностей `GET /api/v1/agents/{id}/configuration` выдаёт заголовки:

```text
ETag: "2"
SP-Backup-Configuration-Offer: b7ed4b31-9fb6-43c9-a468-a9e6d3de1f12
```

Идентификатор предложения сохраняется на сервере и привязан к агенту, ревизии, содержимому документа и текущему подключению. Повторные `200`/`304` используют тот же идентификатор; записи не множатся при каждом опросе. Изменение документа без изменения ревизии отклоняется. Между чтением и выдачей сервер повторно проверяет ревизию и подключение. При изменении нужен повторный запрос, а не подтверждение прежних данных.

Старый клиент без новой возможности получает прежний ответ без предложения и продолжает передавать мониторинг. Новая библиотека работает и со старым сервером без заголовка; она не придумывает идентификатор и не отправляет неподтверждённые заявления. Проверка поддержки непустых заданий действует до выдачи предложения и до `304`.

## Ответ агента

`POST /api/v1/agents/{id}/configuration-receipt` с bearer-токеном агента и `Content-Type: application/json`:

```json
{
  "agentId": "1f564dde-0f9a-455d-bb21-f88e9ef6f18d",
  "revision": 2,
  "offerId": "b7ed4b31-9fb6-43c9-a468-a9e6d3de1f12",
  "status": "Accepted",
  "reason": null,
  "observedUtc": "2026-10-29T00:00:00Z"
}
```

| Поле | Значение |
| --- | --- |
| `agentId` | Совпадает с адресом и аутентифицированным агентом. |
| `revision`, `offerId` | Именно выданное предложение, а не номер прежнего кэша. |
| `status` | `Accepted` либо `Rejected`. |
| `reason` | Для принятия — `null`. Для отказа — только `InvalidConfiguration` либо `CacheWriteFailed`. |
| `observedUtc` | Время проверки агента с UTC-смещением 0; сервер не использует часы агента для упорядочивания принятия. |

Пути, задания, текст исключений, пароли и произвольные причины в подтверждение не включаются. Неизвестные поля, дубли JSON, неверные статусы/причины и некорректная привязка отклоняются.

Успех возвращает `204`. Неизвестное или чужое предложение — `404`, предложение прежнего подключения — `410`, несовпадение ревизии — `409`, неверный набор — `400`. Отозванный токен не проходит аутентификацию. Предложение не является дополнительным правом доступа.

Первый отказ сохраняется до последующего принятия. Повтор отказа не меняет время и аудит; после устранения причины отказ может перейти в принятие. Принятие не отменяется запоздавшим отказом — сервер возвращает `204`, сохраняя принятый результат. Повтор принятия также не меняет время и аудит. Обновление результата и запись аудита выполняются одной транзакцией; ошибка аудита откатывает результат.

Ответы на ранее выданные ревизии допустимы после публикации новой, но последняя принятая ревизия выбирается по максимальному номеру, а не по времени прибытия. Ответы старой ревизии не перезаписывают состояние новой. После отзыва доступа и повторного подключения прежние результаты не выдаются за результаты нового подключения.

## Кэш и повторная передача

Принятие создаётся после проверки всего набора и атомарной записи кэша. При отказе сохраняется прежний кэш, если он существовал. Ошибка разбора привязывается к предложению и ETag ответа; отсутствие достоверной привязки или обычная ошибка сети не создают отказ для номера прежнего кэша.

Кэш сохраняет идентификатор предложения и контрольную сумму типизированной конфигурации. Это проверка целостности локальных данных, не свидетельство выполнения копирования. Повреждённый кэш не подтверждается через `304`. Прежний кэш без привязки либо кэш предыдущего подключения сначала обновляется полным ответом; одинаковые настройки с вложенными списками сравниваются по значениям, а не ссылкам объектов.

Рядом с файлом кэша находится отдельная очередь `<cache>.receipts`. В ней нет заданий и секретов: только адрес привязки и подтверждение. Она ограничена 64 файлами по 8 КиБ при чтении; за один опрос отправляются до 4 ответов, сетевой бюджет отправки — 5 секунд. Недоступный канал подтверждений помечается `AgentSyncResult.ReceiptPending`; успешное сохранение настроек при этом остаётся успешным. После перезапуска очередь повторяется идемпотентно. Повреждённый элемент не мешает передаче остальных; элементы другого сервера/агента не отправляются текущему. В Standalone этот обмен не выполняется.

Если запись очереди не удалась после записи кэша, следующая синхронизация может восстановить подтверждение из корректно привязанного `304`. Очередь удаляет доставленный элемент только после ответа сервера. Потерянный ответ после серверного коммита приводит к безопасному повтору. Неподдерживаемое предложение прежнего подключения удаляется по `404`/`410`; актуальное подтверждение восстанавливается последующим предложением.

## Что видно администратору

`GET /api/v1/management/agents/{id}/configuration-state` доступен только административному cookie-сеансу. Он возвращает желаемую ревизию, состояние её предложения и последнюю принятую ревизию текущего подключения. Состояние читается одним согласованным запросом; текущий результат соответствует также хешу желаемого документа. В карточке агента показаны ожидание, проверка/сохранение или фиксированная причина отказа. В журнале действий есть принятие и отказ без содержимого заданий.

Публикация и legacy-heartbeat сами по себе не создают принятие. `reported_revision` остаётся отдельной декларацией heartbeat. Серверное время получения ответа отличается от времени наблюдения на агенте. Подтверждение не означает, что расписание запущено; результаты копирования показаны отдельно.

## Схема БД 3

Добавлена таблица `server_configuration_offers`; существующие данные агентов, желаемых конфигураций, мониторинга и истории не преобразуются. Миграция выполняется общей транзакцией с существующим advisory-lock. Повторный запуск безопасен; ошибка после создания новой таблицы откатывает и таблицу, и номер версии.

Перед установкой будущего серверного выпуска со схемой 3 остановите сервер и сохраните проверенную копию PostgreSQL, настроек и сертификатов. Прежнее приложение со схемой 2 не следует запускать поверх успешно обновлённой БД: для возврата нужна соответствующая копия БД. Этот пакет пока не опубликован и не обновляет рабочую установленную систему автоматически.
