# План первой версии 1C-Backup

Агент Windows для резервного копирования файловых баз 1С, MS SQL и PostgreSQL. Работает автономно или подключается к серверу управления через API. Effector Saver служит ориентиром по рабочему процессу: задания, расписания, история выполнения и контроль результата.

Сейчас приоритет — закончить Windows-агент и Windows-сервер. Развитие Linux переносится на следующий этап; уже опубликованные пакеты сохраняются. Рабочий порядок и критерии готовности: [Windows: оставшиеся работы](windows-readiness.md).

## Рабочий процесс

1. Администратор создаёт задание: тип базы, источник, способ резервного копирования, место хранения и расписание.
2. Программа проверяет настройки. Кнопка «Проверить хранилища» проверяет временную папку и запись, чтение и удаление тестового файла в каждом назначении, без создания копии базы или очистки её копий. «Проверить источник» проверяет файл 1С или SQL-подключение без создания копии. Для PostgreSQL нужен `psql` рядом с `pg_dump`. Выгрузка / дамп, доступ к данным таблиц, права SQL-службы на папку и восстановление проверяются первым копированием и тестовым восстановлением.
3. Задание запускается вручную или по расписанию; повторный запуск того же задания исключается.
4. Программа создаёт резервную копию и проверяет результат выбранным способом.
   При включённой архивации готовая копия упаковывается в ZIP с проверкой содержимого. Ошибка упаковки означает ошибку задания; очистка прежних копий не запускается. Исходный файл сохраняется.
5. Только после успешной проверки применяет правила хранения ранее созданных копий этого задания.
6. История сохраняет время начала, длительность, результат, путь к копии и понятную причину ошибки. Пароли и другие секреты не попадают в журнал.

## Файловые базы 1С

Предусмотреть два явных режима:

- Выгрузка `.dt` через установленную платформу 1С в режиме Конфигуратора. Требует исполняемый файл платформы, доступ к базе и возможность эксклюзивного подключения. Неудачная выгрузка не считается успешной копией.
- Архив файла `1Cv8.1CD` без платформы при закрытых сеансах: эксклюзивный дескриптор `FileShare.None` удерживается во время упаковки и проверки ZIP. Отказ в доступе означает ошибку задания. Этот способ подключён к ручному запуску; поведение блокировки с реальными сеансами и на UNC предстоит проверить на Windows. Обычное копирование открытой базы не обеспечивает согласованность данных.

Программа не завершает пользовательские сеансы принудительно по умолчанию. Если эксклюзивный доступ получить нельзя, задание завершается ошибкой или переносится согласно явно заданной политике. Снятие блокировок, установленных заданием, выполняется также при ошибке.

## MS SQL

Отдельно от собственных заданий добавлен мониторинг завершённых внешних копий по `msdb`, с локальной историей и очередью отчётов. Подробности обоих SQL-источников — в [external-backup-monitoring.md](external-backup-monitoring.md). Наблюдения не дают агенту права удалять внешние копии.

- Использовать штатную команду `BACKUP DATABASE`, а не копирование файлов MDF/LDF.
- Для независимой полной копии по умолчанию использовать `COPY_ONLY`, чтобы не менять базу дифференциальных резервных копий существующего обслуживания.
- Использовать `CHECKSUM` и проверку `RESTORE VERIFYONLY`. Проверка не заменяет пробное восстановление.
- Путь в команде SQL относится к файловой системе SQL Server. Учётной записи службы SQL Server нужны права записи в этот каталог. Это отличается от прав программы на конечное хранилище.
- Если копия переносится в другое хранилище, успех задания требует завершения переноса и проверки итогового файла. Исходная копия не удаляется до подтверждения переноса.
- Сжатие включать с учётом возможностей выбранной версии и редакции SQL Server.
- Поддержать Windows-аутентификацию и SQL-аутентификацию; способ безопасного хранения секретов определить после выбора платформы приложения.

## PostgreSQL

- Использовать `pg_dump --format=custom` для одной базы. Утилита должна быть совместима с версией сервера; старая утилита не используется для более нового сервера.
- Проверять код завершения и каталог архива через `pg_restore --list`. Для подтверждения возможности восстановления нужна отдельная тестовая база.
- Пользователи и другие глобальные объекты кластера не входят в дамп одной базы; их резервное копирование через `pg_dumpall --globals-only` рассматривается отдельно.
- Пароль не передавать в аргументах командной строки. Определить безопасный механизм передачи учётных данных при реализации исполнителя.

## Первая версия

- Создание, изменение, отключение и удаление заданий.
- Ручной запуск, ежедневное расписание и выбранные дни недели с явно выбранным часовым поясом; до 48 времён в день.
- Локальный диск, сетевой каталог (UNC) и FTP/FTPS; до 8 назначений на задание с отдельным количеством копий в каждом. Проверка фактической записи и содержимого доставленной копии. Выбор временной папки для формирования выгрузки / ZIP и проверки FTP на другом диске.
- Сохранение последних N успешных копий. Очистка касается только копий, зарегистрированных программой для конкретного задания; минимум одна успешная копия сохраняется.
- История выполнения и журнал ошибок.
- Проверка резервной копии, соответствующая выбранному методу. Извлечение проверенного ZIP файла 1Cv8.1CD в новую папку без перезаписи существующих баз; локальное и сетевое хранилища.
- Дополнительная архивация в ZIP для каждого задания. Потоковая упаковка, проверка содержимого по SHA-256, отмена с удалением временного архива и запрет перезаписи существующих архивов. Старые задания по умолчанию не архивируются.
- Восстановление после перезапуска: незавершённые задания отмечаются как прерванные, временные файлы не считаются успешными копиями.

## Отложенные возможности

Яндекс Диск, Облако Mail.ru и S3 рассматриваются после основной версии как отдельные адаптеры общего контракта хранилища. Почтовые уведомления, дифференциальные копии, резервное копирование журнала транзакций, автоматическое восстановление, глобальные объекты PostgreSQL и расширенные расписания также отложены.

## Выбранная архитектура

Для серверной части подготовлена [начальная дорожная карта](server-roadmap.md): единый ASP.NET Core-сервер с веб-панелью, Windows-приложение / служба, Linux-контейнер и systemd; macOS — возможное последующее расширение. Основа первого этапа реализована; рабочее управляемое подключение агента и этапы alpha / beta ещё предстоит завершить. [Запуск сервера](server-start.md).

Windows-приложение на C#/.NET 10 с WPF-интерфейсом. Поддерживаются файловые базы 1С, MS SQL и PostgreSQL.

Агент является единственным локальным исполнителем и в автономном, и в серверном режиме. Сервер управления проектируется вместе с агентом; исходящий HTTPS API передаёт конфигурацию и состояние, а файлы резервных копий направляются непосредственно в хранилища. WPF-интерфейс будет работать с агентской службой через защищённый локальный IPC. Серверная недоступность не останавливает исполнение принятого расписания.

- `OneCBackup.Core`: режимы агента, HTTPS-клиент конфигурации/heartbeat, отдельный серверный кэш, независимые циклы связи/расписания, ZIP, хранилища, журнал успешных копий и очистка. Подключены реальные исполнители, история запусков и постоянная очередь наблюдений внешних копий. Служба Windows, очередь ручных команд и интеграционные проверки MS SQL LocalDB/PostgreSQL уже подключены; далее — закрытие пунктов Windows-готовности.
- `OneCBackup.Desktop`: создание и редактирование заданий, история запусков и раздел зарегистрированных копий с проверкой размера / SHA256 и открытием папки. Управление службой, разделённые настройки и локальное пошаговое руководство подключены.
- Служба Windows уже исполняет задания без окна и без входа пользователя, под выбранной учётной записью. Она использует профиль владельца, проверку SID, ACL, экспорт секретов DPAPI и общую очередь команд. Общий каталог ProgramData для всех пользователей не вводился; ограничения переноса и доступа описаны в [windows-service.md](windows-service.md).
- Адаптеры резервного копирования 1С, SQL Server и PostgreSQL реализованы; следующий этап — интеграционные проверки и пробное восстановление на тестовых базах.
- Сервер управления (следующий этап): веб-панель мониторинга агентов и истории копирования, удалённое создание и изменение заданий, регистрация агентов, назначение конфигураций с ревизиями, heartbeat, идемпотентные отчёты и команды. Панель различает сохранённую и принятую агентом ревизии; изменения для отключённого агента ожидают связи. Начальный контракт описан в [agent-api.md](agent-api.md), требования к панели и подтверждениям — в [server-management.md](server-management.md).

Сейчас реализованы редактор настроек, расчёт следующего запуска, диспетчер с таймером и завершение операции доставки с регистрацией успешной копии и очисткой. Подключены файловая 1С, `BACKUP DATABASE` / `RESTORE VERIFYONLY` для SQL Server и `pg_dump` / `pg_restore --list` для PostgreSQL, с ограничением времени, отменой, постоянной историей и сохранением рабочих файлов при ошибке. Планировщик исполняет задания всех типов в окне или отдельном автономном агенте текущего пользователя. Фоновый агент запускается и останавливается из интерфейса, продолжает работу после закрытия окна и может запускаться при входе в Windows. На Windows CI проверены реальные SQL Server LocalDB и PostgreSQL 17: создание, доставка и восстановление тестовых данных. Рабочая платформа 1С и удалённые производственные СУБД требуют отдельной проверки. Служба Windows реализована. Настройки не содержат паролей; MS SQL поддерживает Windows-аутентификацию и сохранённый SQL-логин, PostgreSQL — стандартный файл паролей. SQL-логин входит в следующий неопубликованный пакет после alpha.24. Подробности — в [sql-backups.md](sql-backups.md).

Режим `Standalone` использует локальные задания без обращений к API; `Managed` — отдельный кэш принятой конфигурации. Локальные задания сохраняются при переключении режимов, серверные доступны только для просмотра. Серверный кэш привязан к адресу сервера и ID агента. Некорректная или устаревшая конфигурация не заменяет принятую. API-клиент и агентские циклы реализованы в ядре. Сервер мониторинга с установкой на Windows и подключением автономных агентов реализован. Рабочее управляемое исполнение Managed и серверный редактор заданий пока не подключены. Служба автономного агента и локальные команды уже работают с профилем владельца; это отдельный механизм от будущего управления ревизиями с сервера.

Расписание поддерживает ручной, ежедневный и недельный режимы. Переход часов вперёд переносит запуск на первую допустимую минуту, повторение часа не даёт второй запуск. Диспетчер обрабатывает задания последовательно, пропущенные события не образуют очередь, а после перезапуска выбирается следующее событие. Состояние диспетчера находится в памяти; хост должен запускать только один его экземпляр и передавать реальные исполнители.

`BackupCompletion` выполняет доставку, регистрацию в `BackupCatalog` и очистку через `BackupRetention`. Сохраняются новая копия и N−1 последних прежних (минимум N=1). Перед удалением сверяются принадлежность, размер и SHA-256; отсутствие новой копии или повреждённый журнал блокируют очистку. Ошибки удаления возвращаются отдельно и не скрывают факт сохранения новой копии. Лимит распространяется на зарегистрированные копии в текущем конечном хранилище, без чужих файлов и исходных файлов отдельного рабочего каталога. Путь журнала и права на него должен задать будущий хост службы; используется один экземпляр журнала и координатора на процесс.

Модуль ZIP уже реализован, проверяет содержимое упакованного файла и подключён к ручной выгрузке файловой 1С; проверка ZIP не подтверждает возможность восстановления базы.

Раздел «Резервные копии» читает общий журнал `BackupCatalog` и обновляется после операций. Ручная проверка через `BackupCopyVerifier` сверяет принадлежность заданию, прежнюю идентичность хранилища и расположение до обращения к диску или FTP, затем проверяет размер и SHA256. Изменённое хранилище и удалённое задание не используются для проверки прежних копий. Проверка отменяема, не изменяет журнал или файлы и доступна при остановленном планировщике; интерфейс исключает одновременный запуск копирования. Записи журнала сами по себе не подтверждают текущее наличие файла. Для локального диска и UNC доступно открытие папки в Проводнике.

Для файловой 1С реализован выбор `OneCMethod`: `PlatformDump` (по умолчанию для старых заданий) или `FileArchive`. Второй способ не вызывает платформу и не требует её настроек, создаёт ZIP с единственным `1Cv8.1CD` под эксклюзивной блокировкой. Дополнительная упаковка такого ZIP исключена; история, доставка и хранение последних N копий используются общие.

`BackupDelivery` объединяет упаковку и доставку готового файла. Для FTP архивирование выполняется локально; удаляется только принадлежащий операции промежуточный архив. FTP проверяется полным обратным чтением, что требует дополнительного трафика и места на диске. Пароли не входят в модель задания; сохраняется только идентификатор учётных данных. FTP/FTPS подключён к интерфейсу и расписанию через `RoutedBackupStorage` и диспетчер учётных данных Windows. Перед созданием базы проверяется наличие учётных данных; доступ к серверу проверяется при доставке. Windows API проверяется в Windows CI. Привязка секретов к выбранной учётной записи службы реализована через защищённый экспорт DPAPI и ACL. Сетевой адаптер использует права процесса Windows, без автоматического подключения дисков и хранения SMB-паролей. Старые задания остаются локальными.

## Проверка готовности

- Файловая база: успешная копия тестовой базы; корректный отказ при занятой базе; отсутствие оставленной блокировки после ошибки.
- SQL Server: копирование отдельной тестовой базы, проверка копии и пробное восстановление в отдельную базу.
- Планировщик: запуск в назначенное время, исключение одновременных запусков одного задания, обработка перезапуска.
- Хранилище: ошибки доступа, нехватка места и прерванная запись не приводят к удалению успешных копий.
- FTP: передача файла и ZIP, проверка содержимого, отказ при неверных учётных данных, очистка временного файла при доступном соединении, отсутствие перехода на обычный FTP при требовании FTPS. Отдельно проверить успешную передачу по FTPS с доверенным сертификатом и UNC-доступ под учётной записью службы Windows.
- Очистка: удаление только зарегистрированных копий нужного задания и только после успешного завершения новой копии.

Сборка WPF в облачной среде выполняется с Windows targeting pack; настоящий интерфейс, Windows Vault/DPAPI, MS SQL LocalDB, PostgreSQL и установщик проверяются на Windows CI. Новая проверка службы использует отдельную временную учётную запись и SCM. Реальная платформа 1С и целевые Windows Server требуют отдельного стенда; рабочие базы для таких проверок не используются.

Хост `OneCBackup.Agent` работает как фоновый процесс текущего пользователя или как служба Windows под выбранной учётной записью. Окно и агент используют существующий профиль, историю и межпроцессный замок `engine.lock`; второй исполнитель не запускается. Поддерживаются ручная очередь при включённом расписании, работа без входа пользователя через службу, экспорт секретов для неё и проверка SID владельца при управлении. Состояние агента обновляется раз в секунду; запросы остановки и ручного запуска привязаны к сеансу. Установка и ограничения описаны в [windows-service.md](windows-service.md).

Добавлены задания обычных файлов и папок: полный ZIP или цепочка инкрементов, определяемых по SHA-256, периодические полные основы, защита зависимостей при очистке и восстановление в новую папку через текущие хранилища. Это не системный образ: VSS и метаданные NTFS не реализованы.


## Совместимость локального приложения с Windows Server

Начальный минимум — Windows Server 2016 x64 с Desktop Experience; далее 2019 / 2022 / 2025. Исправление порога ОС установщиков и статус нативных проверок описаны в [windows-compatibility.md](windows-compatibility.md). Поддержка 2008 R2 отложена: нынешний .NET 10-дистрибутив не совместим с этой ОС. Требования центрального сервера рассматриваются отдельно.


## Разработка альфа-версии и выпуски

Несколько связанных доработок и исправлений накапливаются в рабочей ветке и проверяются через CI. Новый тег и установщик для скачивания публикуются после подготовки пакета изменений; отдельная правка сама по себе не означает новый выпуск. Критические ошибки резервного копирования или обновления могут потребовать отдельного срочного выпуска. Существующие теги, дистрибутивы и файлы выпусков не заменяются.
