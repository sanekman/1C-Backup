# Мониторинг и управление агентами

Сервер предоставляет веб-панель для мониторинга агентов и изменения настроек резервного копирования. Агент исполняет задания на Windows и обращается к серверу по исходящему HTTPS API. Этот документ описывает планируемые возможности; сервер и перечисленные ниже новые API ещё не реализованы. Действующий контракт клиентского модуля описан в [agent-api.md](agent-api.md).

## Мониторинг

Также нужно отображать копии, созданные внешними средствами SQL Server и PostgreSQL. Агент уже имеет отдельные источники наблюдений и очередь отчётов; контракт описан в [external-backup-monitoring.md](external-backup-monitoring.md). Панель показывает происхождение и основание результата: история `msdb` либо отчёт скрипта PostgreSQL. Наличие записи в SQL-истории не отображается как подтверждённая проверка файла или восстановления.

В списке агентов показываются имя, ID, версия, время последней связи, доступность исполнения резервного копирования и состояние конфигурации. Онлайн-статус определяется по времени получения heartbeat сервером и настроенному порогу отсутствия связи. Время из часов агента не используется для определения доступности.

Карточка агента содержит задания, расписание с часовым поясом, следующий запуск, текущие операции и историю результатов. Для каждой операции сохраняются ID запуска, ID задания, ревизия использованных настроек, время начала и завершения, длительность, результат, размер и расположение копии, результат проверки и ошибки. Ошибки очистки старых копий отображаются отдельно от успешного сохранения новой копии. Пароли и токены в отчёты не включаются.

Связь с агентом и результат резервного копирования отображаются отдельно: доступный агент может иметь неудачные задания. Отсутствие отчёта не считается успехом. При потере связи последнее состояние и следующий запуск помечаются как устаревшие с временем получения данных; отображение последнего запуска как «выполняется» не означает, что он продолжает работать.

Агент передаёт фактический следующий запуск и используемую ревизию. Расчёт сервера по сохранённому расписанию может показываться как прогноз, пока агент не подтвердил настройки. Для ежедневных и недельных заданий панель показывает последнюю успешную копию и отсутствие ожидаемого результата после предусмотренного допуска; ручные и отключённые задания не считаются просроченными по расписанию.

## Изменение настроек

Администратор может создавать, редактировать, отключать и удалять задания конкретного агента. Управляемые параметры: тип и источник базы, ссылки на учётные данные, расписание и часовой пояс, ZIP-архивация, конечное хранилище и количество сохраняемых копий. Параметры подключения SQL Server и PostgreSQL входят в модель заданий; их текущие ограничения описаны в [sql-backups.md](sql-backups.md). Секреты не входят в обычную конфигурацию; ссылка на учётные данные должна быть разрешена на агенте.

Сервер хранит две отдельные величины:

- **Сохранённая ревизия** — набор настроек, который администратор назначил агенту.
- **Принятая ревизия** — последний набор, принятие которого подтвердил агент.

Сохранение изменений атомарно создаёт следующую ревизию полного набора заданий. Панель показывает «Ожидает применения», пока агент не подтвердит эту ревизию. Отключённый агент получает изменения при следующем подключении; сохранение на сервере не означает немедленного изменения на машине агента. После подтверждения показывается «Принято агентом» с временем подтверждения. Это подтверждает принятие настроек, а не успешное создание резервной копии.

При ошибке проверки агент сохраняет прежнюю принятую конфигурацию. Сервер должен получать отказ с номером предложенной ревизии и понятной причиной, а панель — показывать «Отклонено» и действующую ревизию. Такой отчёт об отказе предстоит добавить к API; текущий heartbeat сообщает только принятую ревизию. При отсутствии подтверждения причина остаётся неизвестной, и панель не предполагает отказ или успех.

Изменения применяются к новым запускам. Уже начатая операция завершается по неизменяемому снимку своих настроек; её отчёт содержит эту ревизию. Отключение или удаление задания запрещает последующие запуски после принятия конфигурации и не отменяет автоматически текущую операцию. История удалённых заданий сохраняется.

Параллельное редактирование защищается проверкой исходной ревизии: если другой администратор уже изменил настройки, сервер отклоняет сохранение до повторного чтения. Возврат к прежним значениям создаёт новую ревизию, а не уменьшает её номер. Доступ разделяется на просмотр мониторинга и управление настройками; журнал изменений сохраняет автора, время и изменённые поля без значений секретов.

## Работа без связи

В режиме `Managed` агент продолжает работать по последней принятой конфигурации. Изменения на недоступном сервере не влияют на локальные запуски, пока не получены и не приняты. Режим `Standalone` сохраняет независимые локальные задания и не требует сервера.

Отчёты о запусках предстоит хранить в постоянной очереди агента до подтверждения сервером. После восстановления связи они отправляются повторно при необходимости; уникальный `runId` исключает дублирование в истории. Сервер хранит время события на агенте и время получения отдельно. Поздно полученный отчёт не должен заменять состояние более нового запуска только из-за более позднего получения. Незавершённые операции после перезапуска получают итог «Прервано», а не «Успешно».

## Расширение API

Уже реализованный клиент использует `GET /api/v1/agents/{agentId}/configuration` и `POST /api/v1/agents/{agentId}/heartbeat`. Для сервера предлагаются следующие дополнительные маршруты; их контракт ещё предстоит реализовать:

| Маршрут | Назначение |
| --- | --- |
| `GET /api/v1/management/agents` | Список агентов, связь и состояние настроек. |
| `GET /api/v1/management/agents/{agentId}` | Сведения об агенте, сохранённая и принятая ревизии. |
| `GET /api/v1/management/agents/{agentId}/configuration` | Полная назначенная конфигурация с `ETag`. |
| `PUT /api/v1/management/agents/{agentId}/configuration` | Атомарное сохранение полного набора заданий с обязательным `If-Match`; новую ревизию назначает сервер. При конфликте — `412 Precondition Failed`. |
| `GET /api/v1/management/agents/{agentId}/runs` | История с фильтрами по заданию, результату и времени, с пагинацией. |
| `POST /api/v1/agents/{agentId}/runs` | Идемпотентная передача состояния и результата запуска. |
| `POST /api/v1/agents/{agentId}/configuration-results` | Подтверждение или отказ принятия конкретной ревизии. |

Для отчётов запуска нужны `runId`, порядок обновлений внутри запуска и итоговый статус: повторная отправка совпадающего события безопасна, устаревшее обновление не переводит завершённую операцию обратно в выполнение. Пустой набор заданий является явной конфигурацией с новой ревизией. Агентский токен привязан к одному агенту и не предоставляет доступ к административным маршрутам.

## Проверка готовности сервера

- Изменение задания офлайн-агента остаётся ожидающим; после связи применяется и подтверждается конкретная ревизия.
- Два администратора не перезаписывают изменения друг друга: сохранение с устаревшим `If-Match` получает конфликт.
- Некорректная конфигурация отклоняется целиком, прежние задания продолжают работать, причина отказа видна на сервере.
- Изменение или удаление задания во время выполнения не меняет параметры начатой операции; последующие запуски используют принятые настройки.
- При недоступности сервера агент продолжает расписание; после связи накопленные отчёты появляются один раз и в правильном порядке событий.
- Панель различает отсутствие связи, устаревший статус и ошибку копирования; новая ревизия не отображается как принятая без подтверждения.
- Автономные задания остаются независимыми от настроек сервера.
