# Публикация серверной конфигурации: начальный контракт

API опубликован в server preview.4; библиотечная поддержка — в alpha.29. В разработке после этих выпусков подключены [Managed-хост и включение в окне Windows](managed-execution.md), [веб-мастер](server-job-wizard.md), несколько локальных/UNC-хранилищ и история планов. Автономный клиент не объявляет managed-execution-v1 и не получает непустые серверные задания. [Протокол подтверждений](configuration-receipts.md) означает проверку и сохранение конфигурации, а не результат копии. Локальные автономные задания сохраняются отдельно.

## Что поддерживается

Контракт ограничен Windows-заданиями **Файлы и папки** и **Файловая 1С → ZIP файла базы**, с основным и до семи дополнительных локальных или UNC-хранилищ. Поддерживаются расписание, часовой пояс исполнителя (`Local`) или явный часовой пояс, полные/инкрементные файловые копии и день полной копии. Новое задание API по умолчанию выключено и имеет ручное расписание.

SQL, WebDAV, FTP, выгрузка `.dt`, шифрование архива и ссылки на локальные секреты в этот начальный контракт не входят. Их поля отклоняются, а не отбрасываются. Пароли, токены и DPAPI-данные сюда передавать нельзя. Конфигурация с неподдерживаемыми полями, уже находящаяся в БД, также не читается и не заменяется этим API: ответ `409 stored_configuration_not_editable` сохраняет прежний документ.

Пути проверяются как Windows-пути независимо от ОС сервера: абсолютный путь диска или UNC, без устройств, ADS, переходов `..`, неоднозначных конечных точек/пробелов. Источник, хранилище и временная папка не должны пересекаться. Сервер не проверяет существование файлов и права пользователя удалённой службы; это будущая проверка на агенте.

## Прочитать текущую ревизию

`GET /api/v1/management/agents/{id}/configuration`

Нужен административный cookie-сеанс. Ответ `200` содержит `agentId`, `revision`, `protocolVersion` и `jobs`. Заголовок `ETag`, например `"1"`, нужен для последующей записи. Ответ не кэшируется (`Cache-Control: no-store`). Неизвестный агент возвращает `404`.

## Сохранить следующую ревизию

`PUT /api/v1/management/agents/{id}/configuration`

Нужны административный cookie-сеанс, действующий `X-CSRF-TOKEN`, `Content-Type: application/json` и один сильный `If-Match` из последнего чтения. Значение `*`, слабые ETag, списки и число без кавычек не принимаются. Номер новой ревизии назначает сервер; поля `revision` в запросе нет.

```json
{
  "agentId": "b7ed4b31-9fb6-43c9-a468-a9e6d3de1f12",
  "protocolVersion": 1,
  "jobs": [
    {
      "id": "1f564dde-0f9a-455d-bb21-f88e9ef6f18d",
      "name": "Документы",
      "kind": "FilesAndFolders",
      "source": "C:\\Company\\Documents",
      "destinationDirectory": "D:\\Backups",
      "storageKind": "LocalDirectory",
      "enabled": false,
      "scheduleKind": "Manual"
    }
  ]
}
```

`agentId` должен совпадать с адресом запроса. ID заданий обязательны, уникальны в наборе и сохраняются при редактировании. Весь набор заменяется целиком; `jobs: []` задаёт пустую желаемую конфигурацию, не удаляя архивы и не подтверждая остановку исполнителя. Для UNC-хранилища нужен `storageKind: "NetworkShare"` и полный путь `\\server\share\folder`.

Варианты `kind`: `FilesAndFolders`, `OneCFile`; `oneCMethod` допускает только `FileArchive`. `scheduleKind`: `Manual`, `Daily`, `Weekly`, `SystemStartup`. Поля расписания: `dailyAt` (по умолчанию `23:00:00`), `additionalDailyTimes` (до 47 дополнительных уникальных времён), `daysOfWeek` (например `Monday, Friday`), `timeZoneId` (по умолчанию `UTC`). `None` разрешён только для ненедельного расписания. `keepLast`: 1–10 000, по умолчанию 7. Файловый план: `fileBackupMode` (`Full`/`Incremental`), `fullBackupEvery` (1–365, по умолчанию 7), `fullBackupDayOfWeek` (например `Sunday` либо `null`). `temporaryDirectory` необязателен. Для ZIP базы 1С доступен `allowOpenOneCDatabase`, по умолчанию `false`.

Ограничения: 1 МиБ для тела запроса и сохранённого документа, 256 заданий, 256 символов в имени, 4096 в пути. Неизвестные поля, дубли свойств JSON, числовые значения перечислений и неизвестная версия протокола отклоняют весь запрос. Ошибка не содержит имя задания, путь или исходный JSON.

Для крупных запросов используйте `Expect: 100-continue`: сервер сможет отклонить заведомо слишком большой `Content-Length` до отправки тела. При передаче превышающего лимит тела без этого согласования HTTP-соединение может закрыться; изменение конфигурации не происходит.

## Результаты и конфликты

| Статус | Значение |
| --- | --- |
| `200` | Желаемая ревизия сохранена; тело содержит назначенный номер, `ETag` обновлён. |
| `428` | Нет обязательного `If-Match`. |
| `400` | Некорректный ETag/JSON/набор, неподдерживаемые поля или неверный CSRF. |
| `412` | Другой редактор уже изменил ревизию. Прочитайте актуальную конфигурацию и сравните правки; не повторяйте запись вслепую. |
| `409` | Доступ агента отозван, прежняя конфигурация не поддерживается этим редактором либо номера ревизий исчерпаны. |
| `413` | Превышен размер, в том числе при передаче без `Content-Length`. |
| `415` | Не JSON. |
| `401` / `403` | Нет административного сеанса либо `agentId` не совпадает с адресом. Агентский bearer не даёт права публикации. |

При одновременной записи с одним ETag успешна только одна операция. Повтор той же операции со старым ETag получает `412`, не создавая вторую ревизию или запись аудита. Изменение документа, увеличение номера и событие `ConfigurationPublished` фиксируются одной транзакцией. Сбой аудита откатывает запись целиком. Смена сеансов администратора и отзыв доступа агента учитываются в этой транзакции. Сам API публикации использует исходные таблицы. Для журнала [подтверждений](configuration-receipts.md) следующему пакету нужна схема БД **3**; переход выполняется отдельной транзакционной миграцией.

**Сохранено на сервере** и **принято агентом** — разные состояния. Публикация не меняет сообщённую агентом ревизию и не доказывает выполнение копирования. Перед выдачей конфигурации сервер по-прежнему проверяет возможности клиента, включая условный запрос `304`. Старый клиент без поддержки исполнения продолжает отправлять мониторинг.

## Пользовательский интерфейс

На карточке агента откройте **Настроить задания на сервере**. Мастер использует те же типизированную проверку, атомарную публикацию и контроль ожидаемой ревизии, что API. До последнего подтверждения изменения остаются в форме; конфликт сохраняет введённые значения и требует сравнения со свежим планом. [Подробные шаги](server-job-wizard.md).

## Дополнительные локальные и сетевые хранилища

Поле задания `additionalDestinations` необязательно. Отсутствие, `null` или пустой массив сохраняют один основной путь; старые однопапочные документы не требуют миграции. Допускается не более семи дополнительных записей:

```json
"additionalDestinations": [
  {"storageKind": "NetworkShare", "destinationDirectory": "\\\\nas\\copies", "keepLast": 30},
  {"storageKind": "LocalDirectory", "destinationDirectory": "E:\\Copies"}
]
```

`keepLast` допускает `null` или отсутствие (наследовать основной `keepLast`) либо число от 1 до 10000. Разрешены только `LocalDirectory` с полным Windows-путём и `NetworkShare` с UNC. Неизвестные вложенные поля, секреты, пустые/относительные пути, устройства и несовпадение типа с путём отклоняют всю ревизию. Все папки назначения должны находиться отдельно друг от друга, от источника и рабочей папки; сравнение Windows-путей не зависит от регистра и ОС сервера.

Массив соответствует уже поддерживаемому `BackupJob.AdditionalDestinations` агента. Протокол и обязательные возможности `configuration-v1`, `strict-configuration-v1`, `managed-execution-v1` не меняются: существующий Managed-исполнитель уже умеет доставку и отдельную очистку. Старый сервер с начальным узким DTO не должен редактировать такие планы: неподдерживаемый формат отклоняется целиком.

Для одного запуска создаётся один архив, затем выполняется отдельная доставка и очистка каждого хранилища. Результаты доставки независимы; ошибка одной папки не отменяет успешные архивы. Настройки и их принятие по-прежнему не обозначают успешную копию.

## История и возврат плана (после preview.4)

Требуются вход администратора и те же правила CSRF, что для публикации. Все ответы административных маршрутов запрещают кэширование. Схема БД обновляется с 3 на 4; до обновления нужна проверенная копия сервера.

- `GET /api/v1/management/agents/{id}/configuration/history?page=0` — последние ревизии по убыванию номера: `entries` с `revision`, `savedUtc` (UTC), `author`, `restoredFrom`, `jobCount`; также `total` и `page`. По 20 записей на страницу; номер ограничивается 0–4.
- `GET /api/v1/management/agents/{id}/configuration/history/{revision}` — типизированный сохранённый план с его прежним номером и ETag. Неизвестная/удалённая запись даёт 404; неподдерживаемый документ — 409 и не выдаётся как редактируемый план.
- `POST /api/v1/management/agents/{id}/configuration/history/{revision}/restore` — вернуть **весь** выбранный план новой ревизией. Обязателен `If-Match` **текущей** ревизии, а не ETag старого документа. Тело плана не принимается как источник настроек: сервер читает собственную историю. CSRF передаётся как при PUT.

Например, POST возврата `/history/2/restore` с `If-Match: "5"` создаёт ревизию 6 с заданиями из 2. Успешный ответ — новый типизированный план и `ETag: "6"`. Сам старый документ не меняется. Текущую/будущую ревизию возвращать нельзя (409). Истёкшая сессия/отзыв агента, неизвестный формат текущего или старого плана, отсутствие сохранённой записи и конфликт не изменяют план. Повторный POST со старым If-Match даёт 412.

План, новая запись истории, ограничение до 100 последних ревизий на агент и аудит `ConfigurationRestored` фиксируются одной транзакцией. Обычные публикации также попадают в историю с автором. В журнале возврата хранится исходный номер в `restoredFrom`. При миграции сохраняется только действующая конфигурация, автор такой исходной записи неизвестен; более ранних снимков нет. Начальный пустой план нового агента также учитывается в лимите. Переподключение агента не очищает историю.

Повторная публикация не считается принятием агентом: применяется обычный протокол предложений и подтверждений. Начатый запуск сохраняет прежний снимок; архивы и история запусков не откатываются. История планов не заменяет копию БД, настроек и сертификатов сервера.
