# Обновление сервера в Docker одной командой

Команда доступна в рабочей ветке `feature/local-backup-agent`. Она предназначена
для штатного `deploy/server/compose.yaml` на Linux: один сервер, отдельная
контейнерная PostgreSQL 17, именованные тома и локально опубликованный HTTPS-порт.
Нужны Docker с Compose v2, Git, OpenSSL и Python **3.11 или новее**, доступ к
Docker и чтение файлов секретов. Windows-агент alpha.35 сервер не обновляет.

Из обновлённого checkout репозитория:

```sh
./deploy/server/update.sh
```

Команда выбирает наибольшую версию среди опубликованных серверных выпусков,
включая preview. Теги агента `v0.2.0-alpha.*` и черновики исключаются.
Актуальный серверный выпуск — **server-v0.1.0-preview.9**.
[Публикация, файлы и проверки](server-preview9-publication.md).
Команда выбирает уже опубликованный выпуск; новых релизов она не создаёт.

Для определённой версии:

```sh
./deploy/server/update.sh --version server-v0.1.0-preview.9
```

Если при установке использовались своё имя проекта или `.env`, передайте те же
значения. Для сертификата на собственное имя укажите его DNS-имя:

```sh
./deploy/server/update.sh \
  --project-name server \
  --env-file /opt/spbackup/.env \
  --health-host backup.example.ru
```

Проверка соединяется с локально опубликованным портом, использует имя
`--health-host` (по умолчанию первое имя из `AllowedHosts`) и доверяет
сертификату из текущего PFX. Имя, срок и TLS проверяются; отключения проверки
сертификата нет. Ошибка проверки до обновления оставляет сервер работающим.

## Что выполняется

1. Проверяется работающий стек, соответствие его переменным, порту, тому и
   файлам секретов в Compose. При несовпадении обновление отклоняется.
2. Получается неизменяемый серверный тег. Рабочая ветка не переключается:
   сборка идёт из отдельного временного worktree выбранного коммита.
   Схема более нового сервера не понижается до схемы старого выпуска.
3. Собирается новый образ. Ошибка сборки не останавливает текущий сервер.
4. Сохраняются прежний образ, эффективная конфигурация, секреты и публичный
   сертификат. После короткой остановки приложения — дамп БД и весь `server-data`.
   PostgreSQL остаётся работающей, её контейнер и том не заменяются.
5. Выполняется `--migrate`, пересоздаётся служба `server` с новым образом,
   проверяется HTTPS `/health/ready`. Успех выводится после проверки.

Если образ уже помечен выбранными тегом и коммитом, повторный запуск ничего
не пересоздаёт. Для старого образа без этих меток первый запуск может заново
собрать тот же выпуск; последующие запуски распознают установленный исходник.
`--offline --version <серверный-тег>` использует уже имеющийся локальный тег.

## Сбой и комплект возврата

По умолчанию комплекты находятся в `deploy/server/backups/<дата>-<суффикс>`.
Другой каталог задаётся через `--backup-directory /путь`. Каталог комплекта
имеет права 0700, содержит пароли и закрытый ключ и исключён из Git и контекста
сборки. Хранятся `previous-image.tar`, `database.dump`, `server-data.tar`,
`compose.json`, секреты и `state.json` с результатом и SHA-256 файлов.
Свободное место проверяется заранее, но от других процессов не резервируется.

При обычной ошибке миграции или готовности команда останавливает новую программу,
проверяет комплект и возвращает прежние БД, данные и образ. БД пересоздаётся
из дампа, чтобы новые таблицы не остались после неудачной миграции. Это допустимо
только для отдельной БД штатного стека. Ошибка обновления возвращает ненулевой
код даже при успешном автоматическом возврате.

Если возврат не завершён, команда сообщает об этом и сохраняет комплект;
успех не объявляется. Отключение питания, `kill -9` или отказ Docker требуют
ручного восстановления из комплекта с проверкой состояния стека. Автоматического
возобновления после перезагрузки хоста нет. Комплекты не удаляются автоматически.
Обычная замена образа не возвращает уже мигрированную БД. `down -v` не используется.

Команда обновляет образ существующего сервиса с прежними настройками. Изменение
топологии Compose, внешняя БД, несколько реплик, перенос секретов и обновление
major-версии PostgreSQL в этот сценарий не входят.
