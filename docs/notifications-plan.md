# План развития оповещений Telegram и MAX

Дата: 11 ноября 2026 года.
Статус: **план; новая реализация и приёмка не выполнены**.
Основа анализа: ветка `feature/local-backup-agent`, коммит `56dc919`.

Отдельное направление из [Windows-дорожной карты](windows-roadmap.md).
Разработка оповещений не переоткрывает пропущенные проверки 1С, не меняет
условия beta и не означает разрешения отправлять реальные сообщения.
[Действующая пользовательская инструкция](notifications.md) описывает
существующее поведение; этот документ — будущие изменения.

## 1. Что уже есть

- `src/SPBackup.Core/BackupNotifications.cs`: Telegram/MAX, фильтры событий,
  HTTP-отправитель, диспетчер и сохранённые отметки доставки.
- `src/SPBackup.Desktop/NotificationsWindow.xaml` и код окна: включение
  независимых каналов, числовой ID, токен, тест и сохранение.
- `src/SPBackup.Core/WindowsNotificationCredentialStore.cs`: защищённые
  токены Windows; JSON содержит ссылки на них.
- `tests/SPBackup.Core.Tests/BackupNotificationTests.cs`: модели API,
  фильтры, повторы, независимость каналов, межпроцессная блокировка.
- По текущему коду допускается один получатель на провайдера, всего два канала.
  Ошибки/предупреждения включены по умолчанию; успех и отмена — отдельно.
- История запусков служит очередью; удаление истории до доставки теряет
  соответствующие уведомления. После сбоя используется минутная задержка
  в памяти, которая не переживает перезапуск.
- Отметки защищают от обычного повтора после перезапуска, но разрыв после
  принятия сообщения сервисом всё ещё может дать дубль.

Наличие кода и автоматических моделей не подтверждает доставку настоящему
боту из-под конкретной службы. Это отдельная приёмка.

## 2. Результат и границы первой поставки

Сначала довести существующие локальные уведомления до предсказуемой работы
из окна, трея и службы. Затем добавить центральные правила сервера.

Первая поставка:
- ошибки, неполные копии, прерывания и предупреждения;
- успех/отмена по выбору пользователя;
- независимая сохраняемая очередь, повтор после сети/перезапуска;
- понятное состояние каналов, безопасные сообщения и тест подключения;
- совместимость действующих настроек и отметок доставки.

Следующая поставка:
- серверные правила по агентам/папкам/заданиям;
- отсутствие связи, отсутствие свежей копии, отклонение плана;
- устранение проблемы и, отдельно, ежедневная сводка.

Не входят в первую поставку: команды боту для запуска/удаления копий,
получение архивов через мессенджер, webhook и входящий обработчик команд,
многоадресная рассылка, автоматическое переключение провайдера и
произвольный редактор шаблонов. Telegram и MAX — независимые каналы:
ошибка одного не должна порождать повтор в уже успешном другом.

## 3. Кто формирует и отправляет событие

| Режим | Источник событий | Отправитель |
| --- | --- | --- |
| Автономный агент | Итог локального запуска | Агент/служба либо окно под общей блокировкой очереди |
| Подключённый мониторинг | Итог локального запуска; центральные проблемы наблюдения отдельно | Для итогов по умолчанию сохранить нынешнюю локальную отправку |
| Управляемый агент | Итог запуска и принятие плана | По умолчанию локальная отправка, пока центральная политика явно не включена |
| Центральные правила | Принятые отчёты и серверные состояния | Серверный фоновый обработчик с очередью в PostgreSQL |

Для центральной поставки ввести явный выбор владельца отправки для области
и класса событий: локально, сервером либо намеренно обоими. Переключение
не должно молча включать второй источник уведомлений.

Серверная политика имеет версию и момент действия; агент подтверждает её
применение. До подтверждения панель показывает возможное пересечение.
При согласованном переключении фиксируется граница событий; старые
локальные задания доставки не стираются молча, а завершаются или отменяются
с видимой причиной. Автоматический локальный fallback при потере сервера
в первую центральную поставку не включать: иначе риск двойной отправки.

Сервер может заметить отсутствие агента, сам агент — не всегда.
Остановившийся сервер не способен сообщить о собственной остановке;
для этого нужен внешний мониторинг, отдельный от данного плана.

## 4. События и правила по умолчанию

| Событие | Первая поставка | Центральная поставка |
| --- | --- | --- |
| Ошибка, прерывание, неполная/частичная доставка | Включено; итог с разбивкой количества назначений | Из принятого неизменяемого результата |
| Успех с предупреждениями | Включено, отдельно от чистого успеха | Аналогично; не объявлять полной исправностью |
| Чистый успех | Выключено; включается отдельно | По правилу либо в сводке |
| Отмена | Выключено; включается отдельно | По правилу |
| Нет связи | Не выводить из локального молчания как достоверный центральный факт | По серверному порогу OfflineAfterSeconds |
| Нет свежей копии | Не вводить второй локальный алгоритм в первой поставке | По существующему MaximumBackupAgeHours и области источника/назначений |
| Ошибка опроса SQL | Отдельное расширение, не маскировать как ошибку созданной агентом копии | Использовать текущую модель внешних наблюдений |
| План отклонён, нужен локальный доступ, исполнитель недоступен | Не путать с результатом копии | По существующим кодам проблем |
| Проблема устранена | После введения модели инцидентов | Только если уведомление об этой проблеме было принято сервисом в том же маршруте |

В центральных правилах переиспользовать модель раздела «Проблемы».
Не дублировать расчёт свежести, привязку источника и правила устаревания.
Не назначенный срок свежести означает отсутствие такого контроля.

## 5. Надёжная доставка

### 5.1. Самостоятельная очередь

Предлагаемая модель: событие, маршрут/версия получателя, состояние,
число попыток, NextAttemptUtc, срок актуальности, безопасный код последней
ошибки, ID сообщения сервиса и времена создания/принятия.
Ключ уникальности: EventId + ChannelId + RouteRevision.
Для итогов запуска EventId выводится из стабильного RunId, а не времени опроса.

Локально использовать сохраняемый outbox в профиле агента с существующими
механизмами атомарной записи и отдельной межпроцессной блокировкой.
Сервер использует PostgreSQL, уникальный ключ и аренду задач.
Копирование не удерживает сетевую отправку под своим исполнительским замком.

Согласовать запись итога и создание outbox: локально нужен восстанавливаемый
журнал намерения либо другой явно проверяемый протокол между файлами.
После аварии восстановление добавляет недостающее событие без повторения
копии. Пока событие не материализовано в outbox, удаление соответствующей
истории должно быть защищено. После материализации удаление истории
не удаляет ожидающее уведомление. Ошибка записи outbox видна локально,
но не превращает успешную резервную копию в ошибку.

На сервере создание события и постановка в очередь выполняются одной
транзакцией с принятием отчёта/изменением состояния инцидента.

### 5.2. Состояния и повторы

Состояния: ожидает → отправляется → принято API; отдельно повтор ожидается,
неизвестный исход, требуется исправление настроек, истекло и отменено.
Пользователю показывать «Принято сервисом», а не «Прочитано получателем».

Предлагаемые начальные параметры, уточняемые при реализации:
- сетевые сбои, 5xx: задержки 1/2/5/15/30 минут с небольшим случайным разбросом;
- 429: соблюдать задержку, которую API возвращает в документированном поле
  или заголовке; если её нет, использовать ограниченный backoff;
- 401/403 и постоянные ошибки получателя: приостановить маршрут,
  показать действие; повтор после исправления/явной команды;
- неизвестные ошибки классифицировать по провайдеру и безопасному коду,
  не объявлять все 4xx постоянными без разбора;
- состояние повтора и срок аренды сохранять; после перезапуска очередь продолжается;
- стартовое предложение: актуальность 72 часа, предел 10 000 ожидающих доставок
  на отправителя. Достижение предела видно в интерфейсе; не удалять
  ожидающие ошибки молча. Политику переполнения проверить отдельно;
- просроченное событие получает явный статус. После долгого офлайна
  предлагать сводку пропущенных событий вместо неконтролируемого потока.

Очередь сохраняет минимальную безопасную сводку, независимо от истории копий.
Изменение получателя не пересылает ему старую очередь без явного выбора.
Простая замена токена того же бота не должна сбрасывать идентичность маршрута.
Для другого бота — новая ревизия и проверка получателя.

### 5.3. Дубли и порядок

Успешный ответ и ID сообщения сохраняются до следующей задачи.
При таймауте после возможного принятия или аварии до записи квитанции
исход неизвестен. Повтор может дать дубль: гарантировать exactly-once нельзя
без соответствующего контракта провайдера. Сообщение содержит короткий ID события.

Постоянная ошибка одного маршрута не блокирует другие.
Состояние очереди не меняет результат резервного копирования.
Не отправлять оповещение об ошибке уведомления через тот же неисправный
канал бесконечно: состояние видно в окне/панели и журнале.

## 6. Защита от потока сообщений

Локальные итоги: одно событие на итог запуска и маршрут; не слать отдельное
сообщение для каждого файла. Результаты назначений агрегировать в одной сводке.

Центральные проблемы: сохраняемый инцидент по AgentId, JobId, коду причины
и области источника; открытие → изменение → устранение.
Предложение: первое сообщение, затем напоминание не чаще одного раза в 6 часов.
Повторный отчёт/heartbeat не открывает новый инцидент.

При восстановлении связи сначала принять доступные свежие отчёты, затем
сверить актуальность. Не отправлять «всё исправлено» только из-за heartbeat:
связь восстановлена и копирование успешно — разные события.
Устаревшую ожидающую тревогу можно заменить текущей сводкой с отметкой
в журнале; потеря исторического факта не допускается.

Ограничивать скорость по боту и получателю, учитывать 429.
Для MAX официально указан предел двух сообщений в секунду в один
диалог/чат/канал; начальный общий ограничитель можно сделать строже.
Ежедневная сводка и тихие часы — после базовой поставки, с явным часовым
поясом и проверкой переходов времени.

## 7. Настройка и содержание сообщений

Сохранить текущий вход из настроек. Для каждого канала:
включение, бот/защищённый токен, получатель, тест, состояние и последняя ошибка.
Показывать очередь, следующую попытку и возможность повторить/отменить
конкретную доставку. Тест не включает канал и не переотправляет историю.

Проверять реальную отправку службой, а не делать вывод по успешному тесту окна.
Перед тестом понятно указать отправителя; реальный тест отправляется только
в явно выбранный владельцем тестовый чат.

Сообщение: SP Backup, понятное имя агента/псевдоним, задание, результат,
время события с часовым поясом, количество успешных/ошибочных назначений,
безопасная категория причины, короткий ID.
Для центрального сообщения — ссылка на авторизованную карточку/историю,
без токенов и автоматического входа.

Пример будущего сообщения:

> SP Backup · Бухгалтерия-01  
> Задание: Основная база  
> Частичная доставка: 1 из 2 хранилищ  
> Причина: недоступно хранилище  
> Событие: 11.11.2026 18:40 UTC+10  
> ID: 7f31c2  
> Подробности — в истории задания.

Передача имён компьютера и заданий уже существует; дать возможность
заменить их псевдонимами. Не отправлять пути, строки подключения,
SQL-текст, сырой вывод утилит, содержимое файлов и секреты.
Пользовательское имя может само содержать чувствительный текст:
применять ограничение длины/управляющих символов и объяснить состав сообщения.
Plain text по умолчанию; разметку не принимать из имени задания.

## 8. Провайдеры и секреты

Переиспользовать отправитель, выделив результат отправки и безопасную
классификацию ошибок вместо универсального исключения на все случаи.
Транспорт провайдера не должен знать правила копирования/инцидентов.

Telegram: официальный HTTPS Bot API, sendMessage, числовой chat_id.
MAX: официальный POST /messages, user_id либо chat_id, токен в Authorization.
Действующий код уже использует platform-api2.max.ru.
Не строить план на неофициальных шлюзах.

Только фиксированные HTTPS-домены, без перенаправлений и отключения TLS.
Для MAX требования доверия к сертификатам проверяет администратор по
официальной инструкции; программа не устанавливает корневые сертификаты молча.
Telegram-токен входит в URL API: исключить полный URI из HTTP-логов,
исключений, трассировки и диагностических архивов.

Получатель задаётся числовым ID. Инструкция подключения должна объяснять,
как владелец получает ID официальными средствами; не читать обновления
чужого рабочего бота и не менять его webhook автоматически. Для MAX
учесть получение chat_id из событий добавления/старта и отсутствие готового
списка всех чатов. Нужен доступ владельца к боту ещё до реальной приёмки.

Windows: сохранить Vault и существующую делегацию службе.
Сервер: отдельный провайдер секретов, учитывающий пользователя службы,
ACL и совместимость со снимками/возвратом. Не использовать клиентский
Windows Vault администратора как неявное хранилище серверной службы.
Для Linux — отдельная реализация после Windows, без открытого токена в БД.
В настройках, аудите и экспортируемой конфигурации — только ссылки/маски.

Настройка серверных каналов — администратору. Правила областей должны
соблюдать существующее разграничение доступа; роль просмотра не получает токен.
Секреты не запрашивать в чате и не включать в CI.

## 9. Этапы реализации и критерии готовности

Все этапы ниже **запланированы**. Выполнять пакетами; даты после оценки стендов.

| Этап | Работа | Критерий завершения |
| --- | --- | --- |
| N1. Контракты и миграция | Схемы событий/outbox/маршрутов, безопасные ошибки провайдеров, восстановление записи, тестовая матрица. | Утверждённые примеры, версия формата, сценарий перехода старых настроек/квитанций без рассылки старой истории. |
| N2. Надёжная локальная доставка | Сохраняемая очередь, lease, backoff/429, неизвестный исход, TTL/лимиты, независимость каналов. | Сбой и перезапуск не теряют подтверждённые/ожидающие события; очистка истории не уничтожает outbox; возможный дубль явно описан. |
| N3. Windows-настройка и приёмка | Статусы, повтор/отмена, тест фактическим исполнителем, обновлённая инструкция, токены службы. | WPF 900×580/обе темы, служба после перезагрузки; тестовые Telegram и MAX приняты API, получатель подтвердил видимость; секреты не попали в артефакты. |
| N4. Центральные события | Очередь PostgreSQL, правила областей, версия владельца отправки, offline/overdue/plan/access. | Транзакционная постановка, идемпотентный приём, согласованная граница локально/сервером и актуальные причины без дублей по polling. |
| N5. Инциденты и сводки | Напоминания, устранение, объединение накопившихся событий; затем суточная сводка/тихие часы. | Нет потока на каждый heartbeat; устранение соответствует отправленной проблеме и текущей области; пояс и DST проверены. |
| N6. Пакет и документация | Приёмка обновления/возврата, серверные роли/браузер, снимки секретов, заметки выпуска. | Зафиксированы коммит/SHA-256, реальные границы, инструкции и откат. Публикация — отдельная команда пользователя. |

**Ближайший пакет: N1 → N2 → N3.** Серверные N4–N6 — после локальной
приёмки и выбора центрального режима. Этот план не меняет текущую отправку.

## 10. Проверки и миграция

Автоматически, без реальных получателей:
- оба успешных API-ответа и неверное тело при HTTP 200;
- 401/403, неверный ID, 429, 5xx, TLS/сеть, таймаут до/после возможного принятия;
- сбой до отправки, после ответа и до записи квитанции, восстановление lease;
- конкурентные окно/служба, разные каналы, перестановка и повтор событий;
- удаление истории, повреждение outbox, полный диск, лимит и истечение TTL;
- включение/отключение, изменение фильтров, смена получателя/бота, ротация токена;
- старые notifications.json/notification-deliveries.json, отмена миграции,
  повтор запуска миграции без повторной рассылки;
- сервер: откат транзакции, два обработчика, поздний отчёт, offline→online,
  смена источника, новый enrollment, роли и изоляция областей;
- отсутствие токенов, получателей и полного API-URI в журналах/артефактах.

Миграция: резервировать старые файлы; импортировать существующие отметки;
не рассылать историю до точки включения; не запускать старый и новый
диспетчер параллельно. Отдельно определить возврат старой версии приложения:
старый диспетчер не читает новый outbox и может повторить уже отправленное.
До готовности обратной совместимости безопасный возврат — остановка
диспетчеров, явное отключение каналов и восстановление согласованного
снимка по инструкции с предупреждением о возможном дубле.

Реально, после отдельного разрешения владельца тестового чата:
Telegram/MAX из окна и действующей службы, перезапуск/офлайн, смена токена,
тестовая группа/личный получатель, серверный бот. Для MAX отсутствие
разрешённого бота/доступа платформы означает «ожидает доступа»,
а не успешную приёмку по моделям API.
