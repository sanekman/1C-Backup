# Проверка SQL-копий и восстановления

Задание `native-sql` в Windows CI создаёт отдельные временные экземпляры и базы. Оно не использует настроенные источники пользователя, рабочие базы, обычный экземпляр LocalDB или существующий кластер PostgreSQL. Упаковка дистрибутива зависит от успешного завершения этих проверок вместе с основными тестами.

## SQL Server LocalDB

Новый экземпляр LocalDB получает уникальное имя. Тест создаёт таблицу с текстовыми данными, включая кириллицу, исполняет настоящие `BACKUP DATABASE ... COPY_ONLY, CHECKSUM` и `RESTORE VERIFYONLY`, доставляет `.bak` в хранилище и восстанавливает её в другую базу с проверкой строк.

Затем путь чтения агентом намеренно меняется. SQL создаёт ещё одну копию, но задание завершается ошибкой чтения; прежняя зарегистрированная копия и каталог остаются прежними. Монитор читает настоящую `msdb`: оба завершённых SQL BACKUP наблюдаются независимо от результата доставки агентом, повторное наблюдение не создаёт дублей и не даёт права на очистку внешних файлов.

LocalDB подключается через локальный именованный канал под текущим пользователем Windows. Для этого тест использует отдельную фабрику соединений с опциональным шифрованием. Настройки подключений приложения к обычным SQL Server сохраняют обязательное TLS-шифрование и проверку сертификата. Тест проверяет SQL-команды, доставку и восстановление данных; удалённая аутентификация, сертификат сервера и права отдельной службы требуют своих интеграционных проверок.

## PostgreSQL

Тест инициализирует новый кластер с отдельным пользователем и SCRAM-паролем, слушающий только `127.0.0.1` на свободном порту. Пароль передаётся через временный файл, не аргументы процесса. Уже установленный сервис и его каталог данных не используются.

Два настоящих `pg_dump` проходят `pg_restore --list`, архивирование ZIP AES-256 и параллельную доставку в два локальных места. Основное хранит две копии, дополнительное — одну. Последняя копия проходит SHA-256, сохраняется на компьютер, расшифровывается и восстанавливается настоящим `pg_restore` в другую базу. Проверяется содержимое таблицы после изменения исходных данных между двумя копиями.

Отдельно `tools/postgresql_backup_report.py` создаёт внешнюю копию настоящими утилитами. Агент читает её JSON-отчёт, регистрирует наблюдение без дублей и не меняет каталог принадлежащих ему копий.

Оба экземпляра останавливаются и удаляются вместе со своими временными файлами. В артефакт CI попадает только TRX-результат; временные файлы паролей и кластеров не загружаются.

## Ручной запуск на Windows

Нужны .NET SDK 10.0.401, Python 3.12, SQL Server LocalDB и PostgreSQL с утилитами `initdb`, `pg_ctl`, `psql`, `pg_dump`, `pg_restore`. В PowerShell из корня репозитория:

```powershell
$env:ONECBACKUP_NATIVE_SQL = '1'
$env:ONECBACKUP_TEST_REPOSITORY = (Get-Location).Path
$env:ONECBACKUP_TEST_LOCALDB_EXE = 'C:\Program Files\Microsoft SQL Server\160\Tools\Binn\SqlLocalDB.exe'
$env:PGBIN = 'C:\Program Files\PostgreSQL\17\bin'
dotnet test tests/OneCBackup.Core.Tests --filter 'Category=NativeSqlIntegration'
```

Пути к установленным утилитам могут отличаться. Без явного флага интеграционные тесты пропускаются; обычная проверка ядра исключает их фильтром `Category!=FtpIntegration&Category!=NativeSqlIntegration`. В обязательном задании CI отсутствие утилит считается ошибкой подготовки, а не успешным пропуском.
