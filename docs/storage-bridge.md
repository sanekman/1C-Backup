# Шлюз хранилища для Proxmox — 0.1.0-alpha.2

Выпуск собран SDK 10.0.402 и использует .NET / ASP.NET Core 10.0.13. Версия пакета, установщика и Docker-образа задаётся в `deploy/storage/VERSION`; при сборке по тегу она должна совпадать с `storage-v…`. Публикация занятого Docker-тега запрещена; старый выпуск `storage-v0.1.0-alpha.1` сохраняется.

Контейнер находится в локальной сети рядом с диском или NAS. Он подключается **наружу** к публичному HTTPS-узлу и записывает полученные копии в подключённую папку. Входящие порты, белый IP и сертификат Let’s Encrypt самому шлюзу не нужны. Сетевое соединение внутри ретранслятора дополнительно защищено взаимным TLS агента и шлюза.

Публичный узел может работать в основной программе/фоновом агенте Windows либо отдельным контейнером на доступном из интернета сервере. Для узла нужны доменное имя, HTTPS и WebSocket. Если обе стороны за NAT и входящего доступа нет, потребуется отдельный публичный узел.

## Proxmox: Debian 12 LXC

Рекомендуемые ресурсы: Debian 12 x64, 1 CPU, 512 МБ RAM, 8 ГБ системного диска. Создайте **unprivileged LXC** через интерфейс Proxmox и подключите папку диска/NAS как `/backups`. Docker и nesting этому варианту не требуются.

Можно создать LXC из подготовленного шаблона на хосте Proxmox:

```bash
bash deploy/storage/create-proxmox-lxc.sh \
  --id 120 --storage-path /mnt/nas/backups \
  --template local:vztmpl/debian-12-standard_ВАШ_ШАБЛОН.tar.zst \
  --rootfs-pool local-lvm --bridge vmbr0
pct enter 120
```

Скрипт не удаляет существующие VM/CT и не меняет владельца данных NAS. Реальное имя шаблона посмотрите в Proxmox; номер CT должен быть свободным. Настройте права записи для пользователя службы. При стандартном unprivileged UID mapping UID пользователя контейнера отображается на UID хоста с добавлением 100000. Узнайте фактический UID через `id onecbackup-storage`; права NAS настраивает его администратор. Не выполняйте рекурсивный chown существующего NAS автоматически.

Внутри LXC от root:

```bash
apt-get update
apt-get install -y git ca-certificates
git clone --depth 1 --single-branch --branch storage-v0.1.0-alpha.2 \
  https://github.com/sanekman/1C-Backup.git
cd 1C-Backup
bash deploy/storage/install-from-github.sh \
  --storage /backups --endpoint wss://relay.ВАШ-ДОМЕН
```

Для закрытого репозитория предварительно настройте GitHub-аутентификацию Git, например через `gh auth login` и `gh auth setup-git`. Пароли и токены не вставляйте в URL. Скрипт скачивает пакет из отдельной версии ветки GitHub, проверяет SHA-256 и устанавливает самодостаточное приложение .NET; SDK в LXC не нужен.

При первом запуске создаются файлы сопряжения. Файл **client-pairing.json** помещается в отдельную папку `/root/onec-backup-storage-pairing.XXXXXXXX/`; его точный путь выведет установщик. Файл содержит секреты. Скопируйте его безопасно на компьютер основной программы. В контейнере также будет `/etc/onec-backup-storage/hub.json` — это список ID и хешей доступа для публичного узла, без закрытых ключей и паролей. Перенесите его на публичный узел.

После импорта client-pairing.json уберите ненужные копии этого файла из доступных мест; сохраните необходимые секреты восстановления отдельно и защищённо. Сам пароль архива **не входит** в сопряжение — его задают и сохраняют отдельно в основной программе. Служба шлюза не получает этот пароль.

```bash
systemctl status onec-backup-storage
journalctl -u onec-backup-storage -f
```

До включения публичного узла сообщения `gateway_connection_warning` ожидаемы: шлюз повторяет подключение каждые 5 секунд. О наличии связи свидетельствует `gateway_connected`. Установка службы сама по себе не означает доступность внешнего узла.

При повторной установке того же проверенного пакета настройки и сопряжение сохраняются. Для обновления получите новый исходный тег/установщик и пакет; версии размещаются отдельно под `/opt/onec-backup-storage`, затем меняется ссылка `current`. Старые версии и данные автоматически не удаляются. Первоначальный установщик поддерживает Debian 12 x64; реальный systemd/Proxmox нужно проверить на вашем хосте.

Переход alpha.1 → alpha.2 проверен штатным `install-from-github.sh` в Debian 12: данные, сертификаты, секреты, конфигурация и файл сопряжения сохранились. Проверены повторная установка, откат на сохранённую alpha.1 и возврат на alpha.2. Пакет с другой контрольной суммой при том же номере версии отклоняется до перезапуска службы. Эти проверки используют запись вызовов `systemctl`; работа настоящего systemd в Proxmox остаётся отдельной проверкой.

## Docker внутри Linux VM

Docker предпочтительно устанавливать в Linux VM Proxmox. Исходники из того же тега:

```bash
export STORAGE_VERSION="$(cat deploy/storage/VERSION)"
docker build -f deploy/storage/Dockerfile --build-arg VERSION="$STORAGE_VERSION" -t "onec-storage-bridge:$STORAGE_VERSION" .
mkdir -m 700 storage-config
docker run --rm --user "$(id -u):$(id -g)" \
  -v "$PWD/storage-config:/config" "onec-storage-bridge:$STORAGE_VERSION" \
  initialize /config wss://relay.ВАШ-ДОМЕН
export STORAGE_CONFIG_DIRECTORY="$PWD/storage-config"
export STORAGE_DATA_DIRECTORY=/mnt/nas/backups
export STORAGE_UID="$(id -u)" STORAGE_GID="$(id -g)"
docker compose -f deploy/storage/compose.yaml build --build-arg VERSION="$STORAGE_VERSION"
docker compose -f deploy/storage/compose.yaml up -d --no-build
docker compose -f deploy/storage/compose.yaml logs -f
```

`STORAGE_UID`/`STORAGE_GID` должны иметь доступ на запись к папке NAS. Compose монтирует только необходимые ключи шлюза и открытый сертификат агента; client-pairing.json и закрытый ключ агента в контейнер не передаются. Файлы данных хранятся вне writable layer контейнера. Доступ к конфигурации, секретам и Docker daemon ограничьте владельцем.

`STORAGE_VERSION` берётся из того же файла версии, что и Linux-пакет. Явные `build --build-arg VERSION=…` и `up --no-build` работают также с неизменяемым исходным тегом `storage-v0.1.0-alpha.2`: в его Compose-файлах переменная ещё не передаётся автоматически, поэтому `up --build` собирает версию `0.1.0-dev`. В текущих исходниках Compose требует версию и передаёт её в сборку. Опубликованный образ GHCR уже имеет правильную версию.

## Подключение в Windows

Требуется **1C-Backup 0.2.0-alpha.13 или новее**.

1. Если публичный узел будет в основной программе: «Настройки → Публичный узел → Импортировать hub.json». Добавление файла другого шлюза объединяет разрешённые ID, а не удаляет прежние.
2. Опубликуйте локальный порт **127.0.0.1:7087** через Caddy, IIS или Apache, по инструкции ниже. Окно в трее, фоновый агент или служба должны работать. Выключение узла закрывает подключения, но сохраняет список разрешённых шлюзов.
3. В задании выберите «Шлюз хранилища (Proxmox) → Импортировать подключение» и укажите client-pairing.json.
4. Задайте пароль архива. Он обязателен для удалённого назначения. Используется существующий AES-256 ZIP: содержимое защищено, но ZIP не скрывает все имена внутренних файлов.
5. Проверьте хранилище и создайте копию. Шлюз доступен также как дополнительное назначение со своим числом хранимых копий.

Если основной компьютер сам обслуживает узел для этого шлюза, клиент использует локальный туннель с взаимным TLS, избегая NAT loopback. Внешнее подключение шлюза всё равно идёт по публичному WSS/HTTPS.

## Публичный узел и Let’s Encrypt

### Caddy: отдельный сервер

Перенесите **только hub.json** в отдельную папку сервера. Не переносите туда client-pairing.json, PFX, пароли и ключи шлюза.

```bash
export STORAGE_CONFIG_DIRECTORY=/opt/onec-relay-config
export STORAGE_DOMAIN=relay.ВАШ-ДОМЕН
export ACME_EMAIL=ваша-почта@example.com
export STORAGE_UID="$(id -u)" STORAGE_GID="$(id -g)"
export STORAGE_VERSION="$(cat deploy/storage/VERSION)"
docker compose -f deploy/storage/compose.hub.yaml build --build-arg VERSION="$STORAGE_VERSION"
docker compose -f deploy/storage/compose.hub.yaml up -d --no-build
```

DNS A/AAAA должен указывать на публичный узел. Разрешите входящий TCP 80 и 443; удалите ошибочную AAAA-запись, если IPv6 не доступен. Caddy получает сертификат именно у Let’s Encrypt и продлевает его автоматически. Тома `caddy-data` и `caddy-config` сохраняйте при обновлении: в них находятся ключи ACME/сертификаты. Бэкенд слушает только loopback в общей с Caddy сетевой области.

### Caddy на компьютере основной программы

Установите Caddy из официального выпуска https://caddyserver.com/download. Создайте Caddyfile по `deploy/storage/Caddyfile`, подставив свой домен и email вместо переменных, и запустите `caddy run --config Caddyfile`. Для постоянной работы настройте запуск Caddy службой по документации Caddy/администратора. Порт бэкенда по умолчанию 7087; если изменили его в hub.json, измените прокси тоже. Входящие 80/443 и DNS требуются на этом компьютере или его маршрутизаторе.

### IIS (Windows)

1. Установите IIS, функцию **WebSocket Protocol**, URL Rewrite и ARR. В ARR включите **Enable proxy**; настройте достаточный таймаут для длительных передач. Локальный API узла должен работать на 127.0.0.1:7087.
2. Создайте IIS-сайт с HTTP binding вашего домена и поместите `deploy/storage/iis-web.config` в корень сайта как **web.config**. Разрешите Upgrade/WebSocket на сайте.
3. Установите win-acme из официального выпуска https://www.win-acme.com/. От администратора выполните:

```powershell
.\deploy\storage\enable-iis-letsencrypt.ps1 -SiteName 'OneCBackup' `
  -Domain 'relay.ВАШ-ДОМЕН' -Email 'ваша-почта@example.com' `
  -WinAcmePath 'C:\Tools\win-acme\wacs.exe'
```

Скрипт получает сертификат Let’s Encrypt, устанавливает HTTPS binding IIS и позволяет win-acme создать задачу автоматического продления. Проверьте задачу в Task Scheduler и логи win-acme. Сертификат принадлежит HTTPS-сайту IIS; основной программе не нужно хранить его закрытый ключ. Issuance через HTTP-01 требует доступного снаружи порта 80.

### Apache

Apache **2.4.47+**, модули `md`, `ssl`, `proxy`, `proxy_http`, `headers`. Используйте `deploy/storage/apache.conf`, заменив домен/email. `mod_md` запрашивает и продлевает Let’s Encrypt. Подтвердите согласие с условиями Let’s Encrypt настройкой `MDCertificateAgreement accepted`. На Debian модули можно включить через `a2enmod md ssl proxy proxy_http headers`; после изменения проверьте `apachectl configtest` и перезагрузите Apache.

Шаблон предполагает, что Apache и бэкенд находятся **на одном компьютере**: HTTP до loopback несёт уже зашифрованный внутренний TLS-туннель. Для Apache на другом компьютере настройте отдельный проверяемый HTTPS-канал до бэкенда и не отключайте проверку его сертификата.

Если порты проверки домена закрыты, используйте DNS-01 с поддерживаемым DNS-провайдером в Caddy/win-acme/mod_md. Для DNS API потребуется отдельный ограниченный ключ в защищённом хранилище. Сертификат не делает компьютер доступным за NAT сам по себе.

## Границы первой версии и проверка

Загрузка, проверка, скачивание, удаление, квота (по умолчанию 100 ГБ), переподключение и сохранность данных после перезапуска проверяются автоматически. Ретранслятор не хранит полные архивы и не имеет ключей внутреннего TLS; доступны 4 одновременных соединения на шлюз. Секреты и содержимое сообщений не пишутся в лог, логи Docker ограничены по размеру.

Частичные файлы не публикуются как готовые копии. При разрыве загрузка повторяется с начала; продолжение по блокам пока не реализовано. После жёсткого завершения могут остаться `.part`-файлы: они учитываются в квоте и автоматически не удаляются. Не удаляйте их во время активной загрузки. На уровне основного задания действуют существующие правила истории, независимой очистки хранилищ и сохранения инкрементных цепочек.

На диске/NAS объекты лежат как `<ID задания>/<ID копии>.bin`, рядом сохраняется JSON с исходным именем архива (имя задания и дата), размером, SHA-256 и временем приёма. В основной программе и при скачивании используются исходные имена. Полный список удалённых копий после потери локального каталога пока не импортируется автоматически: сохраняйте защищённые резервные копии jobs.json/copies.json, файл сопряжения и пароль архива отдельно. При необходимости `.bin` можно скопировать с NAS, проверить по JSON и открыть как ZIP с вашим паролем. Для инкремента потребуется вся цепочка.

Внутренние сертификаты сопряжения действуют 3 года; перевыпуск требует нового сопряжения. Это отдельные сертификаты от автоматически продлеваемого публичного Let’s Encrypt. Публичный узел отзывается удалением соответствующего ID из списка Peers; после применения настройки соединения закрываются.

В этой среде проверяются настоящие контейнеры, HTTPS Caddy с отдельным доверенным тестовым сертификатом и взаимный TLS. Реальный выпуск Let’s Encrypt требует вашего домена и не выполнялся. Нативные IIS, Windows GUI, systemd и Proxmox здесь не запускались. Сначала проверьте на тестовой папке, затем используйте для рабочих копий.
