# План пользователей и разграничения доступа сервера

Дата: 11 ноября 2026 года.
Статус: **план; права и скачивание пока не реализованы этим документом**.
Основа: ветка `feature/local-backup-agent`, коммит `c0855b3`.
Связанные документы: [дорожная карта](windows-roadmap.md),
[план оповещений](notifications-plan.md), [правила панели](server-management.md).

## 1. Цель и существующее состояние

Администратор создаёт отдельную учётную запись каждому человеку и выбирает:
какие компьютеры и задания он может мониторить, может ли скачивать их копии.
Пользователь видит только разрешённые ему данные. Изменение настроек,
ручной запуск и удаление копий не выдаются вместе с мониторингом/скачиванием.

Сейчас существуют `server_users`, хэши паролей, security_stamp,
cookie-сеанс, смена пароля и аудит. Но `ServerHost.cs` при входе
назначает роль Administrator каждому вошедшему; страницы и management API
в основном требуют эту роль. Пользовательской роли и объектных разрешений нет.

Точки изменений:
- `ServerAuthentication.cs` — политики и актуальность сеанса;
- `ServerHost.cs` — вход, роль, группы маршрутов;
- `ServerStore.cs`, `ServerStore.Administration.cs` — пользователи/сеансы;
- страницы, запросы мониторинга/истории/проблем и будущий экспорт копий;
- PostgreSQL-миграции, интеграционные тесты и браузерная приёмка.

Скачивание через сервер пока является предложенным механизмом.
Право на него можно подготовить заранее, но до реализации передачи
панель должна говорить «функция ещё недоступна», а не показывать рабочую кнопку.

## 2. Модель первой версии

Две роли:
- **Администратор:** пользователи, права, все компьютеры/задания,
  управление сервером и существующие административные действия.
- **Пользователь:** только явно выданный мониторинг и, отдельно, скачивание.
  Нет общего права редактирования заданий, запусков, удаления или настройки сервера.

В дальнейшем роли оператора/управляющего можно добавить отдельно.
Не вводить их одновременно с первой поставкой без отдельной потребности.

### Разрешения

| Разрешение | Что позволяет | Чего не позволяет |
| --- | --- | --- |
| Мониторинг | Видеть разрешённое задание, его расписание, результаты, прогресс, историю и безопасные сведения о копиях | Изменять план, запускать копирование, читать секреты, скачивать файлы |
| Скачивание | Заказывать подготовку и скачивать зарегистрированные копии разрешённого задания | Восстанавливать поверх базы, удалять архивы, получать пароль архива или произвольные файлы |
| Администрирование | Существующие административные действия и управление пользователями | Не заменяет ограничения протокола агента и проверку принадлежности копии |

Скачивание требует мониторинга того же задания.
Администратор имеет оба разрешения на все объекты.
Пользователь без назначений входит в панель и видит объяснение отсутствия доступа,
а не список всех компьютеров.

## 3. Выбор компьютеров и заданий

В карточке пользователя для каждого компьютера:
- **Выбранные задания:** явный список стабильных JobId с двумя флажками;
- **Все задания компьютера, включая будущие:** отдельное явное назначение,
  рядом мониторинг и скачивание. Перед сохранением виден эффект для будущих задач.

Первое назначение по умолчанию — выбранные задания и только мониторинг.
Флажок «скачивание» по умолчанию выключен.
Переход от выбранных заданий к целому компьютеру требует явного действия
и показывает расширение доступа.

Предлагаемая модель — только разрешения, без скрытых запрещающих правил.
Действующие разрешения складываются; широкое назначение компьютера
нельзя сузить снятием флажка отдельного задания. Интерфейс показывает,
откуда получено право, и предлагает убрать широкое назначение.

Примеры:
| Пользователь | Область | Мониторинг | Скачивание |
| --- | --- | --- | --- |
| Бухгалтер | ПК «Бухгалтерия», задание «Основная база» | Да | Да |
| Наблюдатель | ПК «Склад», задание «Документы» | Да | Нет |
| Руководитель | Все текущие и будущие задания ПК «Филиал-1» | Да | Нет |

Папки можно использовать для поиска компьютеров, но в первой версии
они не являются источником наследуемых прав.
Перемещение компьютера между папками не меняет разрешения.

### Идентичность и жизненный цикл

- Права связываются с AgentId + JobId, а не именем, путём или номером строки.
  Для целого компьютера — AgentId.
- Учитывать задания из мониторинга автономных агентов, а не только
  поддерживаемые серверным мастером. Неподтверждённый произвольный JobId
  назначить нельзя.
- Переименование не меняет доступ. «Создать на основе» создаёт новый JobId:
  выбранные задания не наследуют право; широкое назначение компьютера — наследует.
- Новый компьютер/enrollment с новым AgentId не наследует права старого.
  Если ID сохраняется при повторном подключении, до реализации определить
  явную процедуру подтверждения переноса доступа, без молчаливого расширения.
- Удалённое задание может сохранить историю/копии: назначение по JobId
  продолжает открывать только его исторические данные. Показать это администратору.
  Повторное использование JobId для другой задачи запретить.
- Мониторинг задания раскрывает его историю, а не только последний запуск.
  Скачивание распространяется на доступные зарегистрированные копии этого JobId.
  Ограничение по датам — отдельное будущее расширение.
- Отозванный агент не выполняет новые запросы передачи. Уже подготовленные
  файлы его копий становятся недоступны до административного решения.

## 4. Интерфейс администратора и пользователя

Раздел **«Пользователи»**:
логин, отображаемое имя, роль, активность, последняя успешная авторизация,
число доступных компьютеров/заданий. Пароли и их хэши не показываются.

Карточка:
1. Учётная запись: логин, имя, роль, активность.
2. Доступ: поиск компьютера, выбранные задания либо весь компьютер,
   мониторинг/скачивание, явное указание будущих задач.
3. Предпросмотр: итоговые права и источник каждого разрешения.
4. Безопасность: сброс пароля, завершение всех сеансов, блокировка.
5. Аудит изменений этой записи.

Пример настройки:
«Пользователь Иван → Бухгалтерия-01 → Основная база →
Мониторинг ✓ → Скачивание ✓».

Для пользователя:
- вход и выход, собственная смена пароля;
- список доступных компьютеров;
- карточки только разрешённых заданий и их история;
- раздел «Копии» с разрешённым скачиванием после реализации экспорта;
- никаких ссылок на пользователей, секреты, настройки сервера и управление планами.

Выбор одного задания даёт минимальную карточку компьютера: имя, связь,
время последнего отчёта и версия агента. Общемашинные сведения способны
раскрывать контекст; это указать при назначении. Пути и защищённые привязки
не включать в минимальную карточку.
Прогресс чужого задания скрывать, даже если он есть в общем отчёте компьютера.

## 5. Проверка доступа на сервере

Единый сервис авторизации: субъект, действие, AgentId, при необходимости JobId,
RunId, BackupId и DownloadRequestId. Проверка принадлежности всех идентификаторов
обязательна; одного права на компьютер из параметра URL недостаточно.

Разделить маршруты и политики:
- AuthenticatedUser — свой профиль, смена своего пароля, выход;
- MonitoringRead — мониторинг с фильтром объектов;
- BackupDownload — подготовка/скачивание с объектной проверкой;
- Administrator — управление сервером, пользователями, планами и командами;
- AgentBearer — существующие агентские маршруты, без человеческих прав.

Не заменять Administrator на «любой вошедший» у всей группы management.
Новые DTO для чтения исключают поля управления и секретные ссылки.
Роль берётся из БД; жёсткое назначение Administrator при входе удаляется.
Агентский токен не даёт права входа пользователя или скачивания в браузере.

### Все поверхности данных

Фильтровать в SQL **до пагинации и подсчёта**:
список компьютеров, карточки, задания, историю, копии, поиск,
сводки проблем, счётчики, папки и данные будущих уведомлений.
Нельзя сначала получить всё и только скрыть чужие строки в Razor.

Проверять также:
- прямые URL и API, детали результата/назначения, раскрытые причины;
- общий прогресс и предупреждения сбора, способные раскрыть чужие задания;
- историю планов и возврат плана — оставить администраторам;
- состояние конфигурации целого агента, capabilities и системную диагностику —
  оставить администраторам либо дать отдельный минимальный DTO;
- аудит всего сервера, OpenAPI и диагностику — администраторам;
- имена папок: показывать только необходимые предки разрешённых компьютеров,
  без чужих имён, количества и пустых чужих веток;
- экспорт таблиц и списки выбора, если такие появятся.

Чужой или несуществующий объект возвращает одинаковый 404.
Для своего известного объекта без права действия допустим 403.
Неаутентифицированный API возвращает 401.
Ответы с частными данными — no-store; кэш зависит от пользователя и версии прав.

## 6. Скачивание копий с учётом прав

Будущий поток:
заявка пользователя → серверная проверка → команда агенту →
временный файл сервера → проверка SHA-256/размера → выдача браузеру → очистка.

Требования:
- разрешение проверяется при заявке, перед разрешением передачи агенту,
  после подготовки, при открытии файла и при каждом Range-запросе;
- заявка привязана к UserId, AgentId, JobId, BackupId, текущему подключению
  агента и сроку действия. В запросе нет произвольного пути или URL хранилища;
- агент сверяет зарегистрированную копию и область запроса;
  сервер не принимает файл для чужой заявки;
- подготовленные файлы вне wwwroot, без публичных ссылок; выдача только
  после актуальной авторизации. URL/ID заявки сам по себе не является разрешением;
- пользователь по умолчанию видит только свои заявки; администратор может
  видеть и отменять все. Общий внутренний файл не отменяет отдельной проверки;
- отзыв права/блокировка отменяет незавершённые заявки пользователя.
  Продолжающуюся выдачу сервер прекращает при обнаружении отзыва
  с ограниченной задержкой, которую фиксируют тесты; уже полученные байты
  забрать обратно невозможно;
- защищённый архив остаётся зашифрованным, пароль в панель не передаётся;
- инкремент: предупредить о цепочке, выдавать комплект только при праве
  на каждую составляющую и подтверждённой принадлежности. Внешний SQL-отчёт
  сам по себе не даёт файла;
- квоты диска/параллельных скачиваний/объёма и время хранения —
  отдельные настройки экспорта. Копия защищена от очистки на время чтения.

До реализации этого механизма этап прав может быть принят для мониторинга,
но право скачивания остаётся неактивной возможностью, а не принятой функцией.

## 7. Учётные записи, сеансы и аудит

- Отдельный нормализованный уникальный логин; переиспользовать существующее
  хэширование паролей, ограничения ввода и защиту от перебора.
- При создании администратор задаёт временный пароль через защищённую форму
  либо одноразовую активацию. Для первой версии выбрать временный пароль:
  обязательная смена при входе, до смены мониторинг и скачивание закрыты.
  Не писать пароль в аудит/логи; не пересылать его ботом автоматически.
- Администратор сбрасывает, но не читает прежний пароль.
  Своя смена требует текущего пароля; все сеансы этой записи завершаются.
- Обновление роли, прав, пароля, блокировка меняют security_stamp/версию доступа.
  Существующая проверка сеанса расширяется проверкой активности.
  При отзыве следующая серверная операция уже не пользуется старым cookie.
- Длительные задачи и отправка файла проверяют актуальное состояние отдельно;
  одной проверки cookie в начале недостаточно.
- Последнего активного администратора нельзя заблокировать, удалить или
  понизить: проверка транзакционная с защитой от конкурентных запросов.
- В первой версии блокировка вместо физического удаления:
  сохранить владельцев заявок, ссылки аудита и историю.
- CSRF на всех изменяющих формах/API, включая заявку скачивания;
  GET не запускает подготовку файла и не меняет права.
- Пользователь не назначает себе права и не управляет чужими сеансами.

Аудит: субъект и объект, время UTC, безопасный тип действия,
изменённые области и разрешения до/после, результат, ID заявки скачивания.
Отдельно «запрошено», «подготовлено», «передача началась/завершилась/прервана»:
успешный HTTP-ответ не доказывает, что пользователь сохранил файл.
Не включать пароли, токены, секретные ссылки или содержимое архивов.

## 8. Данные, миграция и совместимость

Предлагаемые изменения, окончательные имена определить в этапе U1:
- расширить server_users: display_name, role, enabled,
  must_change_password, access_version, last_login_utc;
- таблица назначений: user_id, agent_id, nullable job_id,
  monitor, download, version. NULL job_id — все задания компьютера;
- ограничения уникальности отдельно для назначения компьютера и задания,
  проверка download ⇒ monitor, ссылки на пользователя/агента;
- каталог идентичности заданий для локальных и управляемых задач,
  если имеющейся модели недостаточно; не делать FK только к текущему JSON-плану;
- расширение аудита и, при необходимости, серверное состояние отзыва
  длительных операций.

Существующие учётные записи перенести в активных администраторов —
до миграции именно так они интерпретировались. Роль не оставлять неявной.
Новые записи пользователя не получают доступ по умолчанию.
Первичная настройка создаёт первого администратора и остаётся закрытой
после настройки. Миграция схемы — транзакционная, с текущим механизмом блокировки.

Смена пароля/выход должны работать и у пользователя;
нынешние Administrator-ограничения на этих маршрутах пересмотреть отдельно.
Функции чтения, изменённые для пользователя, не ослабляют права записи.

Перед изменением схемы — согласованный снимок программы, БД, настроек и ключей.
**Возврат старого кода поверх новых пользователей опасен: старый вход
назначает всем Administrator.** Для отката требуется остановка сервера,
возврат согласованного снимка старой БД/программы и завершение всех сеансов,
созданных после перехода. Сохранение новых пользователей при запуске старого
приложения недопустимо. Откат схемы удалением столбца role не является
безопасной процедурой.

## 9. Связь с оповещениями

Серверный бот — самостоятельный получатель данных, а не автоматически
текущий пользователь панели. Назначение чата/области остаётся административным
действием и явно показывает, какие сведения уйдут наружу.

Если появятся личные подписки пользователя, вычислять их область как
пересечение подписки и действующего мониторинга; проверять снова перед
доставкой из очереди. После отзыва не отправлять накопленные чужие события.
Не считать право мониторинга разрешением скачивать по ссылке из сообщения.
Никаких ссылок с токеном обхода авторизации.

## 10. Этапы и критерии приёмки

Все этапы запланированы; этот документ не присваивает им готовность.

| Этап | Работа | Критерий завершения |
| --- | --- | --- |
| U1. Контракт доступа | Матрица действий/объектов, перечень маршрутов и DTO, семантика назначения компьютера/заданий, схема/миграция и откат | Для каждой страницы/API известны требуемое право, фильтр и ошибки; есть сценарии запрета и безопасный переход со старого сервера |
| U2. Учётные записи | Пользователи, роли, создание/блокировка/сброс, своя смена пароля, stamp, защита последнего администратора | Новый пользователь не становится администратором; блокировка/понижение прекращают действие старого сеанса |
| U3. Ограниченный мониторинг | Единый сервис прав, SQL-фильтры, безопасные DTO, история/проблемы/папки/поиск | Ни HTML, ни API, ни счётчики не раскрывают чужие задания; прямой URL не обходит ограничение |
| U4. Интерфейс назначений | Список пользователей, карточка, поиск, выбранные задания/весь компьютер, итоговые права | Администратор видит эффект для будущих заданий и источник прав; две темы, клавиатура и компактный браузер приняты |
| U5. Право скачивания | Интеграция с фактическим механизмом экспорта, заявки, права на файл/Range, отзыв и квоты | Пользователь без download не получает байты через заявку, чужой ID, ссылку или Range; экспорт отдельно прошёл приёмку |
| U6. Обновление и эксплуатация | Миграция, аудит, проверка сохранения администратора, снимок/возврат, инструкции | Проверены старый→новый сервер и согласованный возврат без повышения прав новых пользователей |

**Порядок:** U1 → U2 → U3 → U4 — самостоятельная поставка мониторинга.
U5 зависит от реализации передачи архивов через сервер; одновременно
добавлять его «на будущее» как работающий механизм нельзя.
U6 выполняется для каждой выпускаемой поставки. Даты — после оценки реализации.
Новый выпуск только по отдельной команде пользователя.

## 11. Обязательные проверки

- Пользователи A/B, два компьютера, несколько заданий, администратор,
  отключённая запись и пользователь без назначений.
- Все комбинации monitor/download; нельзя сохранить download без monitor.
- Подмена AgentId/JobId/RunId/BackupId/заявки; ID своего задания с чужим запуском.
- Список/поиск/папки/сводки/пагинация не раскрывают чужие имена и количества.
- Общий отчёт агента с несколькими задачами не раскрывает чужой прогресс,
  историю, пути, секретные ссылки или данные конфигурации.
- Только выбранное задание; новое задание не появляется автоматически.
  Широкое назначение явно включает будущее; снятие частного флажка не скрывает
  широкого права.
- Переименование, клонирование, удаление с историей, перемещение папки,
  повторное подключение и новый enrollment.
- Отзыв прав между запросом и подготовкой, между подготовкой и выдачей,
  во время потока, при докачивании; блокировка владельца заявки.
- Два конкурентных понижения последних администраторов не оставляют сервер
  без администратора; устаревшая форма не перезаписывает новые права.
- Смена пароля/сброс/понижение/выход, временный пароль, просроченный cookie,
  CSRF и ограничение попыток входа.
- Старый сервер→новая схема, сбой миграции, обязательный запрет старого
  приложения поверх новой схемы, согласованный возврат и отзыв сеансов.
- Агентские API продолжают работать; пользователи не получают AgentBearer.
- Настоящий браузер: каждая роль, прямые переходы, обе темы, пустое состояние,
  длинные имена, навигация и доступность действий.
- Автоматические тесты экспорта используют собственные тестовые файлы;
  проверка реальной выдачи не затрагивает рабочие резервные копии.

Принятие: указаны коммит, окружение, отчёты и ограничения.
Наличие списка пользователей само по себе не означает изоляцию данных.

## 12. Обратимость документа

План добавляется отдельным коммитом без изменений приложения.
Его отмена: `git revert <коммит-добавления-плана>`.
Будущая реализация пользователей требует процедуры возврата из раздела 8;
одного git revert кода недостаточно.
