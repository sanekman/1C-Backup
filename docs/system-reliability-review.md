# SP Backup. Сквозной разбор перед файловой beta

19 ноября 2026 года. Ветка `feature/local-backup-agent`, коммит `4bcd1b2`. Разбор охватывает Windows-агент и службу, файловое ядро, WPF, обмен с сервером, PostgreSQL панели, Dashboard, восстановление и обслуживание. Для SQL, 1С, шлюза и установщиков использованы код и существующие протоколы. Новые опыты выполнены на общем ядре в Linux с .NET 10.0.13, SDK 10.0.402 и временными локальными каталогами.

## Решение для следующего выпуска

Первый пакет должен отвечать на один операторский вопрос: **«Какую версию данных я смогу восстановить, откуда и когда это проверено?»** Сейчас одни части программы отвечают по записи каталога, другие по итогу запуска, времени окончания или последнему отчёту агента. Эти признаки расходятся именно при сбоях. Воспроизведены три разных последствия: очистка может удалить единственную рабочую основу, серверный отчёт может посчитать успешными оба назначения при ошибке проверки обоих, а корректно записанный запуск может вовсе не пройти отбор для отправки.

Ближайший результат — согласовать выбор точки, разрешение на очистку и итог для оператора. После этого можно проверять доступ к старым назначениям и обновление данных Dashboard. Дерево папок, перенос с подтверждением, цвет связи, переключатель темы, обновление CT 107 и обычное восстановление с NAS уже имеют приёмочные результаты. ## Интерфейс и права оператора

- **Утром в Dashboard.** В одной строке нужны четыре ответа: связь и время её наблюдения, текущая работа, итог последнего запуска, последняя проверенная версия в нужном назначении. Для проблемной строки главное действие — открыть конкретную версию и увидеть, где она сохранилась. «На связи» остаётся зелёным даже при ошибке задания. Причина ошибки выделяется отдельно и имеет текст. При выборе ветви дерева сохранять фильтр и выделение. Проверка — два агента на связи, у одного ошибка назначения, у второго устаревший отчёт. Оператор различает причины без открытия двух карточек. [Таблица Dashboard](../src/SPBackup.Server/Components/AgentDirectory.razor)
- **При настройке задания в WPF.** Рядом с источником и каждым назначением показывать учётную запись исполнителя, действие «Изменить доступ» и результат последней проверки под этой учётной записью. Пароль ZIP относится к архиву, поэтому остаётся в блоке архивации. В «Настройках» достаточно режима запуска и общих параметров. Приёмка — при работающей службе заменить вход на второе хранилище и пароль архива, выполнить следующий запуск и восстановить старый архив прежним паролем. [Правила интерфейса](interface-design.md) · [Привязки](../src/SPBackup.Core/ManagedJobBindings.cs)
- **При восстановлении.** Начинать с задания, даты и файла. После выбора точки показать источник, список назначений, дату последней проверки и требуемый пароль. Открывать прежнее назначение на чтение без перенастройки рабочего задания. Сохранить существующее восстановление во вновь созданную папку. [Окно восстановления](../src/SPBackup.Desktop/MainWindow.CopyRestore.cs)
- **Для дежурного сотрудника.** Использовать существующий план ограниченного мониторинга. Один и тот же набор разрешённых агентов и заданий должен применяться к дереву, поиску, счётчикам, истории и экспорту. Выдачу права на скачивание рассматривать отдельно. Критерий — пользователь одного филиала получает одинаковый набор данных на всех этих экранах. [План прав](server-user-access-plan.md)

## Новые опыты и их границы

**13. Успешная копия выпала из отбора отчётов.** Файловое задание записало изменённый файл в два локальных назначения. Через TimeProvider часы тестируемого агента переведены на час назад между началом и завершением одного запуска. Итог в локальной истории — Succeeded, содержимое новой версии восстановилось из обоих назначений. Штатные ToReport и MonitoringValidation.Valid дали false при разности времён −60 минут и true для контрольного запуска без перевода. Диспетчер добавляет в очередь только прошедшие валидацию отчёты, для остальных увеличивает CollectionWarnings. Поэтому число PendingRuns само по себе не выявит этот пропуск. Проверены локальный запуск, восстановление и отбор по общему контракту. Поведение интерфейса и передача по HTTPS в этом опыте не измерялись. [Контракт отчёта](../src/SPBackup.Core/ServerMonitoringContracts.cs) · [Диспетчер](../src/SPBackup.Core/ServerMonitoring.cs)

**14. Исправный архив прежнего назначения.** Созданы две копии одного файла. Оба прежних назначения заменены третьим в экземпляре задания с тем же ID. Для обеих старых записей штатный восстановитель сообщил, что нужны прежние настройки хранилища. Файлы оставались на диске. При передаче исходных настроек тот же восстановитель вернул исходное содержимое из обоих мест. Это ограничение доступа к истории, физические копии в опыте сохранились. [Выбор назначения](../src/SPBackup.Core/BackupCopyVerifier.cs)

**15. Длительная эксплуатация и диагностика.** Шаблон записи получен от настоящего файлового запуска с двумя назначениями. Для измерения истории сгенерированы уникальные ID запусков и распределены по 1, 10 и 20 заданиям, по одному запуску в день в течение 365 дней на задание. Замерены штатные ReadAsync и SaveAsync при замене одного результата. Release-сборка, один прогрев и медиана трёх повторов на локальной файловой системе Linux. Числа зависят от машины, файлового кэша и состава записи.

| Записей | Объём runs.json, байт | Чтение, мс | Замена одной записи, мс |
| ---: | ---: | ---: | ---: |
| 365 | 1 302 687 | 12,6 | 19,7 |
| 3 650 | 13 026 852 | 259,5 | 287,5 |
| 7 300 | 26 053 702 | 134,3 | 207,8 |

Времена на больших наборах различаются немонотонно, поэтому экстраполяция на парк по ним ненадёжна. Подтверждён объём работы: изменение одной записи читает и переписывает общий файл. Диспетчер мониторинга также читает всю историю при опросе, выбирает до 25 отчётов и сохраняет подтверждение после каждого успешного ответа. При очереди в 1 000 готовых отчётов это минимум 40 партий даже при стабильной связи. Длительность отправки и нагрузка PostgreSQL здесь не измерялись. [История](../src/SPBackup.Core/BackupRunHistory.cs) · [Мониторинг](../src/SPBackup.Core/ServerMonitoring.cs)

Отдельно созданы два валидных профиля и экспортированы настоящие диагностические ZIP. При 7 300 записях (26 053 702 байта) в runs-summary.json вошли 1 000 строк, HistoryStatus был Available. При 10 950 записях (39 080 552 байта) обычное чтение вернуло всю историю, а экспорт выдал ноль строк и Unavailable. Причина в пределе входного файла 32 МиБ, применяемом до выбора последних 1 000 строк. Сохранить ограничение затрат на диагностику и дать ей ограниченный по размеру источник последних событий. Достигнутый предел объёма следует показывать отдельно от повреждения истории. [Экспорт диагностики](../src/SPBackup.Core/DiagnosticBundle.cs)

## Очередность реализации и приёмки

1. **Сохранность и честный итог.** Сначала разделить регистрацию, проверку и очистку в результате каждого назначения. Использовать существующие ID снимков, связи с родителем и признак источника. Для старых записей с неопределённым порядком сохранять сомнительные точки до сверки. Приёмка на Windows объединяет обычную доставку, повреждение одного и двух архивов, исчезновение основы, перевод часов и опустевший источник. Сверить реальный файл, локальную историю и отчёт сервера. Ожидаемый итог при повреждении обоих новых архивов — ошибка доставки и доступная прежняя версия. [Критерии пакета 1](reliability-and-recovery-plan.md)
2. **Согласованность службы, обмена и панели.** Связать отчёт с ID запуска и ревизией, отделить порядок исполнения и длительность от настенных часов. Сохранять фактические отметки при коррекции времени, согласовать формат со старым агентом и сервером. Проверить очередь после перерыва связи и повторной доставки, прогресс при новом запуске того же задания, карточку при множестве внешних наблюдений. Необработанный отчёт должен быть виден оператору. При восстановлении связи на сервере должна быть одна запись на запуск. Проверить WPF и браузер, удержание фокуса, ветви дерева и открытого подтверждения переноса. [Расписание и Dashboard](reliability-and-recovery-plan.md) · [Контракт API](agent-api.md)
3. **Восстановление после потери доступа или машины.** Начать с чтения архивов бывшего назначения без изменения рабочего расписания. Затем испытать сборку одной версии из двух назначений и переносимый комплект на чистой Windows-машине. Для серверного снимка отдельно проверить восстановление БД панели, ключей и связи тестового агента. Сверять фактические данные, время восстановления и действия, требующие оператора. Для SQL использовать тестовую БД и проверку строк после восстановления. Приёмка реальной 1С пропущена по решению пользователя, доменный SQL под службой ожидает стенда. [SQL](sql-backups.md) · [Протокол Windows](windows-stage75-beta-readiness.md)
4. **Годовая история, диагностика и большой парк.** На Windows повторить замер для типичной истории пользователя. Снять медиану и p95 времени открытия истории, начала задания и экспорта диагностики, объём записи на диск и память.
