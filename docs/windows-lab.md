# Изолированный Windows-стенд SP Backup

Стенд предназначен для оставшихся проверок пункта 1: настоящая перезагрузка во время копирования, отдельный SMB-сервер и доменная учётная запись службы. Скрипты создают две ВМ в собственной **Private**-сети Hyper-V: `SPB-DC` — тестовый домен `spbackup.test` и файловый сервер, `SPB-AGENT` — участник домена с агентом. Подключения к рабочей сети и маршрута в Интернет у гостей нет. Управление идёт с хоста через PowerShell Direct.

**Статус:** сценарии подготовлены. Сборка и обычный Windows CI проверяются отдельно; до получения результатов с этого стенда перезагрузка и доменный SMB не считаются проверенными. В текущем облачном окружении нет Windows-хоста и доступа к аппаратной виртуализации.

## Что понадобится

- Отдельный Windows 11 Pro/Enterprise или Windows Server с Hyper-V и правами администратора. Минимум 8 ГиБ свободной памяти сверх потребностей хоста и примерно 60 ГиБ свободного диска.
- Английский Windows Server 2022 или 2025 x64. Для временного теста подойдёт [официальная ознакомительная версия Microsoft](https://www.microsoft.com/en-us/evalcenter/); её условия и срок действия продолжают действовать.
- SDK .NET **10.0.402**, runtime **10.0.13** и установленный PostgreSQL на машине сборки. Нужны его папки `bin`, `lib`, `share`; рабочие базы в комплект не копируются.

GitHub-токен и облачная подписка не нужны. Создаваемые ВМ и сеть получают случайный идентификатор. Родительский VHDX читается; изменения гостей попадают в отдельные разностные диски.

## Один раз подготовить исходный Windows-образ

1. В диспетчере Hyper-V создайте временную ВМ **поколения 2**, установите английский Windows Server с локальной учётной записью `Administrator`. Подходит и Server Core. Рабочих данных, агента и членства в рабочем домене в этой ВМ быть не должно.
2. Установите в неё [Microsoft Visual C++ Redistributable x64](https://aka.ms/vs/17/release/vc_redist.x64.exe), необходимый утилитам PostgreSQL, и обновления ОС.
3. Скопируйте внутрь ВМ файл `tools/prepare_windows_lab_image.ps1` из этого репозитория.
4. Откройте PowerShell от администратора **внутри временной ВМ**:

   ```powershell
   $imageAdmin = Get-Credential -UserName Administrator -Message 'Новый пароль только для тестового образа'
   .\prepare_windows_lab_image.ps1 -Administrator $imageAdmin -PrepareDisposableImage
   ```

   Задайте отдельный пароль длиной не менее 14 символов и сохраните его для следующего шага. Скрипт создаёт закрытый файл первоначальной настройки, выполняет Sysprep и выключает ВМ. Пароль временно находится в файле ответов в открытом виде, с доступом только администраторов и SYSTEM. При первом запуске производного гостя `SetupComplete.cmd` удаляет исходный и кэшированные файлы ответов. Родительский VHDX с ответом тоже храните в закрытой папке.
5. Запомните путь к VHDX выключенной ВМ. **Не запускайте родительский образ снова:** гости должны получить разные SID при первоначальной настройке. При совпадении SID проверка остановится.

## Собрать комплект из зафиксированного коммита

В чистой Windows-копии репозитория с SDK выполните из корня:

```powershell
.\tools\build_windows_lab.ps1 -Output D:\SPBackupLabBundle -PostgreSqlRoot 'C:\Program Files\PostgreSQL\17'
```

Укажите свою папку PostgreSQL. Выходная папка должна быть новой. Скрипт собирает настоящий агент, проверяющую программу и тесты доставки, добавляет Windows SDK и утилиты PostgreSQL. В `bundle.json` записываются коммит и SHA-256 каждого файла. Публичный выпуск не создаётся.

Комплект также собирается проверкой GitHub Actions **Prepare isolated Windows lab bundle** при изменении сценариев стенда. Готовый artifact `windows-lab-<коммит>` хранится 14 дней: его можно скачать и распаковать на хосте Hyper-V вместо локальной сборки. Внутри есть папка `controller` с этими сценариями и инструкцией. Запускайте её файлы для соответствующего коммита; SDK на хосте тогда не нужен.

## Создать и проверить стенд

На хосте Hyper-V откройте PowerShell от администратора в корне репозитория:

```powershell
$imageAdmin = Get-Credential -UserName Administrator -Message 'Пароль, заданный при подготовке образа'
.\tools\windows_lab.ps1 -Action Create -Root D:\SPBackupLab `
    -BaseVhdx D:\Images\WindowsServer-Lab.vhdx `
    -Bundle D:\SPBackupLabBundle -BaseCredential $imageAdmin
```

Подготовка занимает несколько перезагрузок. Скрипт создаёт свои ВМ, поднимает новый лес AD, включает гостя в домен, создаёт пользователя службы и две SMB-папки. NTFS разрешает ему запись в обе; SMB разрешает одну и явно запрещает вторую. Учётные данные сохраняются на хосте через `Export-Clixml` с шифрованием текущего пользователя Windows. Папка стенда доступна владельцу, администраторам и SYSTEM.

После успешного создания:

```powershell
.\tools\windows_lab.ps1 -Action Test -Root D:\SPBackupLab
```

Проверки идут последовательно:

1. **Доменная служба и отдельный SMB-сервер.** Служба под `SPBLAB\spbackup-service` проверяет разрешённую и запрещённую папки, создаёт зашифрованную копию, сверяет SID владельца, SHA-256 и восстановленные байты. Пароль службы передаётся через stdin, не через командную строку или JSON-файл.
2. **Обрыв SMB при доставке.** Тест записывает и сбрасывает первый блок готового архива на второй машине. Контроллер проверяет серверный дескриптор и удаляет только собственную шару. Следующую запись отклоняет Windows. Перед производственным повтором контроллер возвращает шару. Проверяются те же байты, SHA-256, однократная регистрация, сохранность старой копии и отсутствие временных файлов. Сценарий доставки работает от доменного администратора; отдельный сценарий выше проверяет учётную запись службы.
3. **Выключение ВМ во время `pg_dump`.** После проверки рабочих копий настоящий `pg_dump` ждёт реальную блокировку тестовой таблицы. Состояние сохраняется с DPAPI владельца. Хост принудительно выключает только свою ВМ агента и включает её снова. Смена идентификатора загрузки обязательна: перезапуск процесса пройти проверку не может.
4. **Восстановление после загрузки.** Без ручного старта службы проверяются её автозапуск, новый сеанс, владение профилем, завершение старого ручного подтверждения, отсутствие повтора команды и одна стартовая копия за новую загрузку. Сверяются история, обычные и защищённые задания, SHA-256 архивов. Старый и новый SQL-архивы действительно восстанавливаются; обе стартовые ZIP-копии сверяются с исходными данными.

При ошибке этап останавливается. Общее сообщение об успехе появляется только после всех этапов, включая один SMB-тест без пропуска. Результаты копируются в новую папку `results-…` на хосте. В ней должны быть `domain-service-result.json`, `remote-smb.trx`, `reboot-result.json`; в последнем — разные прежний и новый `bootId`. Внутренний зашифрованный checkpoint публиковать не нужно.

Если контроллер не выключил гостя за 75 секунд после готовности блокировки, подготовка завершается ошибкой и очищает свои ресурсы. Успешной проверки перезагрузки тогда нет. Для повторного испытания создайте новый стенд: прежние результаты и checkpoints не заменяются.

## Удалить созданный стенд

```powershell
.\tools\windows_lab.ps1 -Action Remove -Root D:\SPBackupLab
```

Сверяются ID, имена, маркеры, сеть и диски ВМ. Скрипт отказывается удалять ВМ с изменённой принадлежностью или добавленными снимками. Удаляются свои ВМ, Private-коммутатор и два разностных диска. Родительский VHDX и результаты сохраняются. После просмотра оставшуюся папку стенда вместе с зашифрованными тестовыми учётными данными можно удалить вручную.

Эти испытания подтверждают конкретный коммит и ОС образа. Полная матрица Windows, настоящая платформа 1С и физическое отключение питания оборудования остаются отдельными проверками.
