# Мониторинг внешних копий SQL

Наблюдение за внешними копиями — отдельный тип задания в общем списке **Задания** Windows-агента. Оно читает сведения о копиях выбранной базы, созданных СУБД или другой программой. На сервере наблюдение отображается в списке заданий карточки агента и на странице заданий; результаты связаны с тем же идентификатором задания.

После изменения SQL-сервера, базы или папки отчётов прежняя история сохраняется, но не подтверждает наличие копий у нового источника. До нового опроса отображается пояснение «Опрос с текущими настройками ещё не выполнялся». Дождитесь автоматического опроса работающего агента или выполните доступную ручную проверку. После обновления старые записи без привязки к настройкам также подтверждаются новым опросом; повторное чтение той же копии не создаёт дубликат и не меняет время её создания.

## Создать задание наблюдения

1. Откройте **Задания → ▾ рядом с «+ Новое задание» → Наблюдение SQL**. Для создания копий самим SP Backup используйте обычное **+ Новое задание**.
2. Укажите понятное название, вид источника и **имя конкретной базы**. Для MS SQL заполните экземпляр и способ входа; для PostgreSQL выберите каталог JSON-отчётов скрипта.
3. Укажите интервал опроса в секундах, оставьте **Автоматический опрос** и нажмите **Сохранить задание**. Закройте окно: наблюдение появится рядом с заданиями копирования.
4. Выберите его в общем списке. **Изменить** открывает настройки, **Результат** — журнал этой базы, **Выключить опрос** останавливает будущие опросы. **Удалить** удаляет задание, сохраняя историю и внешние копии.
5. Для проверки при остановленном агенте нажмите **Проверить сейчас**. Для постоянного опроса оставьте работающим фоновый агент или службу Windows. Настройки включения и интервала применяются без перезапуска.
6. Проверьте результат: **Копия обнаружена**, **Копии пока не обнаружены**, **Ошибка внешней копии** или **Ошибка опроса**. Успешное чтение пустой истории не считается успешной копией. Ошибка подключения не удаляет предыдущие наблюдения.

Кнопка **Мониторинг SQL** сохраняет доступ ко всей истории, включая удалённые задания и ранее настроенные источники. Ранее сохранённые источники появляются в общем списке автоматически: идентификаторы, учётные данные, интервалы и история сохраняются. Старые источники «все базы» продолжают работать; при настройке нового задания выбирают конкретную базу. Управление наблюдением пока выполняется в Windows-программе, а на сервере доступны список, состояние опроса и история.

## MS SQL

Источник читает завершённые записи `msdb.dbo.backupset` и устройства из `msdb.dbo.backupmediafamily`. В alpha.25 подключение использует учётную запись Windows исполнителя. В следующем пакете после alpha.25 также доступен SQL-логин. Оба способа используют обязательный TLS и проверку сертификата. Учётной записи достаточно прав чтения указанных таблиц; монитор не выполняет `BACKUP`, не изменяет историю SQL и не удаляет файлы копий.

Для варианта с SQL-логином в следующем пакете после alpha.25:

1. Откройте **Задания → ▾ рядом с «+ Новое задание» → Наблюдение SQL** и выберите **MS SQL: история msdb**.
2. Укажите понятное название и экземпляр MS SQL. Адрес и права чтения истории сообщает администратор базы.
3. В **Как подключаться** выберите **Логин и пароль MS SQL**, нажмите **Задать логин и пароль MS SQL…**, заполните данные и сохраните.
4. Нажмите **Сохранить задание**, затем **Проверить источник**. Сохранение пароля само по себе не проверяет доступ к базе. Для ручной проверки фоновый агент должен быть остановлен; при работающем агенте дождитесь автоматического опроса.
5. Проверьте историю наблюдений и последний результат опроса. Пустая история без ошибки может означать, что за выбранный период копий не было; она не подтверждает восстановимость базы.

Пароль хранится в Windows Vault; файл `external-monitors.json` содержит только `SqlAuthentication` и `SqlCredentialKey`. Служба получает пароль через защищённый DPAPI-кэш при сохранении источника или установке службы. Пароль несохранённого черновика не экспортируется. При изменении экземпляра MS SQL задайте пароль заново. Переключение на Windows-вход не удаляет старый секрет; новые источники начинают с Windows-входа. Существующие источники без новых полей работают как прежде.

В настройках задаются экземпляр SQL Server, необязательный фильтр базы, период истории (по умолчанию 30 дней) и часовой пояс сервера SQL. Фильтр передаётся параметром запроса. Группируются все устройства одной копии, в том числе копии из нескольких частей. Типы SQL сохраняются как коды: `D` — полная база, `I` — дифференциальная, `L` — журнал; остальные типы также сохраняются без преобразования в полную копию.

Сведения включают базу, тип, начало и окончание, логический размер `backup_size`, записанные пути устройств и UUID набора копии. Размер не равен обязательно размеру сжатого файла. Время `msdb` не содержит UTC-смещения: сохраняются исходные метки и выбранный часовой пояс без предположения о текущем смещении сервера. Для исправления часового пояса уже импортированного источника создайте новый источник: прежние отчёты остаются неизменяемыми.

Запись означает завершение команды согласно истории SQL. Она не подтверждает наличие файлов сейчас, их целостность или возможность восстановления: путь мог быть перезаписан, а копия могла быть удалена. Ошибки SQL Agent, незавершённые команды и ожидание очередной копии этим запросом не отслеживаются. В следующем пакете после alpha.25 известные ошибки подключения и прав показывают те же русские подсказки, что проверка и копирование MS SQL: см. [разбор ошибок](sql-backups.md#если-подключение-не-получилось). Ошибка подключения или чтения отображается как ошибка проверки; прежние наблюдения сохраняются. Удаление истории из `msdb` не удаляет ранее импортированные записи агента.

## PostgreSQL

Выбран вариант `pg_dump --format=custom` для одной базы с отчётом внешнего скрипта. Это подходит для отдельных баз 1С и не требует внедрения менеджера резервных копий кластера. У PostgreSQL нет общей таблицы истории `pg_dump`: появление файла само по себе не считается успешным результатом.

Скрипт [postgresql_backup_report.py](../tools/postgresql_backup_report.py) запускается независимо от агента — вручную или внешним планировщиком. Пример:

```powershell
python tools/postgresql_backup_report.py --database accounting --instance pg-main --backup-directory D:\Backups\Postgres --report-directory D:\BackupReports\Postgres
```

Укажите установленные утилиты через `--pg-dump` и `--pg-restore`, если они отсутствуют в `PATH`. Настройки подключения передаются через стандартное окружение PostgreSQL (`PGHOST`, `PGPORT`, `PGUSER`, `PGSERVICE`) и файл паролей PostgreSQL. Пароль и строка подключения не передаются в аргументе `--database` и не включаются в JSON-отчёт. Версия утилиты должна поддерживать версию сервера.

Скрипт пишет дамп под временным именем, проверяет код `pg_dump`, непустой результат и `pg_restore --list`, затем публикует дамп с уникальным именем. После выполнения атомарно публикуется один неизменяемый JSON-отчёт с уникальным ID, базой, результатом, временем в UTC, размером и путём. Проверка каталога дампа не заменяет пробное восстановление. При ошибке возвращается ненулевой код и публикуется отчёт `Failed`; частичный дамп сохраняется с расширением `.tmp`. Вывод утилит остаётся в локальном `.log`, на сервер отправляется общая причина без содержимого журнала.

В источнике мониторинга выберите каталог JSON-отчётов и при необходимости фильтр базы. Читаются только опубликованные `.json`, файлы `.tmp` игнорируются. Некорректный отчёт вызывает ошибку проверки и не превращается в пустую успешную историю. Чтение всех отчётов завершено до их регистрации, поэтому ошибка одного файла не приводит к частичному импорту этой проверки. Каталог должен содержать только доверенные отчёты, доступные учётной записи агента. Произвольные старые дампы без отчётов не считаются подтверждёнными копиями.

Скрипт не копирует глобальные объекты PostgreSQL, не управляет WAL и не реализует восстановление кластера до точки во времени. Для будущих источников `pgBackRest`/Barman используется общий интерфейс `IExternalBackupSource`.

## История и отправка

Настройки хранятся в `%LOCALAPPDATA%\OneCBackup\external-monitors.json`, наблюдения и очередь — в `external-backups.json`. Повторный опрос одного источника не дублирует копии. Изменение содержимого отчёта с прежним ключом отклоняется. Наблюдения внешних копий не попадают в `BackupCatalog`, поэтому правила удаления N копий агента на них не распространяются.

В режиме `Managed` новая запись привязана к ID агента и текущему адресу сервера. `ExternalBackupOutbox.SendPendingAsync` отправляет записи через клиент API и отмечает доставку после успешного ответа. Ошибка сохраняет запись для повтора; отправка после перезапуска использует тот же `reportId`. Переключение ID или сервера не отправляет старую очередь другому получателю. В автономном режиме сведения сохраняются локально без назначения сервера; автоматическая передача таких исторических записей при смене режима не выполняется.

Дополнительный контракт:

```http
POST /api/v1/agents/{agentId}/external-backups
Authorization: Bearer <token>
Idempotency-Key: <reportId>
Content-Type: application/json
```

Тело — `ExternalBackupReport` с полями `reportId`, `agentId`, `monitorId`, `targetServer`, `observedUtc`, `observation`, `deliveredUtc` (при отправке `null`). `observation` содержит поля `ExternalBackupObservation`; перечисления передаются строками. Сервер обязан проверить принадлежность агенту, принять запись в постоянное хранилище до ответа 2xx, дедуплицировать по агенту и `reportId` и отвергать изменённый повтор того же ID. Источник копии и уровень доказательства должны отображаться отдельно от результатов копирования самим агентом.

Клиент отправки и очередь реализованы и проверены с подменённым HTTP-транспортом. Автоматический опрос выполняется локальным фоновым агентом, с интервалом каждого источника от 15 до 86400 секунд. Статус последнего опроса сохраняется в `external-poll-status.json` и виден в окне мониторинга. Сервер мониторинга и защищённое хранение токенов подключены; для передачи результатов оставьте работающим агент или службу. Ошибки чтения источника не останавливают резервное копирование. Актуальное состояние опроса и предупреждение о превышении заданного возраста копии передаются на сервер вместе с заданием наблюдения. История хранится без автоматической очистки. Реальные `msdb`, создание и восстановление копий проверены на [локальном полном SQL Server](windows-sql-stand.md); границы этого стенда и непроверенные удалённые сценарии указаны отдельно.

Проверка скрипта:

```sh
python -m unittest discover -s tests/postgresql -v
```

Автоматический опрос использует общий замок исполнения фонового агента. Пока агент работает, ручная проверка источника через окно не выполняется, но редактирование источников и чтение истории доступны. Включение, выключение и изменение интервала применяются без перезапуска. Для внешних копий не запускается очистка по правилу N.

В окне мониторинга можно выбрать каталог PostgreSQL через диалог, отменить ручную проверку и посмотреть полный текст выбранного наблюдения. Удаление источника прекращает будущие опросы; история наблюдений, внешние резервные копии и JSON-отчёты остаются. Уже начавшийся фоновый опрос может завершиться после удаления.


### Контроль свежести копии (следующий пакет изменений)

В настройках задания включите **«Предупреждать, если успешной копии нет больше»** и укажите число часов.
Например, для ежедневного копирования можно выбрать **26 часов** — сутки и два часа на завершение копии.
Выберите конкретную базу. Для MS SQL период чтения истории должен быть не меньше указанного срока.
По умолчанию контроль выключен, в том числе у ранее созданных заданий.

После успешного опроса агент сравнивает время окончания последней успешной копии с текущим временем,
учитывая часовой пояс источника. Если срок превышен или успешных копий выбранной базы нет,
появляется предупреждение **«Нет свежей копии»**. До первого опроса предупреждение не возникает.
Ошибка чтения журнала показывается отдельно как **«Ошибка опроса»**; прежняя история сохраняется.
Выключенное задание не выдаёт предупреждение о свежести. Проверка не создаёт копии сама.

Сервер получает срок, время последней успешной копии и состояние проверки от агента.
Состояние относится к моменту передачи данных; при потере связи проверяйте также состояние агента.
Старая версия сервера продолжит принимать историю, но для отображения контроля свежести потребуется обновление.
Любой успешный тип копии считается обновлением: контроль отдельно полной копии и журнала транзакций пока не входит в эту настройку.


### MS SQL с самоподписанным сертификатом

В настройках задания копирования или наблюдения MS SQL включите **«Подключаться без проверки сертификата MS SQL»**.
Прочитайте предупреждение и нажмите **«Да»**, затем сохраните задание. При выборе **«Нет»** настройка останется выключенной.
Этот выбор сохраняется отдельно для задания и применяется также службой Windows при автоматическом выполнении.
Шифрование соединения остаётся обязательным, но подлинность сервера не проверяется: используйте режим только для известного сервера в доверенной сети.
Устанавливать его сертификат на компьютер агента в этом режиме не требуется. Для возврата к проверке снимите флажок и сохраните задание.
По умолчанию проверка сертификата включена. Настройка не отменяет проверку логина, пароля и прав доступа к базе.

### Как заполнить подключение MS SQL

1. Узнайте адрес сервера и точное имя базы у администратора или посмотрите их в SQL Server Management Studio (SSMS).
2. В поле адреса укажите, например, `SQL-SERVER`, `SQL-SERVER\SQLEXPRESS` или `192.168.1.10,1433`. Порт отделяется запятой. `localhost` означает компьютер, на котором работает агент.
3. Введите имя базы, например `Accounting`. Название задания можно выбрать произвольное, а имя базы должно совпадать с именем в MS SQL.
4. Выберите способ входа. Для Windows доступ должен быть у пользователя агента, а при автоматической работе службой — у учётной записи службы. Для входа по логину MS SQL нажмите «Задать логин и пароль MS SQL…» и сохраните данные. Пароль пользователя 1С сюда не подходит.
5. Обычно проверку сертификата оставляют включённой. Если администратор подтвердил использование самоподписанного сертификата, откройте «Сертификат и защита подключения» и при необходимости включите разрешение без проверки, подтвердив предупреждение.
6. Для наблюдения сохраните задание и нажмите «Прочитать журнал копий». Если фоновый агент или служба уже работают, они читают журнал автоматически. Успешное чтение пустого журнала не означает наличие копии.

В задании **копирования** дополнительно нужны два пути к одной папке. Например, MS SQL записывает `.bak` в `D:\SqlBackups` на своём компьютере, а агент читает этот же файл через `\\SQL-SERVER\SqlBackups`. Если сервер и агент установлены на одном компьютере, оба пути могут быть `D:\SqlBackups`. Создайте папку заранее; дайте службе MS SQL права записи, а исполнителю SP Backup — права чтения. Доступ к MS SQL и доступ к сетевой папке настраиваются отдельно. Итоговое хранилище, куда SP Backup отправляет копию, выбирается следующим шагом мастера.


### Последние копии MS SQL по типам

В подробностях задания агента и в раскрываемом разделе задания на сервере показываются последние успешные полная, дифференциальная копии и копия журнала транзакций. В таблице наблюдений вместо кодов D/I/L используются понятные названия. Времена определяются по окончанию копии с учётом часового пояса источника.

«Не обнаружена» означает отсутствие такого типа в доступной истории выбранной базы, а не ошибку копирования. Например, копии журнала транзакций могут не входить в ваш план. Неуспешная попытка не заменяет дату последней успешной копии. Общий срок свежести пока учитывает любой успешный тип; отдельные сроки по типам не настраиваются. Эти сведения не подтверждают целостность цепочки восстановления.


### Если журнал копий не читается

Сервер показывает категорию ошибки и действие: проверить сертификат, вход, права, доступность соединения или нагрузку при тайм-ауте. Если причину нельзя определить по коду драйвера, показывается ошибка чтения с предложением открыть подробности в агенте. Произвольный текст ошибки не используется для угадывания причины и не передаётся в серверный снимок.

Ошибка опроса не означает, что внешняя программа не создала копию. Прежние копии сохраняются в истории. После следующего успешного опроса категория ошибки очищается. Отсутствие свежей копии показывается отдельно, когда включён контроль срока и журнал успешно прочитан.


### Подробности текущего результата на сервере

В карточке агента состояние задания и его расшифровка относятся к одному отчёту, выбранному агентом для текущего источника. После смены подключения копии прежнего сервера остаются в истории. Даже если их даты новее, они не подменяют причину ошибки текущего источника. Поиск подробностей не ограничен первой страницей истории.

Если состояние задания уже пришло, а соответствующий подробный отчёт ещё не доставлен, панель показывает **«Подробный отчёт ещё не получен сервером»**. Это не успех доставки и не ошибка самой копии. Оставьте агент или службу работающими и обновите страницу после следующей передачи. Время результата и опроса отображается в выбранном часовом поясе сервера; сохранённые отметки времени остаются UTC.
