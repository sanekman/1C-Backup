# Результаты проверки настоящей платформы 1С

## 9 ноября 2026 года: частичная приёмка файловой базы

Пользователь выполнил изолированный сценарий на своём Windows-компьютере с платформой **8.5.1.1150** и агентом **0.2.0-alpha.34**, исходный код агента **9f4b7337f41088a4e0b312a7c0f073d439b4cc43**. Проверка выполнялась от текущего интерактивного пользователя. Она не является приёмкой более нового исходного кода или другой учётной записи службы.

Отчёт real-windows-onec: начало **2026-11-09 08:24:49 UTC**, окончание **08:39:51 UTC**. SHA-256 полученного JSON: **e93145b2e34bb11f28805ae9ba5f1f86cabe4b26294794d15d79400805a9d2ce**. В репозиторий не включаются база, архивы, рабочие профили и платформенные журналы.

| Проверка | Фактический результат |
| --- | --- |
| Создание отдельного тестового источника | Успешно при эксклюзивном чтении исходной базы. |
| Локальная закрытая база, разрешение открытой базы выключено | ZIP восстановлен побайтно; лишнего предупреждения нет. |
| Локальная закрытая база, разрешение включено | ZIP восстановлен побайтно; лишнего предупреждения нет. |
| Локальный открытый сеанс, разрешение выключено | Копирование отклонено. |
| Локальный открытый сеанс, разрешение включено | Копия создана с предупреждением; согласованность открытой базы этим не доказывается. |
| Локальная база после закрытия сеанса | ZIP восстановлен побайтно; предупреждение исчезло. |
| Закрытая база через собственную UNC-папку, разрешение выключено и включено | Обе проверки прошли с побайтным восстановлением и без лишнего предупреждения. |

Пользователь отдельно сообщил: «Копия сделалась успешно. Я лично проверил в 1С». Это подтверждение проверки копии пользователем; оно не уточняет тип архива и не подменяет отсутствующие результаты выгрузки DT.

Общий результат сценария **success: false**. Пользователь предоставил снимок PowerShell: после unc-closed-true выведено «Платформа не удерживает файл тестовой базы. Проверка открытого сеанса не состоялась». Это отсутствие подтверждённого открытого сеанса, а не ошибка создания предыдущих копий. Причина отсутствия блокировки платформой ещё не установлена. Открытый сеанс через UNC, повторная закрытая UNC-база, выгрузка DT, восстановление DT и отмена выгрузки этим отчётом **не подтверждены**. Пункты 4.1–4.2 целиком не закрыты.

Сетевая проверка использует временную папку того же Windows-компьютера. Результат не распространяется на удалённый NAS, доменный SMB-сервер и работу службы под отдельной учётной записью.

На дополнительном снимке пользователя показано окно выбора информационной базы. Само это окно не является открытым сеансом. Инструкция и подсказки сценария дополнены: нужно выбрать тестовый путь, нажать «1С:Предприятие» и дождаться данных. Проверка UNC-открытого сеанса остаётся неподтверждённой до нового результата.

## 10 ноября 2026 года: причина отказа DT

Повторный запуск с платформой **8.5.1.1150** и опубликованным агентом **alpha.34+9f4b733** выполнялся **04:52:49–04:53:12 UTC** (14:52–14:53 во Владивостоке), в режиме platform-only. Отдельная копия исходной базы создана успешно. Выгрузка DT не завершилась; до восстановления и отмены сценарий не дошёл. Доступного места было достаточно: около 123 ГиБ при требуемых 47 ГиБ.

Пользователь прочитал локальный журнал и сообщил: **«Пользователь ИБ не идентифицирован»**. Он подтвердил, что обычно выбирает пользователя 1С и вводит пароль. Опубликованный агент не передавал эти данные платформе; это установленная причина текущего отказа, а не подтверждение неисправности самой базы.

В рабочей ветке добавлены сохранение пользователя ИБ и пароля в Windows, передача через закрытый файл параметров, отключение входа Windows для DT и подсказка о причине отказа. Сценарий поддерживает -AskOneCLogin с проверкой совместимости агента до запроса пароля. Автоматические проверки хранения и передачи не заменяют запуск настоящей 1С. Приёмка DT, восстановления, данных и отмены остаётся открытой до нового отчёта пользователя с новой сборкой.

## 10 ноября 2026 года: настоящая DT-выгрузка с пользователем ИБ

Отчёт **07:24:06–07:25:38 UTC** (17:24–17:25 во Владивостоке), SHA-256 **af7c42ff1c876d49e11215ee34e446a815ec4481a40cabb137057d071ed2a9b8**: платформа **8.5.1.1150**, агент **0.1.0-dev+8cda1bd785628dab5ecd1bfb3583a9be51da6fce**, режим platform-only, текущий интерактивный пользователь Windows.

Подтверждены локальное сохранение данных пользователя ИБ, создание отдельного источника при эксклюзивном чтении и успешная непустая DT-выгрузка настоящей платформой через агент. Таким образом, исправленный вход пользователя ИБ прошёл реальную проверку. Это не подтверждает восстановление или согласованность данных в восстановленной базе.

Сценарий остановился на platform-restore, общий результат и selectedChecksPassed — false. Сам отчёт не содержит текста ошибки платформы. При проверке сценария обнаружена ошибка: каталог восстановления заполнялся копией тестовой базы с её пользователями, но /RestoreIB запускался без данных входа. Восстановление исправлено на тот же защищённый способ запуска с пользователем ИБ, что и проверка восстановленной базы. Папка восстановления отдельная; исходная рабочая база платформой не открывается. Результат нового восстановления, подтверждение данных и отмена выгрузки ещё ожидаются; пункты 4.1–4.2 целиком не закрываются.

## 10 ноября 2026 года: проверка формата входа на готовой копии

Отчёт real-windows-onec-login-probe **08:26:26–08:27:47 UTC** (18:26–18:27 во Владивостоке), SHA-256 **e2cb6c45330a58d4f7559e003559a810788c6d3c33126827acef9c45d5b10d9a**. Настоящая платформа **8.5.1.1150**, агент **8cda1bd**, готовая тестовая копия: рабочая база не открывалась и повторная полная копия не создавалась.

Имя и пароль после обратного чтения из Windows Vault совпали посимвольно с введёнными данными. На одной и той же тестовой базе одна и та же пара прошла выгрузку конфигурации через файл параметров ANSI (кодовая страница 1251), UTF-8 с BOM и UTF-16 LE с BOM. **UTF-8 без BOM отклонён с кодом 1 и сообщением «Пользователь ИБ не идентифицирован».** Это проверка настоящей 1С, отдельно от контроллера с имитатором платформы.

Агент ранее выбирал кодировку по GetACP и не записывал явную метку: при кодовой странице процесса 65001 получался отвергнутый UTF-8 без BOM. Кодовая страница именно процесса агента в пользовательском отчёте не измерялась. Для устранения зависимости файл параметров теперь всегда записывается в проверенном UTF-8 с BOM; тот же формат используется в сценарии восстановления. Проверки файла включают кириллицу и символ за пределами BMP в пароле, а также очистку при успехе, ошибке запуска, ошибке платформы и отмене.

Этот отчёт подтверждает вход и выгрузку конфигурации в трёх форматах. Выгрузку DT обновлённым агентом, восстановление DT, данные восстановленной базы и отмену ещё нужно подтвердить новым запуском; вся приёмка 4.1–4.2 не объявляется завершённой.
