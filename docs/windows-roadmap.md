# Дорожная карта SP Backup: Windows → beta → развитие

Обновлено: 12 ноября 2026 года.

Цель ближайшего цикла — подготовить проверяемый Windows-кандидат для beta,
зафиксировать фактическую совместимость и ограничения. Сначала Windows-агент
и Windows-сервер, затем развитие Linux. Даты этапов назначаются после оценки
доступных стендов; календарных обещаний эта карта не даёт.

Эта редакция заменяет прежний рабочий план, сохраняя номера этапов и подблоков.
[Предыдущая полная редакция](https://github.com/sanekman/1C-Backup/blob/733b1de87b2ca7260ba8c6234ae8e3d1af49fd50/docs/windows-roadmap.md)
содержит подробные критерии этапов 1–6. Новая редакция сама по себе не означает
новой приёмки или публикации.

## Текущее положение

- Рабочая ветка: `feature/local-backup-agent`. PR №2 остаётся черновиком.
- Последние опубликованные версии по сохранённым отчётам: Windows
  **v0.2.0-alpha.35**, Server **v0.1.0-preview.9**.
  [Публикация alpha.35, SHA-256 и проверка обновления](windows-alpha35-publication.md).
  [Публикация Server preview.9, манифест и проверки](server-preview9-publication.md).
- Этапы **1–3 завершены**; **5 завершён для поддерживаемых файловых серверных
  планов**, **6 завершён для штатной Windows-установки**.
- Этап **4 принят частично**. Пропуски 1С и отсутствие удалённого SQL-стенда
  сохраняются; они не превращаются в успешные проверки.
- Этап **7 в работе**: ядро и WPF проверены на Server 2022/2025,
  служба прошла 27+2 сценария на каждой ОС. Установщик **6f7c65a** принят:
  установка 9/9, установленный WPF, обновление с alpha.25 9/9 на обеих ОС.
  Основной кандидат и SHA-256 зафиксированы; подпись и внешние стенды открыты.
  [Текущие результаты и ограничения](windows-stage7-acceptance.md).
- Изменения и кандидаты в ветке не считаются новым выпуском.
- `AGENTS.md` задаёт правила работы; эта карта — приоритеты и состояние.
  Отчёты приёмки содержат исходники, окружение и доказательства.

## Статусы и правила перехода

| Статус | Значение |
| --- | --- |
| Запланировано | Работа описана, выполнение не подтверждено. |
| В работе | Текущий незавершённый блок. |
| В коде | Реализовано, но пакет ещё не принят. |
| Завершено | Критерии приняты в явно описанных границах с доказательствами. |
| Ожидает стенда | Проверка не выполнена из-за отсутствия окружения. |
| Пропущено | Проверка отложена решением пользователя; результат не подтверждён. |
| Доработка | Расширение существующей функции, а не создание её заново. |
| Стенд | Нужна реальная эксплуатационная проверка. |
| Опубликовано | Выпуск действительно доступен, указан его тег. |

Пройденный сценарий внутри частично принятого этапа не закрывает весь этап.
Проверка доступа, создание копии, проверка целостности и пробное восстановление
фиксируются раздельно. Реализованный тест не считается выполненным.

## 1. Завершить накопленный пакет интерфейса

**Завершено: 1.1–1.6.** Компактное окно, отчёты проверок, действия с отчётом,
ручные запросы, прогноз расписания и приёмка установленного интерфейса.
[Доказательства и границы этапа 1](windows-stage1-acceptance.md).

Далее сохраняем принятые свойства: WPF 900×580, доступные основные действия,
прокрутка длинных подробностей и отсутствие ложных сообщений об успехе.
Повторная полная переработка интерфейса в ближайший цикл не входит.

## 2. Упростить первичную настройку

**Завершено: 2.1–2.5.** Выбор источника, подключение, NAS/UNC, проверка
источника фактической службой и инструкция первого запуска.
[Доказательства и границы этапа 2](windows-stage2-acceptance.md).

Следующая проверка — независимое прохождение инструкции в 7.3.
Доступ пользователя из Проводника не считается проверкой доступа службы.

## 3. Довести надёжность длительной работы

**Завершено: 3.1–3.6.** Большие задания, независимые назначения, очередь,
перезапуск и загрузки Windows, инкрементные цепочки и восстановление файлов.
[Доказательства и границы этапа 3](windows-stage3-acceptance.md).

Принятые реальные SMB/NTFS/VHD и смена пользователей не означают приёмку
удалённого SQL, доменного SMB или всей матрицы ОС. Повторные полные копии
без новой причины не выполнять.

## 4. Завершить работу с 1С и SQL на Windows

**Частично принято.** Сохранённые результаты не обнуляются.
Решение пользователя от 11 ноября пропустить оставшиеся проверки 1С
не пересматривается этой картой и не блокирует продолжение разработки.
[Результаты 1С](windows-onec-results.md), [SQL-стенд](windows-sql-stand.md).

| Подблок | Состояние | Дальнейшее действие и критерий |
| --- | --- | --- |
| 4.1.1. Локальная файловая 1С | Пройдено на alpha.34: закрытые и открытые сеансы, отказ/предупреждение, повторное закрытие. | Сохранить результат. Повторять при изменении ZIP-механизма или по обоснованному объёму 7.5. |
| 4.1.2. Файловая 1С через UNC | **Пропущено:** закрытая база принята, открытый сеанс не подтверждён. | Возвращаться при отдельном решении: открыть именно UNC-базу в платформе и проверить отказ и разрешённое копирование. |

| 4.3.1. Полный локальный MS SQL | Пройдено: Express, два способа входа, TLS, создание/проверка/восстановление и msdb. | Сохранить доказательства; повторять при изменении SQL-механизма. |

LocalDB не подменяет результат. |
| 4.4.1. PostgreSQL под службой | Пройдено: SCRAM, делегированный пароль, TLS/отказы, восстановление подключения и данных. | Сохранить отчёты действующей службы; не расширять вывод на непроверенные среды. |

| 4.5.2. Агент → сервер → панель | Пройдено: передача, изоляция, подробности текущего отчёта, пояс и Chromium. | Сохранять [границы приёмки](windows-observation-acceptance.md). Наблюдение не доказывает возможность восстановления. |

Просмотр SQL Full/Diff/Log не означает, что агент сам создаёт
дифференциальные копии и журнал транзакций.

## 5. Довести центральное управление

**Завершено: 5.1–5.5 для поддерживаемых файловых серверных планов.**
[Доказательства и границы этапа 5](windows-stage5-acceptance.md).

Приняты сводка проблем, ревизии планов, локальные защищённые привязки,
удалённые ручные команды и исполнение принятого плана без связи.
Серверный мастер поддерживает файлы/папки и ZIP файловой 1С,
локальные/UNC-назначения. SQL, DT, FTP, WebDAV и Google Drive не объявляются
поддерживаемыми серверным мастером на основании локальных возможностей агента.

Различать сохранённую, принятую и исполненную ревизии. При недоступном
сервере принятое расписание работает; новая удалённая команда не получает
ложное подтверждение старта. Повтор команды не создаёт лишнюю копию.

## 6. Эксплуатация Windows-сервера

**Завершено: 6.1–6.4 в границах штатной Windows-установки.**

Приняты установка, холодная копия/возврат, обновление с возвратом программы

Автоматическая установка не заменяет прохождение новичком в 7.3.

## 7. Приёмка Windows и переход к beta

**В работе, beta не объявляется.** На Server 2022/2025 проверены ядро,
WPF и служба, в том числе изменение локальных заданий и пароля архива
без перезапуска службы. Кнопки FTP и пароля архива исправлены; из новых
имён ZIP файловой 1С убраны идентификатор и `.1CD`. После исправления встроенной
справки оба прогона упаковки **43015632331 / 43015636151** прошли: служба,
установка, установленный интерфейс и обновление с alpha.25. Основной
неподписанный кандидат — **6f7c65a**, версия **0.1.0-dev**.
[Артефакты, SHA-256 и границы](windows-stage7-acceptance.md).

По отдельной команде пользователя опубликован **v0.2.0-alpha.35**, исходник
**0da787d**. Теговая сборка заново прошла штатные проверки Windows/Linux,
установки и обновления на Server 2025; проверено скачивание alpha.35
для текущей alpha.34 на runtime 10.0.13. [Отчёт публикации](windows-alpha35-publication.md).
Предыдущие выпуски сохранены. По отдельной команде опубликован **Server preview.9**:
Windows/Linux 168+1, установка 21/21, снимок 14/14, обновление/возврат 16/16,
Compose 14/14. [Отчёт публикации](server-preview9-publication.md).

### 7.1. Фактическая матрица Windows

1. Составить таблицу: ОС/сборка, роль агента или сервера, зависимости,
   проверенный коммит/пакет, результат, ограничения и ссылка на отчёт.
2. Кандидаты для проверки: Windows 11 и Windows Server
   2016/2019/2022/2025 с Desktop Experience. Проверить совместимость выбранного
   runtime и зависимостей; это целевые стенды, а не обещание поддержки.
3. Для каждой заявляемой системы проверить установку, запуск службы,
   основное копирование/восстановление, перезапуск и затронутый путь обновления.
4. Недоступные стенды оставить «ожидает стенда»; не переносить результат
   `windows-latest` на другие ОС.

**Готовность:** опубликована матрица с доказательствами. Непроверенные системы
отделены от поддерживаемых. Отсутствие старого стенда не исправляется
неподтверждённым обещанием совместимости.

### 7.2. Пользователи, UAC, домен и NAS

Проверить обычного пользователя/UAC, действующего пользователя службы,
смену учётной записи, повторный вход, перезагрузку и доменные SMB-сценарии.
Использовать результаты этапа 3 там, где окружение и поведение не изменились.
Удалённый SQL остаётся отдельной строкой 4.3.2.

**Готовность:** явно известны исполнитель и его права; разрешённые и запрещённые
ресурсы дают ожидаемый результат, секреты не раскрываются и не теряются.
Для домена нужен настоящий отдельный стенд.

### 7.3. Первое использование и понятность интерфейса

Пройти без устных пояснений разработчика:
чистая установка → первое задание → проверка источника/хранилищ нужным
исполнителем → первая копия → пробное восстановление → работа после
закрытия окна/перезагрузки → ошибка и её устранение → обновление → удаление.

Для панели: подключение агента → поддерживаемое серверное задание →
публикация и принятие ревизии → удалённая команда → результат каждого
назначения. При потере связи проверить объяснение устаревших данных.

Расширить уже существующие браузерные проверки, если в полном сценарии
найдены пробелы: светлая/тёмная тема, узкое окно, длинные имена/пути,
клавиатура и фокус. Для WPF сохранить 900×580. HTTP-тесты оставить
для логики; они не заменяют просмотр и действия в браузере.

**Готовность:** сохранён протокол прохождения и найденных проблем;
блокирующие проблемы исправлены и перепроверены. Руководство соответствует
проверенному кандидату, опубликованная версия обозначена отдельно.

### 7.4. Подпись установщиков

Проверить имеющиеся средства подписи, подготовить сертификат издателя
и проверку подписи собранных пакетов. Не запрашивать ключи в чате.
Если сертификата нет, записать внешний блокер; готовность не объявлять.

**Готовность:** действующий сертификат, проверенный издатель и подпись
распространяемого пакета. До этого пакеты явно обозначаются неподписанными.
Изменение этого условия для beta требует отдельного решения пользователя.

### 7.5. Общая приёмка и решение о beta

- Выбрать один кандидат и зафиксировать коммит, версии и SHA-256 пакетов.
- Выполнить относящиеся к накопленным изменениям проверки ядра, WPF,
  службы, сервера, установки/обновления и восстановления.
- Использовать прежние доказательства для неизменённых блоков; новые
  изменения и обнаруженные сбои требуют профильной повторной проверки.
- Проверить отсутствие блокирующих ошибок потери данных, восстановления,
  остановки очереди, повторного выполнения и раскрытия секретов.
- Свести матрицу 7.1, пользователей 7.2, сценарии 7.3, подпись 7.4
  и открытые ограничения этапа 4 в единый отчёт.
- Подготовить заметки выпуска, инструкции установки/возврата и перечень
  фактически поддерживаемых сценариев. Не приписывать кандидату новые прогоны.

**Готовность:** доказательства соответствуют кандидату либо явно обосновано
использование прежних результатов; нет блокирующих ошибок; все пропуски
и неподтверждённые сценарии видны. Приёмка, решение о составе beta
и публикация — отдельные события. Эта карта не разрешает автоматически
публиковать beta, пропускать подпись или закрывать незавершённые проверки.

## 8. Доработки после основной приёмки Windows

Это предложения для следующего цикла, а не новые обязательные блокеры beta.
Начинать по выбранному приоритету и результатам реального использования.

| Направление | Содержание | Проверяемый результат |
| --- | --- | --- |
| Обзор проблем | Оценить краткую сводку проблем у каждого агента на главной странице. Переиспользовать существующий раздел «Проблемы». | Пользователь быстрее находит задание и причину; связь не воспринимается как успех копии. |
| Единый язык интерфейса | Согласовать статусы, названия действий и смысл цветов WPF/веба на основе существующих ресурсов. | Одинаковое состояние объясняется одинаково в обеих темах и интерфейсах. |
| Повторяемая браузерная приёмка | Свести уже имеющиеся проверки и при необходимости автоматизировать недостающие пользовательские переходы. | Отчёт и снимки воспроизводимы; не создаётся второй дублирующий набор. |
| Документация | Убрать противоречащие текущему состоянию формулировки из общего/серверного планов, сохранить ссылки на исторические решения. | Текущая карта — одна точка входа, отчёты сохраняют доказательства. |

## 9. Последующее развитие

- **Telegram/MAX:** отдельная задача по принятому решению; не смешивать
  с завершением Windows-пакета.
- **Linux:** после основных Windows-блоков — обновление, восстановление,
  systemd и затем дополнительные архитектуры. Сохранять опубликованные
  пакеты и проверки совместимости общих библиотек.
  По отдельному запросу пользователя добавлена команда обновления штатного
  серверного Docker Compose: `./deploy/server/update.sh`. Приняты 14 сценариев
  обновления/возврата и 28 профильных Python-проверок.
  [Инструкция и доказательства](server-container-update.md).
  Это не приёмка нативного Linux-установщика, systemd или другой архитектуры.
  Отдельно добавлено обновление LXC из мастера Proxmox: `--update --id`.
  На Debian 13 подтверждены переход preview.8 → preview.9, возврат и сохранение
  доступа. После отказа на CT 107 исправлено посимвольное сравнение
  ConnectionString: проверяются параметры и идентичность локального кластера,
  конфигурация не переписывается. На b65f317 приняты 8 сценариев обновления,
  25 профильных Python-проверок (прогон 43132304502); локально 37/37.
  [Команда и доказательства](server-proxmox.md#6-обновить-существующий-lxc).
  Пользовательский CT 107 остановился на предварительной проверке настроек;
  его успешное обновление и возврат с настоящими pct/systemd ещё не подтверждены.
- **Новые механизмы:** VSS, образ системы, собственные SQL-дифференциальные
  копии и журнал — отдельные проекты с критериями восстановления.
- Остальные платформы и новые облачные хранилища оценивать отдельно,
  без расширения обещаний текущего выпуска.

## Порядок ближайшей работы

1. Составить матрицу 7.1 и отметить имеющиеся доказательства/недоступные стенды.
2. Выполнить доступные проверки 7.1–7.2 и прохождение новичка 7.3.
   Подготовку подписи 7.4 можно вести независимо.
3. Исправить найденные проблемы связанными пакетами; обновить инструкции.
4. Выполнить 7.5 и подготовить конкретный кандидат с известными ограничениями.
5. Публиковать выбранный выпуск только по команде пользователя.
6. Затем выбирать направления 8–9. К пропущенным проверкам 1С возвращаться
   по отдельному решению, к удалённому SQL — при появлении стенда.

Потеря данных, невозможность восстановления или остановка очереди имеют
приоритет перед визуальными улучшениями.

## Проверки, история и откат

- Несколько связанных изменений → одна сборка и профильные проверки пакета.
  Полный Windows CI — для накопленного пакета и перед выпуском; зелёные проверки
  не повторять без новой причины и не ослаблять при сбое.
- Не отправлять каждый маленький коммит отдельно, если это запускает
  одинаковые тяжёлые сборки.
- Различать «в коде», «собирается», «проверено» и «опубликовано».
- Старые теги, дистрибутивы и файлы выпусков не заменять.
  PR №2 остаётся черновиком до отдельного решения о завершении ветки.
- Изменение этой карты оформить отдельным коммитом. Для возврата предыдущего
  плана использовать `git revert <коммит-новой-дорожной-карты>`;
  принудительная отправка и переписывание истории не нужны.
