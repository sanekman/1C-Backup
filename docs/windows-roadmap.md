# Дорожная карта SP Backup: завершение Windows

Обновлено: 8 ноября 2026 года.

Сначала завершаем Windows-агент и Windows-сервер. Затем расширяем Linux. Изменения объединяем в заметные пакеты; тесты запускаем после связанных доработок, а не после каждого поля или подписи.

## Отправная точка

- Последние опубликованные версии: **Windows v0.2.0-alpha.34** и **Server v0.1.0-preview.8**.
- Рабочая ветка: `feature/local-backup-agent`, PR №2 остаётся черновиком.
- В ветке накоплены новые отчёты проверок, экспорт TXT, повтор проверки, ручная очередь и прогноз расписания. Это **ещё не новый выпуск**.
- Общая Windows-проверка обнаружила ошибки компоновки. Исправлено размещение длинного отчёта и возвращена подсказка включения исполнителя. **Остаётся исправить обрезание строк заданий в компактном окне**. Полный пакет ещё не принят.
- Установка, служба, расписание, файловые/SQL-копии, файловые инкрементные цепочки и серверный мониторинг уже реализованы. Дальнейшие пункты включают доработку и эксплуатационную проверку; они не означают, что эти функции отсутствуют.

Статусы: **в работе** — текущий незавершённый блок; **в коде** — реализовано, но пакет ещё не принят; **доработка** — расширение существующей функции; **стенд** — требуется реальная эксплуатационная проверка.

## 1. Завершить накопленный пакет интерфейса

Цель: понятное управление без скрытых действий и ложных сообщений об успехе.

| Подблок | Состояние и работа | Критерий завершения |
| --- | --- | --- |
| 1.1. Компактное окно | **В работе.** Исправить распределение высоты между таблицей, кнопками, прогрессом и отчётами. | В минимальном размере видны строки заданий и основные действия; длинный отчёт читается прокруткой. Существующие проверки видимости проходят без ослабления. |
| 1.2. Результаты проверок | **В коде.** Пользователь, время, длительность, успех/замечание/ошибка/отмена; различия окна и службы. | У всех трёх проверок — источника, хранилищ и копий — понятный итог. Отмена и ошибка получения ответа не выдаются за проверенный доступ. |
| 1.3. Работа с отчётом | **В коде.** Копирование, TXT, очистка, повтор, переход к параметрам, устаревание после изменения задания. | Существующий файл не заменяется; новый результат не содержит старых сообщений; очистка не меняет задания, историю и копии. |
| 1.4. Ручные запуски | **В коде.** Список принятых запросов, восстановление после открытия окна, ошибки подтверждения. | Повторный запуск того же запроса заблокирован; другие задания независимы. Интерфейс не обещает порядок и полноту очереди расписания. |
| 1.5. Прогноз расписания | **В коде, частично проверено.** Три ближайших времени, пояс, ручное/выключенное/стартовое задание, состояние исполнителя. | Прогноз соответствует сохранённому плану; выключенный или устаревший исполнитель не выглядит работающим. Просмотр ничего не запускает и не сохраняет. |
| 1.6. Приёмка пакета | После 1.1–1.5 — один общий Windows-прогон и исправления найденных ошибок. | Проходят новые UI-сценарии, компактная геометрия, очередь и служба. Просмотрены актуальные снимки; результаты относятся к последнему коммиту. |

**Выход блока:** один проверенный пакет удобства Windows, готовый к включению в следующий выпуск.

## 2. Упростить первичную настройку

Цель: новый пользователь самостоятельно создаёт задание и понимает, что нужно исправить.

| Подблок | Следующее действие | Критерий завершения |
| --- | --- | --- |
| 2.1. Выбор источника | Понятные примеры для папки, файловой 1С, MS SQL, PostgreSQL и WebDAV; проверка частых ошибочных значений. | Пользователь различает имя задания, имя базы, путь к файлам и адрес сервера. |
| 2.2. Подключение к базе | Согласовать ввод логина, сертификаты, проверку подключения и пояснения прав. Базовая форма MS SQL уже доработана в alpha.34. | Успешный вход не обозначается как подтверждение прав копирования или восстановления; понятно, какой пользователь подключается. |
| 2.3. NAS и сетевая папка | Связать UNC-путь, отдельный сетевой логин и фактическую учётную запись исполнителя в одном понятном сценарии. | Доступ из Проводника не принимается за доступ службы. Пользователь может выполнить проверку через нужного исполнителя. |
| 2.4. Проверка источника службой | Сейчас проверка источника выполняется из окна. Отдельно реализовать или предоставить равнозначный ясный сценарий проверки под службой. | Результат привязан к реальному исполнителю; нет сообщения «доступно службе» по результату окна. |
| 2.5. Первый запуск | Сделать понятным переход: сохранить → проверить → создать пробную копию → найти результат → проверить восстановление. | Сценарий выполняется по инструкции без знания внутренних файлов программы. |

**Зависимость:** сначала принять интерфейс блока 1; использовать его отчёты и действия, не создавать второй параллельный интерфейс диагностики.

## 3. Довести надёжность длительной работы

Цель: ошибки отдельных файлов, заданий и назначений не уничтожают весь результат и не останавливают остальные задания.

| Подблок | Что проверить или доработать | Критерий завершения |
| --- | --- | --- |
| 3.1. Большие файловые задания | Долгое перечисление, занятые/исчезнувшие файлы, недоступные подпапки, повторные попытки, отмена. | Доступные данные сохраняются, пропуски перечислены, попытки ограничены; задание приходит к итоговому состоянию. |
| 3.2. Сбой назначения | Обрыв NAS, потеря доступа, квота, заполнение диска и повторное подключение. | Остальные назначения проверяются/обрабатываются независимо. Прежние архивы не удаляются ради неудачной доставки. |
| 3.3. Очередь и перезапуск | Ошибка/предупреждение первого задания, остановка службы, повторное открытие окна, потерянное подтверждение. | Следующие задания продолжаются. Завершённая копия не повторяется только из-за ошибки чтения подтверждения. |
| 3.4. Перезагрузка и вход | Реальная перезагрузка, запуск до входа, автозапуск пользователя, смена пользователя службы. | Однозначно известны исполнитель, план и допустимые повторы. Расписание не зависит от открытого окна при работе службы. |
| 3.5. Полные и инкрементные копии | День полной копии, пропущенный день, неполный результат и хранение зависимостей. | Ошибка инкремента не запускает незапланированную полную копию; доступная цепочка остаётся восстанавливаемой, предупреждения видимы. |
| 3.6. Восстановление файлов | Полная/инкрементная цепочка, повреждение или отсутствие архива, восстановление в отдельную папку. | Состав и содержимое сверены с ожидаемыми; повреждение обнаруживается до объявления успеха; исходник не затирается. |

**Состояние:** многие механизмы уже реализованы и покрыты тестами. Блок закрывается реальными сценариями, а не повторной реализацией работающего кода.

## 4. Завершить работу с 1С и SQL на Windows

| Подблок | Что требуется | Критерий завершения |
| --- | --- | --- |
| 4.1. Файловая 1С | Реальные закрытые и открытые сеансы платформы, локальный диск и UNC. | Без разрешения открытая база не копируется как согласованная; предупреждение появляется по фактической ситуации. Проверено восстановление. |
| 4.2. Выгрузка 1С | Установленная платформа, длительная выгрузка, завершение с ошибкой, отмена. | Успех подтверждается результатом выгрузки; не остаются чужие блокировки; отмена даёт понятный итог. |
| 4.3. MS SQL | Удалённый сервер со смешанным режимом, Windows/SQL-вход, сертификаты и служба. | Проверены вход, создание .bak, доставка, проверка и восстановление в тестовую базу. LocalDB не подменяет этот стенд. |
| 4.4. PostgreSQL | Windows-служба, пароль, TLS, совместимость утилит, восстановление дампа. | Проверены правильные и ошибочные параметры, доступ службы и восстановление данных. |
| 4.5. Наблюдение внешних копий | Свежесть, типы MS SQL, ошибки опроса, смена базы/подключения, отсутствие истории. | Не путаются успех чтения журнала и наличие пригодной копии; старые результаты не маскируют состояние нового источника. |

**Граница возможностей:** просмотр типов SQL-копий не означает создание дифференциальных копий и журнала самим агентом. Наблюдение не заменяет тестовое восстановление.

## 5. Довести центральное управление

| Подблок | Следующее действие | Критерий завершения |
| --- | --- | --- |
| 5.1. Сводка проблем | Улучшить поиск агентов без связи, ошибок, неполных и просроченных копий по папкам. | Понятно, какой агент/задание требует действий и почему. |
| 5.2. Серверные планы | Довести назначение поддерживаемых заданий, ревизии, отклонение некорректного плана и работу без связи. | Агент исполняет принятую ревизию; новый неверный план не уничтожает рабочий. Часть этого механизма уже реализована. |
| 5.3. Защищённые подключения | Расширить серверное управление источниками и назначениями с секретами на агенте. | Секреты не попадают в обычные JSON, историю панели или экспорт; понятно, где нужно задать доступ. |
| 5.4. Удалённый ручной запуск | Подтверждение принятия команды, состояние выполнения, отказ/истечение и защита от повтора. | Повторная доставка команды не создаёт лишнюю копию; отсутствие связи не выглядит успешным запуском. |
| 5.5. Управление без постоянной связи | Обрыв и восстановление связи, накопление результатов, повторная доставка. | История не теряется и не дублируется; изменение плана и результат запуска различаются. |

**Зависимость:** опираться на проверенные локальные очередь и идентификаторы из блока 3.

## Отдельные направления

- **Telegram/MAX:** отдельная задача по принятому решению. Не смешивать с завершением Windows-пакета.
- **Linux:** после основных Windows-блоков — удобство обновления, восстановление, systemd и дополнительные архитектуры. Уже опубликованные Linux-пакеты сохраняются.
- **Новые механизмы копирования:** VSS, образ системы, собственное создание SQL-дифференциальных копий и журнала — отдельные проекты с отдельной проверкой восстановления.

## Порядок работы и выпусков

1. Закрыть **1.1–1.6**: текущая компоновка, затем оставшиеся сценарии нового интерфейса.
2. Собрать пакет **2.1–2.5**: первая настройка и проверки доступа.
3. Закрывать **3.1–3.6** вместе с нужными стендами **4.1–4.5**.
4. Развивать серверное управление **5.1–5.5** и эксплуатацию **6.1–6.4** проверяемыми пакетами.
5. Выполнить общую приёмку **7.1–7.5** перед объявлением beta.

Приоритет можно менять по реальным ошибкам пользователей: проблема потери данных, восстановления или остановки очереди идёт раньше улучшения интерфейса.

### Как сократить повторные проверки

- Сначала несколько связанных изменений с критериями завершения, затем одна сборка и профильные тесты пакета.
- Не повторять успешные проверки без новых изменений или обнаруженной проблемы.
- Полный Windows CI — для накопленного пакета и перед выпуском. После реального сбоя исправлять причину; проверку не ослаблять ради зелёного результата.
- Не отправлять каждый маленький локальный коммит отдельно, если это запускает одинаковые тяжёлые сборки.
- В отчёте отделять «написано», «собирается», «проверено на Windows» и «опубликовано».

Новый выпуск создаётся после приёмки выбранного пакета и команды на публикацию. Старые теги, дистрибутивы и файлы выпусков не заменяются. PR №2 остаётся черновиком до отдельного решения о завершении ветки.
