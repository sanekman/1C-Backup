# Подготовка исполнения серверных заданий в Windows-агенте

Выпуски alpha.29 и server preview.4 предоставляют автономное копирование и мониторинг. Сервер умеет публиковать ограниченную файловую конфигурацию через административный API и принимать подтверждение её проверки и сохранения. Это ещё не включение управляемого исполнения в службе Windows.

## Единый источник заданий

После alpha.29 добавлен интерфейс `IBackupJobSource`: диспетчер расписания и ручного исполнения, а также обработчик проверки хранилищ могут получать задания из одного источника. Прежний `JobStore` сохраняет автономное поведение и совместимый конструктор диспетчера.

`AgentExecutionJobSource` привязан к сохранённым настройкам режима и подключения на время жизни исполнителя. Для изменения режима или подключения потребуется остановка и новый запуск хоста. Он читает только эффективные задания `AgentConfiguration`: в автономном режиме — локальные, в серверном — проверенный кэш именно этого агента и HTTPS-адреса. Отсутствующий или чужой кэш возвращает пустой набор; повреждённый кэш вызывает ошибку. Подстановка локальных заданий в серверном режиме запрещена.

`GetSnapshotAsync` читает ревизию и задания одним снимком. Список заданий, дополнительные времена и назначения доступны только для чтения. Новая ревизия влияет на последующее чтение; уже переданный исполнителю снимок не меняется. Один диспетчер удерживает общий шлюз исполнения для расписания и ручного запуска. Задание с ручным расписанием по-прежнему можно запустить вручную.

Конструктор диспетчера для произвольного источника требует отдельный путь журнала запусков при загрузке системы. При подключении серверного режима хост должен отделить этот журнал от автономного и от других серверных подключений: совпадающие ID заданий не должны переносить отметки запуска между режимами.

## Проверено в библиотеке

- Отсутствующий/чужой/повреждённый серверный кэш не запускает локальное задание с тем же ID.
- Ревизия соответствует заданиям при параллельной публикации; вложенные списки снимка нельзя изменить.
- Смена ревизии во время копирования сохраняет начатый снимок; следующий ручной запуск получает новую ревизию и ждёт общего шлюза. Пустая ревизия удаляет серверные задания из последующих чтений.
- После перезапуска без сетевого адаптера серверное расписание из сохранённого кэша доходит до настоящего создания ZIP файловой базы 1С, каталога и истории. Локальные задания не перезаписываются.
- Проверка хранилища использует назначение серверного задания, даже когда локальное задание имеет тот же ID.

Это проверки библиотеки и файлового архива. Они не являются прогоном настоящей платформы 1С, SCM или Hyper-V с серверным режимом.

## Что требуется до включения в службе

Подготовлен адаптер `AgentApiClient(ServerMonitoringSettings, IFtpCredentialStore)`: он использует сохранённое подключение мониторинга и тот же Windows Vault или делегированный кэш службы. Секрет читается заново перед запросом, поэтому восстановление доступа не требует пересоздания клиента. Токен не записывается в настройки или серверный кэш. Адрес с префиксом API, ID агента и ссылка на учётные данные проверяются до чтения секрета; другое подключение требует нового адаптера.

Мониторинг и API используют общую HTTPS-политику: системное доверие либо точный SHA-256 сертификата из подключения. Отпечаток не отменяет проверку имени и срока действия; перенаправления запрещены. Неверный формат токена отклоняется до отправки HTTP. Ошибка адаптера учётных данных, включая отмену, не переносит его сообщение или вложенное исключение в диагностику.

Настоящие HTTPS-проверки охватывают верный/неверный отпечаток, отсутствие системного доверия, чужое имя, просроченный и ещё не действующий сертификат, перенаправление. Интеграция с HTTPS/PostgreSQL проверяет конфигурацию, подтверждения, heartbeat, пересоздание клиента, отказ с сохранением кэша и восстановление токена. Это ещё не проверка этого адаптера под учётной записью настоящей Windows-службы.

1. Подключить подготовленный адаптер и экспорт токена к запуску реального хоста под выбранной учётной записью Windows-службы.
2. Подключить единый источник ко всем путям реального хоста: расписанию, ручной очереди, проверке хранилищ и восстановлению после сбоя. Сохранить единственного владельца исполнителя и отдельный журнал запуска при загрузке для каждого подключения.
3. Запускать синхронизацию с ограничением времени независимо от расписания; показывать режим, принятую ревизию, готовность исполнения и ошибку связи отдельно. Первая связь без кэша не должна запускать задания, офлайн должен сохранять последний принятый план.
4. Сделать понятный режим просмотра серверных заданий в Windows-интерфейсе; запретить их локальное редактирование и менять режим только при остановленном исполнителе.
5. Проверить настоящий Windows-хост/SCM с HTTPS/PostgreSQL: первое подключение, новые и ошибочные ревизии, ручной запуск, офлайн, перезапуск, сохранность автономного профиля и отчётов.

До завершения этих шагов `LocalAgentHost` продолжает отклонять Managed, а список возможностей не объявляет `managed-execution-v1`. Подтверждение конфигурации означает проверку и сохранение, а не выполненную резервную копию. Веб-мастер и расширение файлового контракта остаются отдельными следующими этапами.
