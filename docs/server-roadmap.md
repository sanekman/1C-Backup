# Начальная дорожная карта сервера SP Backup

Статус: опубликован server-v0.1.0-preview.4 с установщиком Windows, PostgreSQL, HTTPS, службами и панелью мониторинга. Работают приглашения, регистрация / отзыв агентского токена, приём результатов, прогресс, история и сведения о неполных копиях. Подключение описано в [server-start.md](server-start.md). Следующий этап — серверное редактирование заданий и управляемое копирование. Цель первой версии — видеть состояние Windows-агентов, результаты резервного копирования и менять их задания через единый интерфейс. Сервер должен работать как приложение или служба Windows, в Linux-контейнере и на Linux через systemd. Поддержка macOS рассматривается после этих вариантов.

Подробные правила мониторинга и применения настроек уже описаны в [server-management.md](server-management.md), существующий клиентский контракт — в [agent-api.md](agent-api.md). Эта карта задаёт последовательность реализации и критерии готовности.

Приоритет разработки — завершить Windows-агент и Windows-сервер по [списку готовности Windows](windows-readiness.md). Новые Linux-возможности и нативный systemd идут после этого; существующие выпуски не удаляются и не заменяются. Проверки общих библиотек на Linux продолжаются как контроль совместимости.

## 1. Общая архитектура

Предлагаемая основа — C# / .NET 10 LTS, ASP.NET Core, веб-интерфейс на Blazor и PostgreSQL для постоянных данных. Это сохраняет основной стек проекта и позволяет использовать один серверный код на разных ОС. Серверный интерфейс открывается в браузере; на Windows небольшой запускатель открывает панель и показывает состояние сервера. Отдельный WPF-интерфейс сервера не требуется.

Первый сервер — одно приложение и одна база данных. API, веб-панель, приём отчётов и обработка уведомлений разделены внутри проекта, но разворачиваются вместе. Отдельные микросервисы и брокер сообщений на начальном этапе не нужны.

| Компонент | Ответственность |
| --- | --- |
| Windows-агент | Создание, архивация, шифрование, доставка и проверка копий; расписание; локальные секреты; очередь отчётов. |
| Сервер | Регистрация агентов, назначение настроек, история, мониторинг, команды, права доступа и аудит. |
| Веб-панель | Компактный список проблем, карточки агентов, мастер задания, история и настройка сервера. |
| PostgreSQL | Пользователи, агенты, ревизии, отчёты запусков и назначений, внешние SQL-наблюдения, аудит; позднее — команды и уведомления. |

Агент обращается к серверу по исходящему HTTPS. Файлы копий идут непосредственно в выбранные хранилища; сервер получает сведения о результате. ОС сервера не ограничивает типы резервного копирования Windows-агента. Работа сервера на Linux или macOS сама по себе не создаёт Linux- или macOS-агент.

Для первой версии PostgreSQL — единственный поддерживаемый провайдер базы, чтобы одинаково проверять транзакции, миграции и повторную доставку отчётов на всех платформах. Контейнерный комплект включает отдельный контейнер PostgreSQL; нативные установки подключаются к локальному или внешнему PostgreSQL. Windows-комплект должен явно объяснять этот шаг настройки. SQLite как вариант установки без отдельной СУБД можно оценить позднее; в начальный объём он не входит.

## 2. Варианты развёртывания

| Вариант | Начальный комплект | План поддержки |
| --- | --- | --- |
| Windows x64 | ZIP с собственным .NET runtime, затем установщик; запуск в консоли или как Windows Service; веб-панель в браузере. | Основной приоритет разработки и проверки. |
| Linux-контейнер x64 | Образ сервера и Docker Compose с PostgreSQL, постоянными томами и конфигурацией HTTPS. | Опубликованный вариант сохраняется; развитие после завершения Windows. |
| Linux x64 без контейнера | Архив, отдельный пользователь сервиса, unit systemd, подключение к PostgreSQL; HTTPS напрямую или через обратный прокси. | Опубликованный вариант сохраняется; развитие после завершения Windows. |
| macOS arm64 / x64 | Нативный запуск и веб-панель; при необходимости launchd. Контейнер через Docker Desktop можно использовать отдельно. | Дополнительный этап после beta; потребуется проверка на настоящих Mac. |
| Linux arm64 | Дополнительный образ и нативный архив. | После проверки x64; совместимость .NET не заменяет проверку пакета и зависимостей. |

Начальная матрица: Windows 11 / Windows Server 2022 и новее, Ubuntu 24.04 LTS и Debian 12 и новее. Это целевые стенды, а не уже подтверждённая совместимость. Точные поддерживаемые версии ОС фиксируются после CI и установки на этих стендах.

Пути данных, логов, сертификата, порт и подключение к БД задаются конфигурацией. В контейнере данные находятся в постоянных томах, при нативной установке — вне папки программы. Веб-панель должна сообщать, что сервер запущен и как открыть её с другого компьютера. Для агентского подключения нужен конечный HTTPS-адрес с доверенным сертификатом: текущий клиент не следует перенаправлениям и проверяет TLS. Также сохраняется вариант размещения под префиксом, например `/backup/`.

## 3. Этапы разработки

### Этап 0 — согласовать границы и контракты

- Добавить проект `SPBackup.Server` и отдельные модели API без зависимости от WPF, диспетчера учётных данных Windows и локальных исполнителей.
- Зафиксировать API v1 и OpenAPI: существующие конфигурация, heartbeat и внешние SQL-отчёты; новые регистрация, результаты запусков и подтверждения ревизий.
- Определить модель данных, версию схемы, обновление и правила хранения истории. Лимит серверной истории не управляет удалением файлов копий на агентах.
- Разделить структурную проверку настроек на сервере и проверку доступности ресурсов на агенте. Linux-сервер принимает `C:\Bases`, UNC и ссылки на локальные секреты Windows, не проверяя их через собственные `Path` / `File.Exists`.
- Сохранить существующие идентификаторы часовых поясов и определить отображение Windows / IANA. Расчёт расписания агентом остаётся основным; контейнер включает нужные данные часовых поясов. Проверить переходы летнего времени на Windows и Linux.
- Спроектировать идемпотентный приём событий: ID запуска, порядок обновлений, неизменяемый итог, время события и время получения. В отчётах использовать этап и код ошибки, а текст передавать только после обработки секретов; сырой вывод процессов и строки подключения не переносить в серверные журналы.

**Готовность:** описаны схемы и миграции; контрактные примеры проходят одинаково на Windows и Linux, включая Windows-пути и часовые пояса. Старый клиент получает совместимые ответы; новые возможности согласуются по версии / возможностям агента.

### Этап 1 — сервер запускается и безопасно подключает агента

- Реализовать запуск через консоль, Windows Service, systemd и Docker Compose; проверки живости процесса и готовности БД.
- Добавить первоначальную настройку БД, HTTPS и первого администратора. У сервера нет общего пароля по умолчанию; первоначальная настройка закрывается после завершения.
- Добавить вход операторов и роли: просмотр, управление заданиями, администрирование. Учётные данные агента не дают доступ к административным маршрутам.
- Сделать добавление агента через одноразовое приглашение с ограниченным сроком, подтверждение подключения и отзыв токена. Сервер хранит хэш агентского токена, агент — токен в защищённом локальном хранилище, а не JSON.
- Реализовать существующие `GET configuration` и `POST heartbeat`: ID агента проверяется по токену; ревизия и `ETag` совместимы с клиентом.
- Добавить структурированные серверные логи с ротацией и ID запросов, без токенов и секретов. Сведения о сборке видны в панели и диагностике.

**Готовность:** реальный Windows-агент подключается к Windows-серверу и Linux-серверу по HTTPS. Перезапуск сохраняет регистрацию; отозванный токен не принимается; агент не может читать чужие данные. Для этого этапа достаточно тестового подключения, без перехода рабочих заданий в управляемый режим.

### Этап 2 — мониторинг и первая полезная веб-панель

- Общая панель: агенты без связи, неудачные и частично успешные задания, отсутствие ожидаемой копии, последняя успешная копия. Исправное состояние не скрывает предупреждения очистки.
- Карточка агента: версия, последняя связь, возможность исполнения, задания, текущая операция, история и результаты каждого хранилища.
- Подключить постоянную очередь отчётов обычных запусков агента. Подтверждать приём только после записи в БД, одинаковые повторы принимать без дублей, изменённые повторы отклонять.
- Реализовать приём уже предусмотренных `external-backups` и включить отправку существующей очереди хостом агента. SQL Server и PostgreSQL показывать отдельно с основанием наблюдения; запись в `msdb` не обозначать как проверенное восстановление.
- Добавить фильтры по агенту, заданию, результату и времени, пагинацию и понятное обозначение устаревших данных. Доступность определяется временем получения heartbeat сервером.
- Настроить срок хранения истории и аудита, предельные размеры запросов и индексы БД. Очистка истории не удаляет резервные копии.

**Готовность:** при недоступном сервере копирование продолжается; после восстановления связи отчёты появляются один раз и в порядке событий. Перезапуск сервера или агента не теряет подтверждённые / ожидающие отчёты. Поздний отчёт не делает завершённый запуск снова «выполняющимся».

### Этап 3 — управление настройками и первая alpha

Текущая подготовка единого источника заданий и оставшиеся условия включения описаны в [managed-execution.md](managed-execution.md).

- Реализовать создание, изменение, отключение и удаление задания в компактном веб-мастере. Доступны текущие типы источников, полное / инкрементное копирование файлов, расписание, временная папка, ZIP / AES-256 и несколько хранилищ с отдельными лимитами.
- Использовать возможности и версию конкретного агента: недоступные ему параметры не назначаются молча. Секреты задаются локально; сервер оперирует только ссылками и доступностью привязки, не значениями паролей.
- Сохранять полный набор заданий атомарной новой ревизией, защищать параллельное редактирование через `If-Match`, показывать сохранённую и принятую ревизии отдельно.
- Добавить отчёты принятия / отказа. Ошибка одной настройки отклоняет всю ревизию; прежняя конфигурация остаётся действующей. Возврат к прежним значениям создаёт новую ревизию.
- Подключить `Managed` к реальному фоновому хосту: исполнитель, каталог, история, очередь отчётов и API-цикл. После alpha.29 подключён headless-хост Managed с изолированными данными, ручной очередью, синхронизацией и ревизией результата; в окне Windows добавлено включение серверных заданий через сохранённое приглашение, ручной запуск и запуск службы; веб-мастер ещё не завершён. Подробнее — [managed-execution.md](managed-execution.md).
- Сохранить единственного исполнителя на машине через существующую координацию. Переключение режимов и принятие настроек не создаёт второго планировщика; автономные задания остаются отдельными.
- Добавить аудит автора и изменённых полей. Работающий запуск использует прежний снимок настроек до завершения; отключение действует для следующих запусков после принятия ревизии.

**Готовность alpha:** администратор подключает агент, видит реальные копии и внешние SQL-наблюдения, изменяет расписание / хранилища и получает подтверждение конкретной ревизии. Агент продолжает принятую конфигурацию офлайн. Сначала этот сценарий проходит с сервером на Windows; контейнер и systemd проверяются на последующем этапе Linux. Проверяется небольшой стенд из 5–20 агентов; это объём проверки, не заявленная предельная ёмкость.

### Этап 4 — команды и уведомления

- Добавить удалённый ручной запуск и проверку последней копии через очередь команд: ID, срок действия, получение, состояние выполнения, результат и аудит.
- Агент забирает команды исходящими запросами. Повторная доставка не создаёт второй запуск; после сбоя незавершённая команда получает состояние, требующее проверки, а не автоматическое повторное исполнение. Восстановление базы и произвольные команды оболочки в начальный набор не входят.
- Добавить уведомления в панели, затем email и webhook: ошибка копии, частичная доставка, длительное отсутствие связи, просроченная копия, отказ конфигурации и восстановление нормального состояния. Повторяющиеся события объединяются.
- Показывать очередь ещё не принятых команд и устаревшие результаты явно. Истёкшая команда не выполняется после позднего подключения.

**Готовность:** потеря ответа или повтор запроса не запускает копирование дважды; нет уведомления об успехе без результата. Порог просрочки учитывает расписание, часовой пояс, допуск и выключенные задания.

### Этап 5 — эксплуатация и beta

- Подготовить Windows-установщик / обновление службы, версионированный Linux-образ и Compose, архив и unit systemd. Обновление сохраняет данные и явно выполняет миграции; совместимость старых агентов проверяется.
- Добавить резервное копирование и проверенное восстановление самого сервера: БД, настройки, необходимые ключи и сертификаты. Перед изменением схемы создаётся копия; возврат приложения после несовместимой миграции требует совместимого восстановления БД.
- Добавить метрики, контроль свободного места, экспорт серверной диагностики и журнал административных действий. Диагностический ZIP агента остаётся ручной выгрузкой; загрузку на сервер, если она понадобится, проектировать отдельно с явным действием пользователя, правами и сроком хранения.
- Прогнать нагрузку минимум на стенде 100 агентов с очередями отчётов после отключения, зафиксировать задержки и потребление ресурсов. Разработать рекомендации по памяти, диску и срокам истории по результатам измерений.
- Расширить эксплуатационные проверки уже реализованной службы Windows-агента и управления из WPF: разные учётные записи, права SQL / UNC / FTP, обновление и восстановление профиля. Служба агента и Windows Service сервера — разные компоненты.

**Готовность beta:** проверены обновление, восстановление после потери БД / перезапуска, истёкший сертификат, отзыв токена, переполнение диска и накопленная очередь. Есть инструкции для всех трёх основных способов установки и известные ограничения. Сервисный режим агента объявляется готовым только после собственной проверки; сервер сам по себе не устраняет ограничения агента текущего пользователя.

### Этап 6 — дополнительные платформы и масштабирование

После beta оценить нативную macOS, Linux arm64, единый вход через OIDC, группы организаций и площадок, шаблоны заданий, централизованное управление секретами, несколько серверных экземпляров и отказоустойчивость. Каждое расширение получает отдельный контракт и проверку. macOS прежде всего получает ту же веб-панель; нативный пакет и launchd — только при практической необходимости.

## 4. Первый набор API

| Группа | Начальный объём |
| --- | --- |
| Подключение | Создание / погашение приглашения, регистрация агента, смена и отзыв учётных данных. Новые маршруты фиксируются на этапе 0. |
| Существующие агентские маршруты | `GET /api/v1/agents/{agentId}/configuration`, `POST .../heartbeat`, `POST .../external-backups`. |
| Отчёты и принятие настроек | `POST .../runs`, `POST .../configuration-results`; ID события, порядок и результаты каждого назначения. |
| Управление | Список / карточка агента, чтение истории и конфигурации, `PUT configuration` с `If-Match`, аудит. Предлагаемые маршруты уже перечислены в server-management.md. |
| Команды — следующий этап | Создание, получение и подтверждение команды, чтение состояния; отдельные права и срок действия. |

Контракты новых отчётов должны содержать ревизию запуска, отдельные результаты хранилищ, ошибки проверки и предупреждения очистки, а для файловых инкрементов — сведения о снимке / цепочке. Не смешивать ошибки связи, результат копирования и наличие наблюдения внешней SQL-копии. Обновление статуса и приём отчёта — транзакционные операции с ограниченным размером тела.

## 5. Интерфейс первой версии

Навигация: **Обзор → Агенты → Задания → История → Внешние SQL-копии → Настройки**. На обзоре сначала показываются проблемы и время актуальности данных. Результат каждого хранилища доступен из запуска; частичный успех заметен сразу. Карточка агента объясняет, когда он связывался и какие настройки реально принял.

Мастер задания повторяет понятный порядок локального приложения: **Источник → Расписание → Архив и временная папка → Хранилища → Проверка и сохранение**. После сохранения показывается «Ожидает применения», а не «Настроено». Ввод Windows-пути сопровождается пояснением «на компьютере агента». Возможность восстановления и доступа к источнику подтверждается агентом, а не размещением сервера.

## 6. Ближайший результат разработки

Этапы каркаса, регистрации, отчётов и мониторинга реализованы; Windows-установщик и пакет с Docker Compose опубликованы. В preview.2 разделены имя системы мониторинга и HTTPS-адрес подключения; preview.3 использует название MS SQL. Ближайший серверный этап — редактирование заданий с подтверждением ревизий и управляемое исполнение. Windows-служба автономного агента уже реализована и развивается отдельно. Нативный Linux/systemd и целевые ОС требуют проверок, перечисленных в инструкции и ограничениях.

Сроки и предельное количество агентов уточняются после первого сквозного сценария и измерений. Контрольные результаты — работающая регистрация, мониторинг, управляемые настройки, alpha и beta; сами по себе экраны или запуск сервера не означают готовность управления копированием.
