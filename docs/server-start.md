# Запуск первой серверной версии

Реализована основа сервера: PostgreSQL, первоначальный администратор, веб-панель, одноразовые приглашения, регистрация агента, отзыв токена, API конфигурации и heartbeat. Сведения о регистрации и связи сохраняются между перезапусками. Все административные страницы требуют входа; изменяющие запросы защищены от CSRF.

Пока конфигурация нового агента содержит пустой набор заданий с ревизией 1. Редактор заданий, отчёты о копировании / внешних SQL-копиях, роли наблюдателей и операторов и подключение Managed к рабочему фоновому хосту будут следующими этапами. Регистрация через API не переключает существующую Windows-программу в рабочий управляемый режим. Автономное копирование продолжает работать независимо. Обновлённый план — в `docs/server-roadmap.md` репозитория.

## Что требуется

- Серверный пакет Windows x64 или Linux x64 с собственным .NET runtime; при запуске из исходников — SDK 10.0.402.
- PostgreSQL 17: локальный или внешний. В Docker Compose СУБД включена отдельным контейнером; в нативной установке её нужно подготовить отдельно.
- HTTPS-сертификат для адреса сервера, файл PFX и файл с его паролем. На клиентских компьютерах сертификат должен быть доверенным; сертификат для localhost не подходит для другого имени сервера.
- Отдельный постоянный каталог сервера для ключей сессий и диагностических логов. Удаление этого каталога завершает прежние веб-сессии; база агентов находится в PostgreSQL.

Пароли передаются через защищённые файлы, значения не входят в пакеты и примеры. Каталог конфигурации доступен только владельцу / учётной записи сервиса. Сервер не отключает проверку сертификатов агента. Для удалённой PostgreSQL задайте параметры проверки TLS, например `SSL Mode=VerifyFull;Root Certificate=<полный путь>`.

## Нативная установка Windows

Распакуйте весь пакет, например в `C:\Apps\1C-Backup-Server`. Подготовьте `C:\ProgramData\OneCBackupServer\server.json` с настройками, заменив имя сервера:

```json
{
  "AllowedHosts": "backup.example.com;localhost",
  "Urls": "https://0.0.0.0:7443",
  "Server": {
    "DataDirectory": "C:\\ProgramData\\OneCBackupServer\\data",
    "ConnectionStringFile": "C:\\ProgramData\\OneCBackupServer\\connection-string.txt",
    "HttpsCertificatePath": "C:\\ProgramData\\OneCBackupServer\\server.pfx",
    "HttpsCertificatePasswordFile": "C:\\ProgramData\\OneCBackupServer\\certificate-password.txt",
    "BootstrapUser": "admin",
    "BootstrapPasswordFile": "C:\\ProgramData\\OneCBackupServer\\administrator-password.txt"
  }
}
```

Файл `connection-string.txt` содержит строку подключения Npgsql: адрес, порт, базу, пользователя и пароль. База должна уже существовать; при инициализации её пользователь должен иметь права создания серверных таблиц. Пример структуры без секретного значения: `Host=localhost;Port=5432;Database=onecbackup;Username=onecbackup;Password=<ваш пароль>`. В остальных файлах — пароль PFX и новый пароль администратора длиной 12–256 символов. Эти файлы создаются вне распакованного пакета с ограниченными ACL.

Из папки программы выполните в PowerShell:

```powershell
.\OneCBackup.Server.exe --Server:ConfigFile C:\ProgramData\OneCBackupServer\server.json --initialize
.\OneCBackup.Server.exe --Server:ConfigFile C:\ProgramData\OneCBackupServer\server.json
```

Первый запуск создаёт таблицы и первого администратора, затем завершается. Повторный `--initialize` не сбрасывает пароль и сообщает `administrator_already_exists`. Для применения последующих миграций предусмотрен `--migrate`; приложение откажется работать с неподготовленной или более новой схемой. Миграции выполняются в транзакции под блокировкой PostgreSQL.

Откройте настроенный адрес, например `https://backup.example.com:7443/`, и войдите. Для службы Windows предусмотрен встроенный Windows Service lifetime с именем `OneCBackupServer`. Зарегистрируйте исполняемый файл с тем же аргументом `--Server:ConfigFile` и выделенной учётной записью; дайте ей доступ к конфигурации и постоянному каталогу. Ключи сессий Windows защищаются DPAPI этой учётной записи. При переходе от консольного запуска к другой сервисной учётной записи используйте отдельный каталог ключей / данных и войдите заново. Установщик и автоматическая регистрация службы пока не добавлены.

## Нативная установка Linux

Распакуйте архив в `/opt/onec-backup-server`; исполняемый файл `OneCBackup.Server` должен сохранить право исполнения. Создайте отдельную учётную запись `onec-backup-server`. Подготовьте PostgreSQL и защищённые файлы в `/etc/onec-backup-server`.

Скопируйте `server.env.example` как `server.env` и замените адрес / пути. Передайте переменные из этого файла процессу и один раз запустите `/opt/onec-backup-server/OneCBackup.Server --initialize` под сервисной учётной записью. Например, в shell этой учётной записи:

```sh
set -a
. /etc/onec-backup-server/server.env
set +a
/opt/onec-backup-server/OneCBackup.Server --initialize
```

Для этого запуска заранее создайте `/var/lib/onec-backup-server`, передав владение сервисной учётной записи и задав режим 0700. `server.env` и файлы секретов должны быть доступны этой учётной записи, но не остальным пользователям. Unit `onec-backup-server.service` использует `/opt/onec-backup-server`, постоянный каталог `/var/lib/onec-backup-server` и отдельный EnvironmentFile. Установите unit через администратора ОС, выполните `systemctl daemon-reload` и `systemctl enable --now onec-backup-server`. Шаблон не заменяет установку PostgreSQL и сертификата.

## Docker Compose

Из репозитория используйте `deploy/server/compose.yaml`. Подготовьте закрытый каталог `deploy/server/secrets` (0700) и четыре файла:

- `database-password.txt` — новый пароль контейнерной PostgreSQL;
- `administrator-password.txt` — новый пароль первого администратора, минимум 12 символов;
- `server.pfx` — сертификат с закрытым ключом;
- `certificate-password.txt` — пароль PFX.

На Linux для файлов внутри закрытого каталога задайте 0444: Compose монтирует отдельные файлы только для чтения, чтобы непривилегированный пользователь приложения мог прочитать их. Закрытый родительский каталог сохраняет ограничение доступа на хосте. Сервер работает не от root. Не добавляйте эти файлы в Git или Docker build context.

При необходимости задайте `SERVER_HOSTS`, `SERVER_BIND_IP`, `SERVER_PORT`, `SERVER_ADMIN_NAME` и `SERVER_SECRETS_DIRECTORY`. По умолчанию внешний порт доступен только на 127.0.0.1:7443; для доступа с других компьютеров настройте адрес привязки и сертификат для реального имени.

```sh
docker compose -f deploy/server/compose.yaml build
docker compose -f deploy/server/compose.yaml run --rm server --initialize
docker compose -f deploy/server/compose.yaml up -d
```

Команда инициализации ждёт готовности PostgreSQL, создаёт схему и первого администратора. Серверные ключи / логи и база находятся в отдельных постоянных томах. Обычная остановка и последующий запуск сохраняют данные. После смены пароля в файле уже инициализированная PostgreSQL не меняет пароль пользователя автоматически; изменение выполняется в самой СУБД и согласованно в конфигурации. Удаление томов требует отдельного решения и резервной копии данных.

Для сборки за корпоративным HTTPS-прокси предусмотрен необязательный Docker build secret `build-ca` с публичным сертификатом доверенного удостоверяющего центра. Он добавляется только в доверенные сертификаты образа сборки, не в образ работающего сервера; TLS и проверка NuGet-пакетов остаются включёнными. Тестовый скрипт `tests/server/compose_smoke.py` использует существующий `SSL_CERT_FILE`, если он задан средой.

## API первого этапа

Все обращения агента — по HTTPS. В панели создайте приглашение, при необходимости привязав к уже известному UUID агента. Код действует 1–60 минут и показывается только в ответе создания. Дальнейшее подключение выполняется через API; мастер в Windows-приложении пока не подключён.

| Маршрут | Назначение |
| --- | --- |
| `POST /api/v1/enrollment` | Однократно погасить приглашение; тело: `invitationCode`, `agentId`, `name`. Ответ 201: `agentId`, `token`, `protocolVersion`. |
| `GET /api/v1/agents/{agentId}/configuration` | Bearer-токен только этого агента. Возвращает API v1 и `ETag: "1"`; подходящий `If-None-Match` даёт 304. |
| `POST /api/v1/agents/{agentId}/heartbeat` | Существующий контракт heartbeat; 204 только после сохранения. Время сервера и агента хранятся отдельно. |
| `GET /api/v1/management/session` | Административная cookie-сессия; получает `csrfToken` для заголовка `X-CSRF-TOKEN`. |
| `GET /api/v1/management/agents?page=0` | Список, 50 записей на страницу, число агентов. |
| `GET /api/v1/management/agents/{id}` | Карточка агента без значений токенов и паролей. |
| `POST /api/v1/management/invitations` | Cookie + CSRF; тело: `name`, необязательный `agentId`, `minutes` (30 по умолчанию). |
| `POST /api/v1/management/agents/{id}/revoke` | Cookie + CSRF; немедленно отзывает серверный токен. |
| `GET /openapi/v1.json` | Описание реализованного API, после входа администратора. |
| `GET /health/live`, `GET /health/ready` | Живость процесса и доступность правильной схемы PostgreSQL; готовы — 200, недоступная БД / схема — 503. |

Полученный агентский токен показывается только при успешной регистрации. Он не даёт права управления сервером или чтения другого агента. В БД хранятся только хэши агентских токенов и приглашений. Повтор приглашения, истёкший код и неподходящий UUID отклоняются. Уже зарегистрированный UUID нельзя перезаписать обычным приглашением; повторная выдача токена тому же агенту будет отдельной операцией следующего этапа. Отзыв доступа не отменяет автономное копирование или последнюю принятую локальную конфигурацию.

Для размещения под `/backup/` задайте `Server:PathBase=/backup`; адрес клиента должен содержать этот префикс. При TLS на обратном прокси явно задайте IP доверенного прокси в `Server:TrustedProxies`. Без этого присланный `X-Forwarded-Proto` не делает HTTP-запрос доверенным HTTPS. В Production запросы к панели / API по HTTP получают 426. Только для локальной разработки предусмотрен `Server:AllowInsecureLoopback=true` вместе с окружением Development и реальным loopback-адресом; он не действует в Production.

## Диагностика и разработка

Структурированные серверные логи находятся в `<DataDirectory>/logs`: события, UTC, сессия, ID агента / запроса, версия, тип и код ошибки. Текст исключений, заголовки, тела запросов и секреты не записываются. Ротация: 14 дней, до 2 МБ на файл, общий бюджет 50 МБ. Ошибка логирования не меняет результат регистрации или heartbeat. Состояние сервера пока проверяется через health API и каталог логов; отдельная выгрузка серверной диагностики будет позже.

Из исходников:

```sh
dotnet restore OneCBackup.slnx
dotnet build OneCBackup.slnx --no-restore -m:1 -nr:false
python3 tools/dev_server_db.py start
```

Последняя команда создаёт только отдельный контейнер PostgreSQL разработки на 127.0.0.1:15432 и защищённый файл `artifacts/server-dev/connection-string.txt`; пароли не выводятся. Повторный запуск использует этот контейнер. `python3 tools/dev_server_db.py stop` останавливает и удаляет только контейнер с меткой этого стенда; постоянной пользовательской БД команда не касается. Для сервера задайте путь подключения через `Server:ConnectionStringFile` и подготовьте остальные параметры выше.

Интеграционные проверки используют собственную временную схему PostgreSQL и настоящий Kestrel с TLS. Укажите `ONECBACKUP_SERVER_TEST_CONNECTION_FILE` на файл подключения к **тестовой** PostgreSQL, затем выполните `dotnet test tests/OneCBackup.Server.Tests --no-restore -m:1 -nr:false --filter 'Category!=ServerPackage'`. Без этой переменной проверки явно пропускаются. Проверка клиентом использует отдельный тестовый доверенный сертификат; производственная проверка TLS сохраняется.

Пакеты: `python3 tools/build_server_distribution.py --runtime win-x64` или `--runtime linux-x64`; результат в `artifacts/server`, рядом SHA-256. macOS и Linux arm64 пока не входят в сборку. Установочные шаблоны systemd / Windows Service требуют отдельной проверки на целевых сервисных учётных записях.
